## 最小差分主義の禁止

「目先の指示を満たす最小の変更」で作業を終えてはならない。

**機能追加・不具合修正が終わった時点のアプリケーション全体のコードが、最も綺麗な状態になっていなければならない。**

既存の構造に継ぎ足すと歪みが生じる場合は、構造の方を直すこと。
今回の変更が触れたクラス・モジュール、およびその変更によって歪みが生じた呼び出し元・呼び出し先は、指示がなくてもリファクタしてよい。

## アプリケーション全体のフォルダ・ファイル・処理・モジュールの役割分担の見通しをよくする

将来そのソースコードを読む者は、多くの場合、特定の観点をもって、その時の目的のソースコードだけを探す。
基本的には「大から小へ」「全体から部分へ」「概要から部分へ」の順で探索する。

このとき、「読み飛ばせる量」が多いほどよい。つまり、その部品を識別するもの（フォルダ名・ファイル名・モジュール名・関数名や引数や戻り値など）だけを見て「中身を読まなくてよい」と判断できるコードの量が多いほど、良い設計である。

具体的には以下のような手段でこれを実現する。

### フォルダ名とファイル名を見るだけで大まかな構成が分かるようにフォルダ分割・ファイル分割する

あるフォルダ1個の直下に並ぶフォルダ名とファイル名を見たときに、各フォルダないしファイルの役割とこの親フォルダの全体的な構造がおおまかにつかめるようにする。

NG: 関心のある箇所にたどり着くため index.tsx を全部読む必要がある
- AppLayout (Folder)
  - index.tsx

OK: 適切な粒度で分割されている
- AppLayout (Folder)
  - index.ts
  - HeaderPane.tsx
  - ContenetPane.tsx
  - FooterPane.tsx

NG: 細切れすぎて index.tsx を全部読んで目的のものを探しているのと変わらない
- AppLayout (Folder)
  - index.ts
  - HeaderPane.tsx
  - HeaderTitleSection.tsx
  - HeaderEndButtonSection.tsx
  - ContenetContainer.tsx
  - ContenetTitle.tsx
  - ContenetMainTable.tsx
  - ContenetDetail.tsx
  - ContenetSideBar.tsx
  ...

どうしても規模が大きすぎて多くのファイル分割が必要ならサブフォルダを切る方がよい
- AppLayout (Folder)
  - index.ts
  - Header (Folder)
    - index.ts
    - HeaderPane.tsx
    - TitleSection.tsx
    - EndButtonSection.tsx
  - Content (Folder)
    - index.ts
    - Container.tsx
    - Title.tsx
    - MainTable.tsx
    - Detail.tsx
    - SideBar.tsx
  - FooterPane.tsx

### 凝集度は高く、結合度は低く

各クラス・モジュールは 1 つの関心事に責任を持ち、他のモジュールの内部事情を知らない方が望ましい。

### 役割語より目的語や名詞で名づける

`XxxHelper`, `XxxService`, `XxxManager`, `XxxUtil`, `XxxProcessor` のような
「名詞 + 役割語」のモジュールは、「個々のファイルの見通し」は良くなるが、モジュール数が爆発して役割分担が不明瞭になりアプリケーション全体の把握ができなくなる。

`XxxHelper` 等の名前を付けたくなったら、その Xxx がドメイン上のオブジェクト（名詞）である。
この Xxx をモジュール名（java や C# ならクラス、React.js ならコンポーネントやフック）とし、Helper / Service / Manager が持つはずだった責務を Xxx の振る舞いとして定義する。

```cs
// NG: 役割語クラスの乱立
class OrderValidator { public bool Validate(Order order) { ... } }
class OrderPriceCalculator { public decimal Calculate(Order order) { ... } }

// OK: 名詞クラスに振る舞いを持たせる
class Order {
    public IEnumerable<string> Validate() { ... }
    public decimal CalculatePrice() { ... }
}
```

例外として、「本来標準ライブラリやフレームワークが提供していてもおかしくない汎用処理」の穴埋めは `XxxUtil` などにまとめて構わない。（例: 文字列結合関数、数値のクランプ関数、など。これと同レベルならよい）

### 外部に公開するものを最小限にする

ここでいう「外部に公開するもの」とは、そのクラス・モジュールの外から呼び出せる・参照できるもの全般を指す
（C# の public / internal メンバー、TypeScript の export など）。

- 複雑なロジックは、複数のクラス・ファイルに散らばらせるのではなく、
  特定の 1 クラス・1 モジュールの中に閉じ込めること。
- 外部に公開するものは最小限にし、それぞれに意味の明瞭な名前を付けること。
- モジュールの**内部**を private メソッド・内部関数に分割するのは自由である。
  内部が長くなること自体は問題ではない。問題なのは外部に公開するものが増えること。

### エントリーポイントの処理を簡潔にする

エントリーポイントとは、ある時間的なトリガーを開始としてその処理が停止するまでの処理の入り口。
C# の Main関数、COBOLのメインルーチン、Webサーバーであれば HTTP エンドポイント、
HTMLであればDOMイベントハンドラー、といったものがこれに該当する。

このとき、エントリーポイントに処理の詳細を全て書いてしまうと、その処理で何をやっているか、逆にその処理では何をやっていないかが分かりづらくなる。

エントリーポイントのソースコードが長くなりすぎる場合は、ある程度の処理の塊に適切な名前をつけて処理を要約し、別モジュールに逃がす。

なお、これはエントリーポイントを短くするためだけに `ProcessCore`, `ExecuteInternal`, `XxxFlow` のような下請けへ括り出せという意味ではない。これはエントリーポイントの役割がその別モジュールに移動しただけであり、「読み飛ばせる量」が増えていないからである。

基準は **流れを追う読み手がそれを開く必要があるか**。
名前だけで効果が予測でき中を読まなくてよいものは、いくつ増えてもよい。

### 1つのファイル内の記述順は「外部公開から内部用へ」「全体から詳細へ」「大から小へ」の順で書く

最初にそのファイル全体のスコープが分かればファイルの下の方を読み飛ばしやすくなるため。
もちろん、変数のスコープの順序の制約などによりこの順で書けない場合は許容する。
