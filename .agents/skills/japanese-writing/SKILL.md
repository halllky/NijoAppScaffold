# 日本語の文章の書き方

## 1. 読み手から見た振る舞いを書く

書く前に、誰が何のために読むかを決める。そのうえで、その人の疑問（なぜそうなのか、どこまでが対象か、足りないときはどうするか）に答える形で書く。

実装した直後は、実装をそのまま文章に書き写しがちである。

- 実装を書き写した例: 複数件の保存は、Entity Framework Core の1回の保存処理にまとめる。
- 読み手から見た振る舞い: 画面から行う複数のデータの一括更新は、原則として1件でも失敗したら全件ロールバックする。

## 2. 文体

日本の業務システム開発の現場にいる中堅のエンジニアが、設計書やコメントに書く言葉で書く。

- 技術用語、フレームワークの用語、クラス名は、そのまま使う。和語や説明的な言い方に言い換えない。
- 1つの文には1つの事柄を書く。

分かりやすさは、平易な語を選ぶことではなく、文を短くし、何が何をするのかをはっきり書くことで出す。

## 3. 手本

視点や密度の参考にする。語の対応表としては使わない。

具体的な場面と、それが起きる理由が書かれている。

> 更新を伴う処理の呼び出しに付けられた冪等キー。更新ボタン連打やタイムアウト時のリトライなどで同じ処理が二重に処理されてしまうのを防ぐ。

対象外のことと、そのときの手段が書かれている。

> 検索条件は、入力されたものをすべて満たす（AND検索）データに絞り込む。
> （備考）OR検索や複雑な検索条件が必要な場合は個別に手書きで実装する。

用語の範囲を、読み手が判断できるように定義している。

> ここで言う外部システムとは、このシステムの開発チームの管理下に無いもの、環境によってはモックを置いて動作させたくなるものを指す。例えばデータベースやログファイルは確かにアプリケーションのメモリ空間の外部にあるが、外部システムではない。

標準にしなかった方式について、その理由を書いている。

> 特別な仕組みは用意していないので、単に各データに削除フラグを逐一定義したり、EFCoreのグローバルクエリフィルターで削除フラグtrueのデータを弾いたりすることで対応する。削除フラグ方式を標準としていない理由は以下。
> - 簡単に削除フラグが使える基盤を用意してしまうと、人の退職済みやワークフローの取り下げといった本来削除フラグではなく独立したステータスとして管理すべき状態に削除フラグが濫用されてしまう可能性が上がるので、これを防ぐため。

引数の説明は、読み手が知りたいことだけを短く書いている。

> `<param name="isDevelopment">開発環境としての設定構築をするかどうか</param>`

<!-- 以下の3つは原案。人が書き直したら、このコメントを消す -->

仕様書の仕様項目。後から当事者がこの記述をもとに判断するので、境界と例外を省かずに書いている。それでも文ごとに主語がはっきりしている。

> 最終操作から24時間が経過したセッションは無効とする。最終操作とは、ログイン中のユーザーによるサーバーへの最後のリクエストを指し、画面遷移時に自動で発行されるリクエストも含む。ただし、ヘルスチェックのリクエストと、静的ファイルの取得は含まない。

制約と、それに当たったときの手段を書いている。

> ログイン失敗回数はサーバーのメモリ上で数えるため、複数台構成では台数分だけ多く失敗できる。台数によらず制限したい場合は、失敗回数を DB などの共有ストレージに保持するよう改修する。

表の前置き。表が何の組み合わせを整理したものかを、表を読む前に分かるようにしている。

> ログイン状態は、Cookie の有無、DB 上のセッションの有無、最終操作からの経過時間の3つで決まる。次の表は、その組み合わせごとに、サーバーがログイン中として扱うかどうかを整理したものである。

## 4. 推敲する

### 4.1 削る

読み手の理解にも判断にも使われない記述を削る。特に次のもの。

- 「今は〜だけを使っている」のような、すぐ古くなる現状の説明
- 読み手の判断に使われない理由
- 本文の理解に要らない参照

ただし、仕様書の仕様項目のように、後からその記述をもとに判断するための文では、場合分けや例外を読みやすさのために削らない。

### 4.2 自分では気付きにくい癖を直す

次の癖は、書いた本人には自然に読めてしまう。見つけたら、語を置き換えるのではなく文を書き直す。

- 主題と動作主のずれ。「待機中のジョブは5秒おきに確認する」では、確認するのはサーバーであってジョブではない。
- 主語の省略。前の文と主語が変わったのに、後の文で主語を省いている。
- 英語の直訳。「ジョブは、起動したユーザーとして実行する」（run as）、「ブラウザに Cookie を消させる」（make A do）、「開発環境でだけ使える」（only in）。

### 4.3 文脈を知らない読み手に読ませる

書いた本人は、自分の知識で文の不足を補って読んでしまう。まとまった量の文章を書いたら、サブエージェントに、書いた文章と想定する読み手だけを渡して読ませる。依頼の例:

```
あなたは業務システム開発の経験がある開発者で、この文章を初めて読む。
次の文章を読み、以下を挙げてほしい。文章の修正はしなくてよい。

- 一読して意味が取れない箇所
- 業務システム開発の現場の設計書では使わない言い回し。<このファイルの絶対パス> の 4.2 の癖を含む
- 読み手として当然知りたいのに書かれていないこと
- 読み手にとって不要な記述

想定する読み手: <誰が、何のために読むか>
文章:
<推敲する文章>
```

指摘のとおりに直すかは自分で判断する。直すときは、語の置き換えではなく文ごと書き直す。4.2 にない癖が繰り返し指摘されるなら、4.2 に足す。
