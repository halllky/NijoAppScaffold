# 日本語の文章の書き方

このスキルは、文章の「形式」ではなく「書き方の手順」を定める。
細かな言い回しの禁止リストは置かない。禁止リストを守ろうとすると、それを避けるための別の不自然な言い回しが生まれるためである。
代わりに、書く前・書いた後に何を考えるかを定める。

対象: コメント、ドキュメント、仕様書、nijo.xml の説明、コミットメッセージ。
コメントに固有の「何を書くか・書かないか」は cleanup-comment スキルにある。言葉づかいと手順はこのスキルに従う。

## 1. 書く前に、読み手と目的を決める

文章を書く前に、次の2つを頭の中で一文にする。

- 誰が読むか（例: このクラスを初めて触る開発者 / テンプレートの採用を検討している人 / 本番の障害を調べている運用担当者）
- その人は何をするために読むか（例: このメソッドを呼んでよいか判断する / カスタマイズの手順を知る）

そのうえで、その読み手が抱く疑問に答える形で書く。よくある疑問は次のとおり。

- なぜそうなっているのか。ほかのやり方ではなぜ駄目なのか。
- どこまでが対象で、何が対象外か。
- それで足りないときは、どうすればよいか。
- 具体的にはどんな状況の話か。（抽象的な仕組みより、「ボタンの連打」「タイムアウト後のリトライ」のような具体的な場面の方が伝わる）

実装した直後は、頭の中にあるのが実装なので、実装をそのまま文章に書き写しがちである。
それは読み手にとって意味のある単位になっていないことが多い。

- 実装を書き写した例: 複数件の保存は、Entity Framework Core の1回の保存処理にまとめる。
- 読み手にとって意味のある形: 画面から行う複数のデータの一括更新は、原則として1件でも失敗したら全件ロールバックする。

「どう実装したか」ではなく「読み手から見てどう振る舞うか、なぜそうなのか」を書く。

## 2. 文体の基準

想定する書き手は、日本の業務システム開発の現場にいる中堅のエンジニアである。その人が、ほかの開発者や関係者に向けて設計書やコメントを書くときの言葉で書く。

- 技術文書で普通に使う語は、そのまま使う。分かりやすくしようとして和語や比喩に言い換えると、かえって不自然になる。例えば、「確認する」を「確かめる」に、「再読み込み」を「読み込み直す」に、「リクエスト」を「問い合わせ」に言い換えない。
  開発の現場で定着しているカタカナ語や英語（マスキング、オーバーライド、カスタマイズ、遷移、ロールバック、など）も同じである。
- フレームワークやライブラリの用語、このリポジトリの中核のクラス名など、開発者がその名前で認識しているものは、名前のまま書く。説明的な言い換えで遠回しにしない。例えば、JavaScript を「画面のプログラム」と言い換えない。
  初出で日本語の呼び名を使うなら、括弧で英語の名前を添える（例: オペレーションコンテキスト(OperationContext)）。
- 「AのBのCのD」のように「の」を連ねて語を分解しない。開発者が普通に使う複合語（一覧画面、起動ユーザー、作業フォルダ、ログインダイアログ）はそのまま使う。
- 1つの文には1つの事柄を書く。読点で事柄をいくつもつなげない。並列する項目が3つ以上あるなら箇条書きにする。
- 段落も1つの話題に絞る。章の冒頭の概要に、別の話題（補足、注意、参照先）を詰め込まない。

分かりやすさは、平易な語を選ぶことではなく、文を短くし、何が何をするのかをはっきり書くことで出す。

## 3. ルールとの付き合い方

コメントや仕様書には、物理名を書かない、変更の経緯を書かない、などのルールがある。
これらはすべて目的（修正漏れを防ぐ、ゼロから読む人を迷わせない、など）のためにある。

ルールを守るために不自然な言い回しや遠回しな説明が必要になるなら、そのルールの目的に照らして判断し、自然に書ける方を選ぶ。
ルールを守った結果、読み手に伝わらない文章になるのは本末転倒である。

## 4. 手本

この文体の手本として、人が書いた文を挙げる。語の対応表として使うのではなく、視点や密度の参考にする。

具体的な場面と、それが起きる理由が書かれている。

> 更新を伴う処理の呼び出しに付けられた冪等キー。更新ボタン連打やタイムアウト時のリトライなどで同じ処理が二重に処理されてしまうのを防ぐ。

対象外のことと、そのときの手段が書かれている。

> 検索条件は、入力されたものをすべて満たす（AND検索）データに絞り込む。
> （備考）OR検索や複雑な検索条件が必要な場合は個別に手書きで実装する。

用語の範囲を、読み手が判断できるように定義している。

> ここで言う外部システムとは、このシステムの開発チームの管理下に無いもの、環境によってはモックを置いて動作させたくなるものを指す。例えばデータベースやログファイルは確かにアプリケーションのメモリ空間の外部にあるが、外部システムではない。

標準にしなかった方式について、その理由を書いている。

> 特別な仕組みは用意していないので、単に各データに削除フラグを逐一定義したり、EFCoreのグローバルクエリフィルターで削除フラグtrueのデータを弾いたりすることで対応する。削除フラグ方式を標準としていない理由は以下。
> - 簡単に削除フラグが使える基盤を用意してしまうと、人の退職済みやワークフローの取り下げといった本来削除フラグではなく独立したステータスとして管理すべき状態に削除フラグが濫用されてしまう可能性が上がるので、これを防ぐため。

引数の説明は、読み手が知りたいことだけを短く書いている。

> `<param name="isDevelopment">開発環境としての設定構築をするかどうか</param>`

## 5. 推敲する

書き終えたら、次の手順で推敲する。

推敲しても、記述の厳密さそのものが役割の文は短くしない。仕様書の仕様項目のように、書いた時点で決めきれなかったことを、後からその記述をもとに判断するための文である。こうした文では、場合分け・境界・例外を、読みやすさのために削らない。厳密さは、語を足すことではなく、主語と条件をはっきり書くことで出す。

### 5.1 削る

書き足すより先に、削れるものを探す。次のものは、読み手が困らないなら削る。

- 章番号や仕様 ID への参照。本文を理解するのに必要なものと、その文書の記載ルールが求めるものだけ残す。
- 「〜はソースを正とする」「〜の対応は必要ない」のような断り書き。
- 「今は〜だけを使っている」のような、すぐ古くなる現状の説明。
- 実装の手順の説明。ソースを読めば分かるものはソースに任せる。
- 設計の理由のうち、読み手の判断に使われないもの。
- 同じ値（期限や件数など）を何か所にも書いているもの。値から導いた値（「期限24時間」と「クリーンナップは毎日」から導いた「最大48時間」など）も同じである。値を変えたときの直し漏れになる。

### 5.2 読み返して直す

読み返して、次のような箇所を探す。どれも AI が書いた文や英語から訳した文に多く、書いた本人は気付きにくい。
挙げた例は症状を見分けるためのもので、使ってはいけない語の一覧ではない。見つけたら、その語だけを置き換えるのではなく、文を書き直す。
表のセルも対象である。厳密さが役割のセル（5. の冒頭）でも、長さや場合分けの多さのほかは、ほかの文と同じに扱う。

文の骨組み

- 「は」で示した主題と、動詞の動作主がずれている。「待機中のジョブは5秒おきに確認する」では、確認するのはサーバーであってジョブではない。「サーバーは、待機中のジョブを5秒おきに確認する」と書く。
- 前の文と主語が変わったのに、後の文で主語を省いている。主語を省いてよいのは、前の文と主語が同じときと、仕様項目の表のように主体が明らかなときだけである。「プロキシが60秒より早く接続を切ると、プロキシのエラーが表示される。待ち時間は60秒より長くする。」では、何の待ち時間を誰が変えるのかが分からない。
- 修飾語がどこに係るか、指示語（これ、その、上の）が何を指すかが、二通り以上に読める。
- 主語と述語が対応していない。「現在時刻を使う処理は、ブラウザの時刻になる」では、処理が時刻になっている。「〜を防ぐため。」のように、述語のない断片だけの文も同じである。
- 1つの文や段落に、事柄や話題をいくつも詰めている（2.）。

英語の直訳

- 英語の構文をそのまま訳している。
  - 「ジョブは、起動したユーザーとして実行する」は run as の直訳で、ジョブが実行の主体になっている。「ジョブは、起動したユーザーの権限で実行される」と書く。
  - 「ブラウザに Cookie を消させる」のような使役は、make A do の直訳である。「Cookie を削除する」のように、システムがすることとして書く。
  - 「開発環境でだけ使える」は only in の語順をなぞっている。「開発環境だけで使える」と書く。

語

- 和語への言い換えや「の」の連なりなど、2. の基準から外れた語。
- 語の組み合わせが不自然である。「振る舞いが外れる」「組み込みはしていない」など。
- 1つの文の中で同じ語を重ねている。「〜の扱いを扱う」「利用者は〜から利用する」など。
- 同じものを別の語で呼んでいる。または、別のものを同じ語で呼んでいる。
- 説明のために作った呼び名。「タブのユーザー」のような英語の逐語訳の造語は、定義を読むまで意味が取れない。既存の呼び名がないかを探し、なければ名前だけで意味が分かる呼び名にする。

論理のつながり

- 接続詞が前後の関係に合っていない。逆接ではないのに「ただし」で始める、など。
- 理由がなくても読み手が困らない文に、「〜ため」の理由を付けている。読み手が判断に使う理由だけを残す。
- 説明の文に、場合を漏れなく挙げるための断り書き（「この4つですべてである」「（関係しない）」など）が入っている。厳密さが役割の文（5. の冒頭）でなければ削る。

### 5.3 漏れなく探す

5.2 の箇所は、文章を流し読みすると見落とす。次のように探す。

- 1文ずつ、主語と述語を確認する。主語を言えない文、述語と対応しない文、前の文と主語が変わっている文は、5.2 の「文の骨組み」に当たることが多い。
- 1か所で癖を見つけたら、文書全体から同じ癖を検索し、それぞれの文を書き直す。癖は同じ書き手の文書に繰り返し出る。
- 長い文書では、語の出現回数を数える。何十回も出る和語や言い回しは、書き手の癖であることが多い。
- 文書全体を見直すときは、章や節に分けて、すべての文を読む。一度に読む量が多いと、後半の文は流し読みになる。
- 書き手は、自分やサブエージェントが見つけた癖が 5.2 のどの項目にも当たらなければ、5.2 を直す。既存の項目で言い表せるなら、その項目の例を差し替える。新しい項目は、既存の項目で言い表せないときだけ足す。

### 5.4 実装を知らない読み手に読ませる

書いた本人は、実装の知識で文の不足を無意識に補って読んでしまう。そのため、自分で読み返すだけでは不自然さや分かりにくさに気付けない。

まとまった量の文章（ドキュメントの節以上、または複数のファイルにわたるコメント）を書いたときは、Agent ツールでサブエージェントを起動し、実装を知らない読み手として読ませる。
サブエージェントには、書いた文章と想定する読み手だけを渡し、実装の経緯や会話の文脈は渡さない。文書全体を見直すときは、5.3 のとおり章や節ごとにサブエージェントを分ける。依頼の例:

```
あなたは、業務システム開発の経験がある開発者で、このリポジトリのこの部分を初めて読む。
次の文章を読み、以下を挙げてほしい。文章の修正はしなくてよい。

- 一読して意味が取れない箇所、読み返さないと分からない箇所
- 業務システム開発の現場の設計書やコメントでは使わない、不自然な言い回し
- <このファイルの絶対パス> の 5.2 に挙げた箇所。5.3 の探し方で、すべての文を対象に探す。どの項目に当たるかも添え、どれにも当たらなければ「該当なし」とする
- 読み手として当然知りたいのに書かれていないこと（理由、対象外のこと、足りないときの手段など）
- 読み手にとって不要な記述

想定する読み手: <誰が、何のために読むか>
文章:
<推敲する文章。コメントなら対象のソースコードも含める>
```

指摘を受けたら、そのとおりに直すかどうかは自分で判断する。指摘された語を別の語に機械的に置き換えるのではなく、文全体として自然になるように書き直す。

1〜2行のコメントや短いコミットメッセージなら、サブエージェントは使わず、1. から 3. と 5.2 の観点で自分で読み返せばよい。
