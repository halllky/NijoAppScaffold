# 設計・開発

Nijoでの開発は、スキーマ定義ファイル `nijo.xml` を中心としたサイクルで進みます。

<img src="/NijoAppScaffold/img/workflow.drawio.svg" alt="開発ワークフロー図" />

## 1. プロジェクト作成

`nijo new` コマンドで新しいプロジェクトを作成します。

## 2. スキーマ定義

データ構造にかかわる変更や、大きな処理の追加の場合、コードを書き始める前に、アプリケーションが扱うデータ構造と処理を `nijo.xml` に定義し、コード自動生成の内容を固めます。

### nijo.xml に定義するもの

`nijo.xml` には以下のものをセクションに分けて定義します。

* **[データ構造](./020300_DataStructures/index.md)**（`DataStructures` セクション）
  * アプリケーションが扱うデータの形です。
  * 以下の属性の組み合わせによって、そのデータ構造から何が自動生成されるかが決まります。
    * **[IsStored](./020300_DataStructures/020310_IsStored/index.md)**: データベースに **永続化** されます。RDBMSのテーブル定義や、トランザクションの境界に相当します。
    * **[IsQueryable](./020300_DataStructures/020320_IsQueryable/index.md)**: 画面や帳票から **一覧検索** されます。一覧検索はどのアプリケーションでも頻出し、かつパターンが決まっている（フィルタ、ソート、ページング）ため、処理本体まで自動生成されます。
    * どちらも指定しない場合は、Webサーバーとクライアントの間で共有される **[構造体](./020300_DataStructures/020330_Structure/index.md)** になります。
* **[コマンド](./020500_Commands/index.md)**（`Commands` セクション）
  * **アプリケーションの利用者や外部システムが要請を行い、結果を返す1サイクル** の定義です。
  * 入力（引数）を受け取り、処理を行い、出力（戻り値）を返します。
  * データの登録・更新だけでなく、「複雑なデータ構造をもつ画面の初期表示処理」や「データ集計Excel出力」といった操作もコマンドとして定義します。
* **[定数](./020700_Constants/index.md)**（`Constants`, `StaticEnums` セクション、および汎用参照テーブル）
  * ソースコード上にハードコードされる静的な定数と、システムの運用中に値が追加削除される動的な定数があります。
* **値オブジェクト**（`ValueObjects` セクション）
  * 識別子などを専用の型として定義します。

:::note
一覧検索処理（IsQueryable）とコマンドの関係は **CQRS (Command Query Responsibility Segregation)** と用語が似ていますが、Nijoにおける定義はそれと必ずしも一致しません。
更新系処理と参照系処理を分離する考え方には通じるところもありますが、Nijoでのスキーマ定義を進める上では意識しなくて構いません。
:::

### 具体例

典型的な例として、デモ101の「売上一覧画面」と「売上詳細画面（新規登録または更新を行う画面）」を挙げます。

一覧検索画面では IsQueryable 属性が指定された1つのデータ構造の検索処理を、詳細編集画面では初期表示・新規登録・更新の3つのコマンドを利用しています。
それらの内部では、売上・商品・従業員といった IsStored 属性が指定されたデータ構造のモジュールを利用して処理を行っています。

![デモ101の売上関連画面の構成](/img/model-collaboration.drawio.svg)

## 3. コード生成

更新された `nijo.xml` をもとに、ソースコードが自動生成されます（図中の橙色の部分）。

## 4. 実装

生成されたコードを利用しながら、UIや案件固有の業務ロジックを実装します。

## 5. 共有

`nijo.xml` をバージョン管理システムにコミットします。チームメンバーは常に最新のスキーマ定義の図を参照できます。

---

2〜5の工程は一度きりではなく、開発期間を通じて繰り返されます。
