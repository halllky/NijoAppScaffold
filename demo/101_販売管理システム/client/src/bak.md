# メタデータを集約ごとの TS ファイルへ移す改修プラン

## Context

今はモデルのメタ情報が、全集約ぶん 1 ファイル（`__autoGenerated/metadata-for-page.ts`、`MetadataForPage.getAll()`）にまとめて出力されている。C# 側にも同じ内容が `MetadataForPage.cs` として出力されている。

このため画面側は、ルート集約名から `members` の木をたどり、途中の外部参照では参照先を探し直す必要がある（[fieldMetadata.ts](demo/101_販売管理システム/client/src/app/fieldMetadata.ts)）。

これを、各集約の `models/*.ts` が自分のメタデータを `export const metadata` として持つ形に変える。キーは**フォーム上のパス（配列の添字を除く）**にしたフラットな表とする。狙いは、後で作る `useDisplayDataForm` / `useSearchConditionForm` が、`name` から 1 回引くだけで制約を得られるようにすること。C# 側の MetadataForPage は、唯一の利用箇所であるユニットテストをリフレクションに置き換えたうえで削除する。

### 合意済みの方針
- メタデータを出すのは、TS ファイルを持つモデルだけ（QueryModel・GDQM 付き DataModel・StructureModel）
- 表は構造体ごとに分ける。`displayData` と `searchCondition`（filter の配下）を別々に出す
- ノードオプションとカスタム属性は**全部出す**（画面で使うものだけに絞らない）
- 外部参照先の項目は展開して出す。各項目に「ref-to の境界を一度でも越えた先にあるか」のフラグを持たせ、`isKey` やカスタム属性をどう解釈するかはアプリ側が決める
- フック（useDisplayDataForm / useSearchConditionForm）の実装は今回の範囲外

## 生成物のイメージ

`models/入荷詳細.ts` の末尾に、関数群と並べて次を出力する。

```ts
export const metadata = {
  root: {
    kind: 'root', model: 'structure-model', uniqueId: 'bf24…',
    displayName: '入荷詳細', comment: '…', /* 全ノードオプション・カスタム属性 */
    members: ['入荷ID', '入荷日時', '担当者', '備考', 'Version', '入荷商品一覧'],
  },
  displayData: {
    '入荷ID':       { kind: 'value', parent: null, isOutsideTree: false, uniqueId: '3e48…', type: 'word', displayName: '入荷ID', /* … */ },
    '担当者':       { kind: 'ref', parent: null, isOutsideTree: false, uniqueId: '37a8…', refTo: 'ref-to:従業員Ref', refToObject: 'RefTarget', members: ['担当者.従業員番号', '担当者.氏名'], /* … */ },
    '担当者.従業員番号': { kind: 'value', parent: '担当者', isOutsideTree: true, type: 'word', isKey: true, /* 参照先の XML 要素の属性そのまま */ },
    '入荷商品一覧':  { kind: 'children', parent: null, isOutsideTree: false, members: [/* … */], /* … */ },
    '入荷商品一覧.数量': { kind: 'value', parent: '入荷商品一覧', isOutsideTree: false, type: 'int', isQuantity: true, /* … */ },
  },
  // QueryModel の場合のみ。キーは filter. を除いたパス
  // searchCondition: { … },
} as const satisfies Util.AggregateMetadata.Entry
```

- `kind` は `'value' | 'ref' | 'child' | 'children' | 'parent'`。`'parent'` は、子集約を参照したときの RefTarget に現れる Parent メンバー。
- `isOutsideTree` は常に出力する。判定は「`SchemaPathNode.GetPathFromEntry()` の中で、自分より手前に `RefToMember` があるか」。参照先が自分のツリー内の集約である場合も正しく判定できるよう、ルート要素の比較では判定しない。
- 値の型は今の形式を踏襲する（`type` / `enumType` / `valueObjectType`）。
- ノードオプションとカスタム属性は、今と同じくフラットに出す。

## C# の改修（Nijo）

### 1. `Nijo/Parts/Common/MetadataForPage.cs` を作り替える（`AggregateMetadata.cs` に改名）
- C# の出力（`RenderCSharp`、`RenderCSharpType` 系、`RenderNodeOptionsCs`、`RenderNodeOptionTypesCs`、`RenderCSharpMemberClass`）と、`getAll()`・`_entries`・`Add` を削除する。
- `IMultiAggregateSourceFile.Render` では、型定義ファイル `__autoGenerated/aggregate-metadata.ts` だけを生成する。
  - 内容は `export namespace AggregateMetadata { Entry, Root, Table, Member, Value, Ref, Child, Children, Parent }`。
  - オプション部分の型には、既存の `RenderNodeOptionTypes(ctx)` を再利用する（カスタム属性の型も含まれる）。
  - index.ts はディレクトリ内の .ts を自動で export するので（[IndexTs.cs](Nijo/Parts/JavaScript/IndexTs.cs)）、登録は不要。
- 集約ごとの定数を作るメソッドを新設する: `RenderTsConstant(RootAggregate root, IInstancePropertyOwnerMetadata? displayData, IInstancePropertyOwnerMetadata? searchConditionFilter, CodeRenderingContext ctx)`
  - 実際に生成される構造体を `GetMembers()` で再帰的に走査する。DeepEqualFunction（[DeepEqualFunction.cs:323-375](Nijo/Parts/JavaScript/DeepEqualFunction.cs#L323-L375)）と同じ走査方法。
    - `IInstanceValuePropertyMetadata` → `kind: 'value'`
    - `IInstanceStructurePropertyMetadata` のうち、`SchemaPathNode is RefToMember` → `'ref'`、`IsArray` → `'children'`、`RefDisplayDataParentMember` → `'parent'`、それ以外 → `'child'`
    - キーは `GetPropertyName(E_CsTs.TypeScript)` を `.` でつないだもの
  - 各要素の属性は `SchemaPathNode.XElement` に対して既存の `RenderNodeOptions(xElement, ctx)` をそのまま使う。値の型と `refTo`（`RefTo.RefEntryName`）の書き方は、既存の `ValueMetadata` / `RefMetadata` の TS 出力処理から移す。
  - Structure → Structure の循環参照で展開が終わらなくなるのを防ぐため、自分より手前に同じ RefToMember の XElement がある場合は、分かりやすいメッセージの例外を投げる。

### 2. 各モデルの登録箇所を変える
- [QueryModel.cs](Nijo/Models/QueryModel.cs)（static な `GenerateCode(ctx, rootAggregate, aggregateFile)` の中。GDQM の場合もここを通る）
  - `aggregateFile.AddTypeScriptFunction(AggregateMetadata.RenderTsConstant(root, displayData, searchCondition の Filter, ctx))` を呼ぶ。
  - 既存の `if (!rootAggregate.GenerateDefaultQueryModel) ctx.Use<MetadataForPage>().Add(...)` は削除する。
- [StructureModel.cs](Nijo/Models/StructureModel.cs): DisplayData を生成する場合はそれを渡す。生成しない場合は `root` だけを出す。`ctx.Use<MetadataForPage>().Add` は削除する。
- [DataModel.cs:269](Nijo/Models/DataModel.cs#L269)、[CommandModel.cs:132](Nijo/Models/CommandModel.cs#L132): `ctx.Use<MetadataForPage>().Add` を削除する。
- [GeneratedProject.cs:288](Nijo/GeneratedProject.cs#L288): `ctx.Use<AggregateMetadata>()` に置き換える。

## ユニットテストの改修（デモ200）

[無条件検索でエラーが発生しないか.cs](demo/200_複雑なパターン/UnitTest/Tests/無条件検索でエラーが発生しないか.cs)
- `無条件検索テストケース()`: `MetadataForPage.GetAll()` による絞り込みをやめる。代わりに、`AutoGeneratedApplicationService` の public なインスタンスメソッドのうち、`LoadAsync` という名前で引数が 2 つ、2 つ目が `IPresentationContext<>` のものを列挙する。
  - 物理名は `searchConditionType.Name` から末尾の `SearchCondition` を除いたもの（Inconclusive の判定に使う名前と一致する）。
  - 取得した `MethodInfo` をそのまま Invoke する。
- 呼び出し部分は、外部参照検索のテストケースと共通の関数にまとめる。
- 176 行目の、使われていない `var metadata = MetadataForPage.GetAll();` を削除する。

## TS の改修（デモ101）

- [app/fieldMetadata.ts](demo/101_販売管理システム/client/src/app/fieldMetadata.ts) を新しい API で書き直す。
  - `getFieldMetadata(table: AggregateMetadata.Table, fieldPath: string)`: 先頭の `filter.` と、数字だけのパス部分を除いて引く。検索条件の場合は、末尾の `.from` / `.to` も除く。
  - `numericPropsOf` と `maxLengthOf` も、ルート集約名ではなく表を受け取るように変える。
- 呼び出し元を書き換える。例: `numericPropsOf("売上一覧", "売上SEQ")` → `numericPropsOf(売上一覧.metadata.searchCondition, "売上SEQ")`
  - 対象: [P100_売上.tsx](demo/101_販売管理システム/client/src/pages/P100_売上.tsx)、P200_入荷、P201_入荷詳細（displayData）、P300_商品、P001_ログイン（ログインParameter の displayData）、shared/StockAdjustmentDialog（在庫調整Parameter）
- [aaaaa.tsx](demo/101_販売管理システム/client/src/aaaaa.tsx): `MetadataForPage` の import を `AggregateMetadata` の型に置き換え、コンパイルが通る状態にする（スケッチなので中身は最小限の変更にとどめる）。

## 確認方法

1. 改修前に、nijo-codegen-diff スキルの `snapshot.sh before` で現在の生成物を退避する。
2. 改修後に `snapshot.sh after` を実行し、`git diff --no-index --stat before after` で次を確認する。
   - `metadata-for-page.ts` と `MetadataForPage.cs` が消え、`aggregate-metadata.ts` が増えている
   - 変わった `models/*.ts` が QueryModel・GDQM・StructureModel のものだけで、どれも末尾に `metadata` が足されただけである
   - デモ101 の `入荷詳細.ts` で、`担当者.*` が `isOutsideTree: true`、`入荷商品一覧.*` が `false` になっている。参照先の `isKey` が出力されている
3. 全デモ（000・101・200）とテンプレートの client で `tsc --noEmit` を実行し、`as const satisfies` の型チェックと fieldMetadata の書き換えにエラーがないことを確認する。
4. `dotnet build` を通したうえで、デモ200 の UnitTest で次の 2 つを確認する。
   - `dotnet test --filter "Name~無条件"` を実行し、改修前と同じテストケース名（`無条件検索_*`、`無条件Ref検索_*`）が同じ件数だけ生成され、結果が同じであること
   - 改修前の件数・名前は `dotnet test --list-tests` の出力で比べる
5. デモ101 を起動し、P100・P201・P300・P001 で、数値欄の桁数・単位や文字列の最大長が改修前と同じであることを目視で確認する。
