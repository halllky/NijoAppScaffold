# 14. 権限

ログインユーザーがどの機能を使えるかを扱う。ログインユーザーが誰かを確かめる仕組みは13章にある。

権限は、画面ごとではなく、処理ごとに決める。処理とは、画面がサーバーに頼む1つ1つの検索や更新のことで、例えば「売上の一覧を検索する」「売上を登録する」がそれぞれ1つの処理である。画面は処理を呼んで動くので、ある画面を使えるかどうかは、その画面が呼ぶ処理を呼び出せるかどうかで決まる。

処理ごとに、呼び出せる利用者を宣言する。宣言は「ログインしていなくても呼び出せる」「ログインしていれば誰でも呼び出せる」「決まった権限区分を持つユーザーだけが呼び出せる」「画面からは呼び出せない」の4つのいずれかである。権限区分は、ユーザーに付ける権限の種類である。テンプレートの権限区分は「システム管理者」だけで、案件の業務に合わせて増やす。

サーバーは、処理を実行する前に、宣言とログインユーザーの権限区分を照らし合わせ、呼び出せなければ実行しない。画面も同じ宣言を使って、ログインユーザーが呼び出せない処理のメニューやボタンを表示しない。ただし、画面の表示は使い勝手のためのもので、不正な呼び出しを防ぐのはサーバーの判定である。

「どのデータを扱えるか」で分ける権限（データ単位の権限）には、共通の仕組みがない。

### AUZ-007 機能公開レベル

| 機能公開レベル | 呼び出せる利用者 |
|---|---|
| ログイン不要 | ログインしていない利用者を含め、誰でも呼び出せる。テンプレートでは AUTH-009 の3つの処理だけである |
| ログインユーザー全員 | ログインしていれば、誰でも呼び出せる |
| 権限で指定 | 宣言した権限区分のいずれかを持つユーザーだけが呼び出せる。システム管理者は常に呼び出せる（AUZ-003） |
| 内部処理のみ | 画面からは誰も呼び出せない。API として公開せず、ジョブなどサーバーの中からだけ呼ぶ |

## 14.2 限界

- データ単位の権限（部署や拠点などで、見られるデータを絞る）の共通の仕組みはない。追加方法は 14.3。通知（NTF-005）、ジョブ（JOB-009）、一時保存のファイル（FIL-007）のように自分のものだけに絞る機能は、それぞれの処理で個別に絞っている。
- 権限区分は、ユーザーに直接付ける。いくつかの権限区分をまとめたロールや、ユーザーのグループに権限区分を付ける仕組みはない。
- 宣言（AUZ-007）の対象は、クエリとコマンドだけである。添付ファイルとジョブのファイルの API は、ログインしていれば呼び出せ、それぞれの仕様（FIL-007、JOB-009）で判定する。手書きで足した API も、宣言の対象にならない。
- 参照する側の画面の利用者は、参照先の検索も呼び出せる（AUZ-009）。例えば、売上の画面で商品を選ぶ販売担当は、商品の一覧の検索も呼び出せる。参照先の検索の項目を見せたくない利用者がいる場合は、参照するための項目だけを持つクエリモデルを別に作り、そちらを参照する。テンプレートの「従業員Ref」と「従業員マスタ」がその分け方である。
- 画面の表示の切り替え（AUZ-004）のうち、ボタンなどは、画面ごとに処理を指定したものに限る。指定し忘れた部品は表示されたままになり、押すとサーバーで弾かれる（AUZ-001）。

## 14.3 主なカスタマイズ方法

### 処理を追加する

- nijo.xml で、クエリモデルまたはコマンドのルート要素に、カスタム属性「機能公開レベル」を指定する。値は AUZ-007 の表のいずれかである。「権限で指定」のときは、カスタム属性「機能利用可能権限」に権限区分を指定する。
- 処理の中に権限の確認は書かない。どこから呼ばれても、処理の本体の前に判定される（AUZ-001）。
- 画面のボタンなど、処理を呼ぶ部品は、その処理を呼び出せるかどうかで表示を切り替える（14.4）。
- ほかのデータを参照する処理を足したときは、参照先の宣言に、その処理の利用者の権限区分を足す（AUZ-009）。足し忘れると、画面でデータを選ぼうとしたときにサーバーで弾かれる。

### 権限区分を追加する

- nijo.xml の静的区分「権限区分」に値を追加して再生成する。
- その権限区分で使えるようにする処理の「機能利用可能権限」に、追加した値を足す。ナビゲーションのリンクは、宣言に合わせて切り替わる（AUZ-004）。

### データ単位の権限を加える

- Entity Framework Core のグローバルクエリフィルターを使う。手書きの DbContext のモデルを定義する箇所で、データモデルごとに、ログインユーザーが見てよい行だけに絞る条件を付ける。
- 条件は、一覧の検索、参照検索、編集のための読み込みのすべてに効く。手書きの SQL と、MapToView のビュー（10.3）には効かないので、ビューを使うデータ構造では、ビューの側でも絞る。
- ジョブなど、すべての行を扱ってよい処理では、条件を外して検索する。
- 書き込みは絞られない。自分の部署以外の値を指定した新規登録などは、入力チェックで防ぐ。

## 14.4 開発者向け情報

- 権限に関わる処理は、次の場所から読み始める。
  - サーバー：`Core/ログイン・認証/処理の呼び出し可否.cs`（判定の規則と、すべての処理が本体の前に通る関門）、`WebApi/OperationEndpoints.cs`（宣言に従ったエンドポイントの登録と、403 の応答）
  - 画面：`client/src/login/canInvoke.ts`（サーバーと同じ規則の判定）、各画面の `navigationItem`（ナビゲーションのリンクと、その画面を開くときに呼ぶ処理）
  - 単体テスト：`UnitTest/Tests/処理の呼び出し可否.cs`（宣言の食い違いと、判定の規則）
- 処理の宣言は、nijo が生成する処理の一覧（サーバーの `Operation<OperationContext>.All` の各処理の `Metadata`、画面の `Operation.Metadata`）に入る。
- ログインユーザーのいない呼び出し（定期実行のジョブなど）では、「ログイン不要」と「内部処理のみ」の処理しか呼べない。それ以外の処理は、関門を通さずに処理の本体を直接呼ぶ（18.3）。画面から起動したジョブは、起動したユーザーの権限区分で判定される（SES-009）。
