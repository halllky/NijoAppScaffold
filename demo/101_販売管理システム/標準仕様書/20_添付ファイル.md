# 20. 添付ファイル（未実装）

画面からファイルを送り、保存し、ダウンロードする。
最終的にファイルが格納されることになる場所は案件により千差万別であるが、WebクライアントからWebサーバーにアップロードするところまででも大仕事なので、その部分だけテンプレートで用意している。最終的な格納先は切り替えやすいように作っている。

添付ファイルを使わない案件は本番稼働前にこの機能を削除すること。削除方法はこの章に書く（未実装）。

## 20.2 限界

- 使われなくなった確定済みのファイルは削除しないので（FIL-006）、保存先の容量は増え続ける。消し方は 20.3。
- 既定の保存先はサーバーごとのフォルダなので、サーバーが複数台のときは共有の保存先に変える必要がある（20.3）。

## 20.3 主なカスタマイズ方法

### 保存先を変える

- ファイルの保存先は、保存・読み出し・削除だけをもつインターフェースの実装で決まる。既定はサーバー上のフォルダ（FIL-004）。
- クラウドのストレージなどに変える場合は、そのインターフェースの実装を作り、登録し直す。外部システム連携（13.3）と同じ形である。
- 実装を差し替えても、一時保存と確定（FIL-002、FIL-005）の振る舞いは変わらない。

### 使われなくなったファイルを消す

- どのファイルが使われていないかは、nijo.xml でファイル型の項目をもつデータ構造を手がかりに、DB から参照されているファイルの識別子を集めて判断する。論理削除で退避したデータ、変更前後の値の記録（12.3）、手書きのテーブルからの参照も含めるかを案件で決める。
- 消す処理はクリーンナップに追加するか、定期的なジョブ（19章）にする。

## 20.4 開発者向け情報

- ファイルを扱う項目には、nijo の項目の型「ファイル型」を使う（未実装）。データモデルの項目にも、コマンドの引数にも使える。ファイル型の項目は、次のように生成される。
  - クライアントの型：保存済みのファイルの情報（識別子・名前・サイズ）か、新しく選んで一時保存したファイルの情報のどちらか
  - C# の型：識別子・名前・サイズ・種類と、中身を読み出す手段
  - DB の列：識別子・名前・サイズ・種類。中身はもたない（FIL-004）
  - 入力部品とダウンロードのリンク、ダミーデータ
- 画面でファイルを選ぶと、処理を呼ぶ前に一時保存の API にファイルを送り、一時保存の識別子を受け取る。処理の引数にはその識別子を入れる。それまでの、処理の引数とファイルを1回のリクエストでまとめて送る仕組みは、この方式に置き換える。
- 一時保存の API は、ログインしているかを確認し、サイズの上限を超えるファイルを拒否する。ASP.NET Core のリクエストの本体の上限も、この上限に合わせる（FIL-003）。
- 一時保存では、ファイルの中身を保存先に書き、一時保存のテーブルに識別子と期限を記録する。処理が DB に保存するとき、同じトランザクションで一時保存のテーブルの行を消して確定する。データモデルの保存では nijo が生成する保存の処理が、コマンドの引数では手書きの処理がこれを行う。DB の保存とファイルの確定が1つのトランザクションに収まるので、外部システムの更新（EXT-001）としては扱わない。
- クリーンナップは、期限を過ぎた一時保存の行を探し、保存先のファイルと行を消す（FIL-005）。確定したファイルは扱わない（FIL-006）。
- 既定の保存先の実装は、設定で決めたフォルダに識別子の名前で保存する。
- ダウンロードの API は、ログインしているかと、手書きで追加した確認（FIL-007）を行ってからファイルを返す。応答には `Content-Disposition: attachment` を付けてブラウザで開かせない（FIL-008）。中身の種類を推測させない指示は SEC-006 で全応答に付く。
