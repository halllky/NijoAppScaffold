# 調査中に見つけた不具合

標準仕様書の整理の途中で見つけた、実装の不具合と、仕様書と実装の食い違いの控え。対応は後で検討する。対応が決まったら、この一覧から消す。整理が終わったらこのファイルは削除する。

## 実装の不具合

- ログインしたことがあり、セッションの行が残っているユーザーを削除すると、外部キー違反で保存に失敗する。セッションからユーザーへの参照の削除時の動作が NoAction のため。保存の処理は DB のエラーとして Error のログを出すので、運用担当者への通知の対象にもなる。通知の宛先やジョブの起動したユーザーは、ユーザーを削除できるように参照にしていないので、セッションだけ設計が食い違っている。（13章の USR-005 に事実として記載済み）
- 2人のシステム管理者が同時に互いのシステム管理者の権限を外すと、更新する行が別なので楽観排他に掛からず、両方とも成功する。システム管理者が1人もいなくなる。（13章の限界に記載済み）
- ログイン処理に、パスワードが未設定のときのメッセージを出す分岐（PasswordNotSetError）が残っている。パスワードの列は NOT NULL なので、この分岐は通らない。
- パスワードを初期パスワードに戻したときのログの文言が「パスワードを再発行しました」のまま。仕様書では「パスワードの初期化」に呼び替えた。処理名「パスワード再発行」も同じ。
- 開発支援機能の API のうち、DB の削除と再作成（DebugDatabaseController）と、実行時の設定の内容を返す API（ExampleController）は、`#if DEBUG` だけで守っていて、環境を確かめていない。Debug ビルドを開発環境以外で動かすと、ログインなしで呼べる。ExampleController は22章の開発支援機能の一覧にもない。
- AUTH-009 の確認方法は「テスト」だが、自動テストで確かめているのは処理の宣言だけで、死活の確認の API はテストしていない。
- 画面を開いたときのログインユーザーと、Cookie のセッションのユーザーが食い違っていても、サーバーは気付かない。同じブラウザの別のタブで別のユーザーがログインした後、ほかのタブが読み込み直さなかった場合（localStorage を使えない、または読み込み直す前の確認で利用者がやめた）、そのタブで前のユーザーの画面のまま操作すると、新しいユーザーとして保存される。呼び出しに画面のユーザー ID を付けてサーバーで照合すれば防げる。（13章の限界に事実として記載済み）
- ログイン状態が切れた後に、リンクで開くファイルのダウンロード（添付ファイル、ジョブの出力ファイル）をすると、ログインのダイアログが出ず、401 の応答をダウンロードしようとして失敗する。（13章の SES-005 の備考に事実として記載済み）

- パスワードの照合が、形式の版を持たない古い形式の値として、ストレッチングをしない HMAC-SHA256 1回の値も受け付ける。テンプレートから作る案件の DB にこの形式の値はないはずなので、不要な弱い経路である。（13章の PWD-001 に事実として記載済み）
- ログインの処理は存在しないユーザー ID のときにパスワードの照合をしないので、応答時間（数ミリ秒と数百ミリ秒）からユーザー ID の有無が分かる。AUTH-003 と AUTH-010 で有無を隠している意図と食い違う。（13章の AUTH-003 と限界に事実として記載済み）
- ユーザー ID の正規化が、画面（NFKC と前後の空白の削除）と、ログインの失敗の数え方（前後の空白の削除と大文字化だけ）とで違い、サーバーの照合は正規化しない。SQLite では全角の ID は一致しないので実害はないが、全角と半角を区別しない照合順序の DB に替えると、API を直接呼んで全角と半角を混ぜた ID で、同じユーザーへの失敗を別々に数えさせ、回数の制限を回避できる。（13章の AUTH-001、AUTH-010 に事実として記載済み）
- パスワードの変更で現在のパスワードを誤っても、回数を数えず、ログにも出さない。ログイン中の端末を他人に使われると、現在のパスワードを総当たりで試せる。（13章の PWD-002 に事実として記載済み）
- データを保存したときのログ（「データを保存しました」）では、キーの値がマスキングされない。セッションのセッションキー（DB に保存したハッシュ値）は、カスタム属性「マスキング」を付けているのに、そのまま出る。ハッシュ値からはなりすませないが、LOG-004 と食い違う。（13章の SES-001 の備考に事実として記載済み）
- ログインのログに、入力されたユーザー ID をそのまま出す。パスワードを誤ってユーザー ID の欄に入力すると、そのパスワードが平文でログに残る。（13章の表「認証のログ」の前文に事実として記載済み）
- 権限のない処理を呼んだときの 403 の応答を、画面がメッセージとして読み取らず、応答の本文（`{"messages":{"error":["「…」を実行する権限がありません。"]}}`）をそのままエラーとして表示する。画面の呼び出しの共通処理は、422 だけを処理の結果のメッセージとして読み、403 は予期しない応答として扱うため。権限区分を外されたユーザーが画面を読み込み直す前に操作したときや、権限のない画面の URL を開いたとき（エラー画面に表示される）に起きる。（14章の AUZ-010 の備考に事実として記載済み）
- 単体テスト `UnitTest/Tests/処理の呼び出し可否.cs` のクラスのコメントに、仕様 ID（AUZ-007）が書かれている。付録の「仕様 ID はソースコードに書かない」に反する。
- コンソールに出力するログの形式が NLog の既定のままで、ログインユーザー ID・処理名・処理1回分の識別子が出ず、日時にタイムゾーンのオフセットも付かない。コンテナなどでコンソールの出力だけを集めると、問い合わせ番号（API-005）からログを探せない。LOG-001 の備考の「コンソールの出力を集める動かし方でも後から調べられる」という意図に届いていない。（15章の LOG-002 と限界に事実として記載済み）
- `appsettings.json` に `Logging` の区画（ASP.NET Core の標準のレベルの設定）があるが、NLog が Microsoft.Extensions.Logging のレベルの絞り込みを外すので効かない。運用担当者が書き換えても何も変わらない。（15章の LOG-001 の備考に事実として記載済み）
- ログファイルの削除（LOG-006）は、ログのフォルダにある拡張子 `.log` のファイルをすべて数えて消す。NLog 自身のエラーを書く `NLog.Fatal.log` も同じフォルダにあるので、ログファイルの1つとして数えられ、古くなると消される。

## 仕様書と実装の食い違い（各章の書き直しで扱う）

- 22章：「DB ビューアは、さらに開発環境でなければ拒否する」とあるが、拒否するのは設定の保存（PUT settings）だけで、テーブルのデータの取得は拒否しない。
- 4章 CFG-003：備考に「環境変数で値を定義する」方法を挙げているが、アプリケーション用の区画（MyApp）の設定は、設定ファイル（`appsettings.json` と `appsettings.Development.json`）だけから読み、環境変数では上書きできない。また、`appsettings.Development.json` は、開発環境でなくても、あれば読む。

## 各章の書き直しの後にまとめてやること

- nijo.xml の Templates.MSG のメッセージの識別子を、仕様 ID に合わせて付け替える（付録「仕様 ID はソースコードに書かない」の例外）。文言は標準仕様書を正とし、付け替えた識別子を使うように C# と TypeScript のコードも直す。
- 権限がないときの文言「「{処理名}」を実行する権限がありません。」（AUZ-010）は Templates.MSG になく、`Core/ログイン・認証/処理の呼び出し可否.cs` に直接書かれている。上の付け替えのときに MSG に移す。
