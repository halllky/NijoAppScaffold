# 調査中に見つけた不具合

標準仕様書の整理の途中で見つけた、実装の不具合と、仕様書と実装の食い違いの控え。整理が終わったらこのファイルは削除する。

## 実装の不具合の修正を引き継ぐ人へ

- 実装の不具合は、仕様書の整理とは別のセッションで直す。この節の下の2つの節が対象である。
- 「（○章の…に記載済み）」とあるものは、仕様書に現在の振る舞いを事実として書いてある。直したら、その箇所も直した後の振る舞いに合わせる。
- 「不具合かどうか判断に迷うもの」は、直す前に、直すべきかどうかを持ち主に確かめる。迷う理由を各項目に書いてある。
- 直したら、この一覧から消す。

## 実装の不具合

### 認証・権限

- ログインしたことがあり、セッションの行が残っているユーザーを削除すると、外部キー違反で保存に失敗する。セッションからユーザーへの参照の削除時の動作が NoAction のため。保存の処理は DB のエラーとして Error のログを出すので、運用担当者への通知の対象にもなる。通知の宛先やジョブの起動したユーザーは、ユーザーを削除できるように参照にしていないので、セッションだけ設計が食い違っている。（10章の USR-005 に記載済み）
- パスワードの照合が、形式の版を持たない古い形式の値として、ストレッチングをしない HMAC-SHA256 1回の値も受け付ける。派生アプリケーションの DB にこの形式の値はないはずなので、不要な弱い経路である。単体テスト `パスワードの照合.cs` の古い形式のテストも合わせて消す。（10章の PWD-001 に記載済み）
- ログインの処理は存在しないユーザー ID のときにパスワードの照合をしないので、応答時間（数ミリ秒と数百ミリ秒）からユーザー ID の有無が分かる。AUTH-003 と AUTH-010 で有無を隠している意図と食い違う。（10章の AUTH-003 と限界に記載済み）
- ユーザー ID の正規化が、画面（NFKC と前後の空白の削除）と、ログインの失敗の数え方（前後の空白の削除と大文字化だけ）とで違い、サーバーの照合は正規化しない。SQLite では全角の ID は一致しないので実害はないが、全角と半角を区別しない照合順序の DB に替えると、API を直接呼んで全角と半角を混ぜた ID で、同じユーザーへの失敗を別々に数えさせ、回数の制限を回避できる。（10章の AUTH-001、AUTH-010 に記載済み）
- パスワードの変更で現在のパスワードを誤っても、回数を数えず、ログにも出さない。ログイン中の端末を他人に使われると、現在のパスワードを総当たりで試せる。（10章の PWD-002 に記載済み）
- 権限のない処理を呼んだときの 403 の応答を、画面がメッセージとして読み取らず、応答の本文（`{"messages":{"error":["「…」を実行する権限がありません。"]}}`）をそのままエラーとして表示する。画面の呼び出しの共通処理は、422 だけを処理の結果のメッセージとして読み、403 は予期しない応答として扱うため。（11章の AUZ-010 に記載済み）
- ログイン処理に、パスワードが未設定のときのメッセージを出す分岐（PasswordNotSetError）が残っている。パスワードの列は NOT NULL なので、この分岐は通らない。分岐とメッセージの定義を消す。
- パスワードを初期パスワードに戻したときのログの文言が「パスワードを再発行しました」のまま。仕様書では「パスワードの初期化」に呼び替えた。処理名「パスワード再発行」も同じ。

### 開発支援機能

- 開発支援機能の API のうち、DB の削除と再作成（DebugDatabaseController）と、実行時の設定の内容を返す API（ExampleController）は、`#if DEBUG` だけで守っていて、環境を確かめていない。Debug ビルドを開発環境以外で動かすと、ログインなしで呼べる。（21章の DEV-001 に記載済み）

### ログ

- データを保存したときのログ（「データを保存しました」）では、キーの値がマスキングされない。セッションのセッションキー（DB に保存したハッシュ値）は、カスタム属性「マスキング」を付けているのに、そのまま出る。ハッシュ値からはなりすませないが、マスキングを付けた意図に反する。（10章の SES-001 と、18章の LOG-004 に記載済み）
- コンソールに出力するログの形式が NLog の既定のままで、ログインユーザー ID・処理名・処理1回分の識別子が出ず、日時にタイムゾーンのオフセットも付かない。コンテナなどでコンソールの出力だけを集めると、問い合わせ番号（API-005）からログを探せない。（18章の LOG-002 と限界に記載済み）
- `appsettings.json` に `Logging` セクション（ASP.NET Core の標準のレベルの設定）があるが、NLog が Microsoft.Extensions.Logging のレベルの絞り込みを外すので効かない。運用担当者が書き換えても何も変わらない。設定ファイルから消すか、効くようにする。（18章の LOG-001 に記載済み）
- ログファイルの削除（LOG-006）は、ログのフォルダにある拡張子 `.log` のファイルをすべて数えて消す。NLog 自身のエラーを書く `NLog.Fatal.log` も同じフォルダにあるので、ログファイルの1つとして数えられ、古くなると消される。（18章の LOG-006 に記載済み）
- NLog 自身のエラーを書く設定（`NLog.Fatal.log`）のレベルが Fatal なので、ログファイルに書き込めなかったこと（NLog では Error）は記録されない。`Core/Logging.cs` のコメント「ファイル出力自体の失敗などは、別途Fatalログとして出力する」と食い違う。（18章の LOG-010 に記載済み）

### 画面の配信・セキュリティ

- 本番環境で、画面の HTML にキャッシュさせない指示（Cache-Control など）が付くのは、`/index.html` を直接開いたときだけである。`/` や画面の URL（`/sales/list` など）を開いたときは、HTML を返す代替の処理（MapFallbackToFile）が静的なファイルの配信の設定（OnPrepareResponse）を使わないので、指示が付かない。（4章の UI-008 に記載済み）
- WebApi の起動処理に、HTTPS の URL へのリダイレクト（`UseHttpsRedirection`）がコメントで置かれているが、位置が静的なファイルの配信より後なので、そのまま有効にすると静的なファイルはリダイレクトされない。

### ソースのルール違反

- 単体テスト `UnitTest/Tests/処理の呼び出し可否.cs` のクラスのコメントに、仕様 ID（AUZ-007）が書かれている。付録の「仕様 ID はソースコードに書かない」に反する。

## 不具合かどうか判断に迷うもの

- 2人のシステム管理者が同時に互いのシステム管理者の権限を外すと、更新する行が別なので楽観排他に掛からず、両方とも成功する。システム管理者が1人もいなくなる。（10章の限界に記載済み）
  - 迷う理由：同時に操作したときだけ起きる競合で、防ぐには「システム管理者が1人以上残る」ことを DB の制約か排他で保証する仕組みが要る。テンプレートとしてそこまで備えるかは判断が要る。
- 画面を開いたときのログインユーザーと、Cookie のセッションのユーザーが食い違っていても、サーバーは気付かない。同じブラウザの別のタブで別のユーザーがログインした後、ほかのタブが読み込み直さなかった場合（localStorage を使えない、または読み込み直す前の確認で利用者がやめた）、そのタブで前のユーザーの画面のまま操作すると、新しいユーザーとして保存される。呼び出しに画面のユーザー ID を付けてサーバーで照合すれば防げる。（10章の AUTH-006 と限界に記載済み）
  - 迷う理由：Cookie を共有する方式の Web アプリケーションでは一般的な振る舞いで、照合を加えると呼び出しの取り決め（10章の 401 の扱いなど）にも手が入る。仕様上の限界として扱う選択もある。
- ログイン状態が切れた後に、リンクで開くファイルのダウンロード（添付ファイル、ジョブの出力ファイル）をすると、ログインのダイアログが出ず、401 の応答をダウンロードしようとして失敗する。（10章の SES-005 に記載済み）
  - 迷う理由：リンクでのダウンロードはブラウザが直接行うので、画面の共通の処理で 401 を受け取れない。直すにはダウンロードの方式を変える必要があり、使い勝手の問題として許容する選択もある。
- ログインのログに、入力されたユーザー ID をそのまま出す。パスワードを誤ってユーザー ID の欄に入力すると、そのパスワードが平文でログに残る。（10章の AUTH-011 に記載済み）
  - 迷う理由：入力されたユーザー ID をログに出すのは、不正なログインの試行を調べるために一般的に行われている。出さないと調査の手がかりが減る。
- 存在しないユーザー ID の応答時間の差（上の「実装の不具合」の項目）を直すと、ログインのたびに数百ミリ秒の計算が必ず走る。一時ロック（AUTH-010）と組み合わせて、負荷の面で問題ないかは確かめが要る。

## 各章の書き直しの後にまとめてやること

- nijo.xml の Templates.MSG のメッセージの識別子を、仕様 ID に合わせて付け替える（付録「仕様 ID はソースコードに書かない」の例外）。文言は標準仕様書を正とし、付け替えた識別子を使うように C# と TypeScript のコードも直す。
- 処理済みの操作を送り直したときの文言「この操作は、すでに処理されています。…」（UPD-008）も Templates.MSG になく、WebApi の処理の呼び出しの共通処理に直接書かれている。上の付け替えのときに MSG に移す。
- 権限がないときの文言「「{処理名}」を実行する権限がありません。」（AUZ-010）は Templates.MSG になく、`Core/ログイン・認証/処理の呼び出し可否.cs` に直接書かれている。上の付け替えのときに MSG に移す。
- 確認方法が「テスト」でも、自動テストが仕様の一部しか確かめていない仕様の扱いを決めて、直す。いま分かっているもの：
  - AUTH-009：自動テストで確かめているのは処理の宣言だけで、死活の確認の API はテストしていない。
  - PWD-001：確認方法は「テスト」に直したが、ほかの章でも同じ食い違いがないか見直す。
