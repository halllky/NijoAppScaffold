# 15. 権限

利用者がどの機能を使えるかを扱う。

## 15.1 外部仕様

| AUZ-001 | 利用者がその機能を使ってよいかは、サーバー側の処理の先頭で確認する | 検査 | セキュリティ | 画面の表示制御は迂回できるため |

## 15.2 限界

- 部署・拠点などによるデータ単位の権限はない。追加方法は 15.3。
- 汎用画面は、すべてのクエリモデルとコマンドについて、ログインしていれば誰でも開ける状態で登録される（AUZ-006）。画面を開けることと、処理を実行できることは別で、処理は AUZ-001 の確認の対象になる。ただし、処理の先頭で権限を確認していない処理は、汎用画面から誰でも実行できる。不要な汎用画面を取り外すことと、すべての処理で権限を確認することは、案件で行う。この限界は、処理に必要な権限の宣言（AUZ-007。未実装）で解消する。

## 15.3 主なカスタマイズ方法

### 権限を追加する

- nijo.xml の「権限区分」に値を追加して再生成する。
- その権限が必要な処理の先頭で、ログインユーザーがその権限を持っているかを確認する（AUZ-001）。
- 画面のメニュー・ボタンの表示を、同じ権限で切り替える（AUZ-004）。

### データ単位の権限を加える

- Entity Framework Core のクエリフィルターを使って追加する。
- DB へのアクセスを担う手書きのクラスで、モデルを定義する箇所に、データモデルごとに、ログインユーザーが見てよい行だけに絞る条件を付ける。
- 条件は、一覧の検索、参照先の検索、編集のための読み込みのすべてに適用される。論理削除（UPD-003）とは衝突しない。
- 手書きの SQL と、MapToView のビュー（11.3）には適用されない。ビューを使うデータ構造では、ビューの側でも絞る。
- ジョブやバッチなど、すべての行を扱ってよい処理では、条件を外して検索する。
- 書き込みは絞られない。自分の部署以外の値を指定した新規登録などは、入力チェックで別に防ぐ（AUZ-001）。

## 15.4 開発者向け情報

- 権限は、ログインユーザーの情報の一部として「権限区分」の値のリストで持ち、ログイン状態確認の戻り値で画面にも渡す。
- 処理に必要な権限の宣言（AUZ-007。未実装）は、nijo.xml の属性を生成されたコードに .NET の属性として出す仕組み（NijoAttr）で、処理ごとの属性として出す。エンドポイントを登録する共通の処理が、リフレクションでこれを読み、宣言のない処理は登録しない。実現には、次の nijo の改修が要る。
  - コマンドとクエリのルートに付けたカスタム属性を、処理1件ごとの場所に属性として出す。今はデータの構造を表すクラスにだけ出るので、コマンドに付けた属性はどこにも出ない。
  - 複数の権限のどれかがあれば呼び出せる、という宣言をできるようにする。今のカスタム属性の列挙は、値を1つしか持てない。
  - 選択肢を、静的区分「権限区分」の値から作れるようにする。
