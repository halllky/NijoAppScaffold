# 付録 この文書の記載ルール

この文書を保守する人のためのルールである。

- この仕様書はテンプレートや開発者や実際の利用者の間の責任分界点になる。メンテナンス漏れを誘発するような書き方をしてはいけない。
  - 1つの事柄は1つの仕様項目にだけ書くこと。複数箇所に書いてはならない。2つの章に関わる仕様は、その振る舞いを決めている処理がある章に置く。他の箇所に書いてある内容を参照するときは、仕様IDで参照したり、参照先の情報の変わらない性質を参照する（例えば「/api/login のコントローラーでも同様の考慮をしており…」よりも「ログイン時にも同様の考慮をしており…」の方がより不変であり頑丈な記述である。その考慮をコントローラーでやるのかアクションフィルターでやるのかは変わりやすいが、その考慮をログイン時に行うのはきっと変わらないだろうから）。
  - ソースコード中に登場する物理名は、IDE によるリファクタリングが効かず修正漏れの元になるので、書かなくても伝わるなら書かない。ただし、物理名を避けるために不自然な言葉に言い換えてはいけない。言い換えるとかえって分かりにくくなる名前や、変わることがまずない名前（EFCore の "DbContext" のようにこのリポジトリが決めたのではない名前、ApplicationService のような中核の名前、nijo.xml に定義した名前など）は、そのまま書いてよい。
- この仕様書はまだ内容検討途中である。
  - 仕様 ID はソースコード（コメントやテストの名前を含む）に書かない。仕様書が固まってきたら主にテストコード中に書いていく想定
  - まだ実装していない仕様は、確認方法に「（未実装）」を付ける（例：テスト（未実装））。章の全体が未実装のときは、章の見出しにも付ける。実装済みの仕様の一部だけが未実装のときは、備考に「未実装：」に続けてその部分を書く。表ではない文章では、その文の末尾に「（未実装）」を付ける。「未実装」で検索すれば、対象の箇所がすべて分かる。
- ファイルは章ごとに分け、名前を「章番号（2桁）_章の名前.md」にする。章の名前の「（未実装）」はファイル名に含めない。章を足したり組み替えたりしたら、README.md の目次も直す。
- 図は `図` フォルダに置く。
