# 付録 この文書の記載ルール

この文書を保守する人のためのルールである。各章の書き方は1章に、文の書き方は japanese-writing スキルに従う。

## 執筆

- ファイルは章ごとに分け、名前を「章番号（2桁）_章の名前.md」にする。章を足したり組み替えたりしたら、README.md の目次も直す。
- 文や表より図のほうが分かりやすいものは、図にする。図は `.drawio.svg` で書いて `images` フォルダに置き、配色は既存の図に合わせる。Markdown のプレビューでは代替テキストが見えないので、何の図かは図の前の本文に書く。
- 仕様 ID は、ソースコード（コメントやテストの名前を含む）に書かない。この文書が捨てられ、ソースコードだけが使われることがあるためである。ただし、nijo.xml の Templates.MSG のメッセージの識別子は、文言と仕様を対応づけるために仕様 ID に合わせる。
- まだ実装していない仕様は、確認方法に「（未実装）」を付ける（例：テスト（未実装））。章の全体が未実装なら、章の見出しにも付ける。仕様の一部だけが未実装なら、備考に「未実装：」に続けてその部分を書く。表の外の文では、文末に付ける。

## 引き算で書く

記述が増えるほど、整合を保つのが難しくなる。修正は、既存の記述の削除、既存の記述の修正や統合、加筆の順に検討する。複数行の情報を1文に詰め込んでも、記述を減らしたことにはならない。

仕様項目の場合分けや例外と、仕様項目から導いた表は、役割があって書いているので（1章の「各章の構成」）、記述量を理由に削らない。

## 依存を減らす

ほかの記述と整合していなければならない記述（見出しや物理名の参照、相手の内容を前提にした記述）は、要らなければ削る。

ただし、章が扱う対象（ログイン状態、ジョブなど）に関わる仕様は、ほかの章にあるものも、その章から仕様 ID で辿れるようにする。ほかの仕様が定める値（期限、件数など）やそこから導いた値を書くときも、その仕様 ID を添える。内容は書き写さない。

## レビュー

加筆修正したら、文脈を持たないサブエージェントに、次の観点で読ませる。編集したエージェントは、自分の知識で不足を補って読んでしまうためである。

- 採用を判断する開発者が、テンプレートが何をしていて、何を変えられるかを判断できるか
- 1章の方針（節の置き方、外部仕様とそれ以外の節の線引き、仕様項目の表の列の使い方）に合っているか
- 引き算と依存のルールに合っているか
- japanese-writing スキルの 4.2 の癖がないか
