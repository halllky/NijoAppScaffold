# 付録 この文書の記載ルール

この文書を保守する人のためのルールである。

## 執筆

- 各章の書き方は1章に従う。文の書き方は japanese-writing スキルに従う。
- 仕様項目の表と、それ以外の節や表とでは、役割が違う。
  - 仕様項目の表は、契約書の条文にあたる。書いた時点で当事者が決めきれなかったことを、後からこの記述をもとに厳密に判断する。そのため、場合分け・境界・例外を、読みやすさのために削ったり、ほかの節に移したりしない。
  - 状態遷移表や補足などの、仕様項目から導いた節や表は、人間が全体を把握しやすくするためのものである。仕様項目と内容が重なってよい。仕様項目から導けない取り決めは書かない。
- ほかの仕様項目が定める値（期限、件数など）や、そこから導いた値を書くときは、その仕様 ID を添える。値を変えるときに、仕様 ID で検索して直し漏れを防ぐため。
- 複数概念の関係や包含の説明で、文や表より図にしたほうが理解しやすいものには図を使う。
- 図は人間とAI両方が編集するため `.drawio.svg` で書き、 `images` フォルダに置く。Markdown のプレビューでは図の代替テキストが見えないので、何の図かは図の前の本文で示す。
- 図は、データビジュアライゼーションの定石に従って描く。
  - 無彩色を基調にし、色は意味を担わせるときだけ使う。強調には1色だけを使う。
  - 色だけで区別しない。形やラベルでも区別できるようにする。
  - 文字は本文と同じ墨色で書く。線や塗りの色を文字に使わない。
  - 線は細くし、枠や補助線は目立たせない。
  - ダークモードでも読めるよう、明暗それぞれの色を指定する。
  - 配色は既存の図に合わせる。
- 仕様 ID はソースコード（コメントやテストの名前を含む）に書かない。この文書を捨ててソースコードだけが使われる可能性があるため。
  - ただし、nijo.xml の Templates.MSG に定義するメッセージの識別子は、仕様 ID に合わせる。合わせないと、メッセージの文言の正本がこの文書とソースの二重になり、どの文言がどの仕様のものかを辿れないので、両者がずれても気付けない問題の方が大きいため。この識別子は、この文書を捨てても、nijo.xml と C#・TypeScript のコードを結びつける識別子として意味を持ち続けるので、上の懸念にあたらない。
- 「設定ファイルでは変えられない」「改修が必要」のような変え方は、仕様の本文や備考に書かず、変え方の列だけに書く。
- まだ実装していない仕様は、確認方法に「（未実装）」を付ける（例：テスト（未実装））。
  - 章の全体が未実装のときは、章の見出しにも付ける。実装済みの仕様の一部だけが未実装のときは、備考に「未実装：」に続けてその部分を書く。
  - 表ではない文章では、その文の末尾に「（未実装）」を付ける。「未実装」で検索すれば、対象の箇所がすべて分かるようにするため。
- ファイルは章ごとに分け、名前を「章番号（2桁）_章の名前.md」にする。章を足したり組み替えたりしたら、README.md の目次も直す。


## レビュー

加筆修正後はレビューをすること。
AIが加筆修正する場合、編集したエージェントは自身の知識に引きずられて正しくレビューできないので、コンテキストを持たないサブエージェントにレビューさせること。

### 読み手の目線で読めるか

この文書の読者は開発者である。ただし、派生アプリケーションの文書として使われると、システム担当利用者と運用担当者にも読まれる（1.1）。読み手によって、読む範囲と気にすることが違う。

- 採用を判断する開発者：全体を読む。テンプレートが何をしていて、何を変えられるかを判断する情報が足りているか。
- テンプレートに沿って作る開発者：全体を読む。作るための情報が足りているか。ソースコードに書くべきことが混ざっていないか。
- システム担当利用者：概要・外部仕様・限界を読む。実装の知識がないと分からない記述がないか。
- 運用担当者：本番環境での振る舞いに関わる箇所（ログ、エラーの通知、リリース、運用の章など）を読む。運用の作業に必要な情報が足りているか。

テンプレートに沿って作る開発者の目線は、執筆する人が既に持っているのでレビュー不要。残りの3者は視点が異なるのでレビューが必要。

サブエージェントに任せる場合、トークン使用料の節約のため、1つのサブエージェントに3者のレビューと、次の「日本語として読めるか」をまとめて依頼する。

### 日本語として読めるか

japanese-writing スキルの 5.2 の観点で読む。サブエージェントに任せる場合は、そのスキルのファイルのパスを渡して読ませる。
この文書は分量が多く、同じ癖が何か所にも出る。癖を1か所で見つけたら、文書全体から同じ癖の箇所を探し、それぞれの文を書き直す。語の機械的な置き換えはしない。

### 1章の方針に合っているか

1章の「各章の構成」と「仕様項目の表」に照らして読む。節の置き方、外部仕様とそれ以外の節の線引き（限界や開発者向け情報に外部仕様が混ざっていないか）、図に仕様が描かれていないかを見る。仕様の本文に、振る舞いではなく変え方（「設定で変えられる」「改修が必要」など）が書かれていないか、変え方・関連非機能要件の列と備考の「未対応」が実態に合っているかも見る。

### 影響する箇所の直し漏れはないか

執筆者自身も確認しているはずだがダブルチェックする。

### 「引き算」で書かれているか

記述は増えれば増えるほど整合性の確保が難しくなり、メンテナンス性が下がる。より少ない記述でより正確な情報を伝えられるほうがよい。
いまある記述の削除で目的の修正を達成できるならそれが最善。いまある記述の修正や統合が次善。どうしてもそれができない場合に加筆する。

これは変更後のファイルの行数を最小にしろという意味ではない。
複数行にわたって書かれていた情報を1文に詰め込んでもそれは記述量が減ったとは言わない。

仕様項目の場合分けや例外と、仕様項目から導いた節や表は、役割があって書いているので（執筆を参照）、記述量を理由に削らない。削る対象は、それ以外の、読み手の理解にも判断にも使われない記述である。

### 依存は最小限か

他の記述と整合していなければならない記述があるとき、この関係性を依存と呼ぶ。文書の見出しでの参照やソースコードの物理名の記載はもちろん、相手方に書かれている内容を前提とした内容依存も含む。

依存は増えれば増えるほど読者があちこち読まないといけなくなるし、メンテナンス漏れも頻発する。

依存しなくてよい箇所で依存しているなら削除する。
ただし、章が扱う対象（ログイン状態、ジョブなど）に関わる仕様は、ほかの章にあるものも含めて、その章を読めば漏れなく辿れるようにする。ほかの章にある仕様は、内容を書き写さず、仕様 ID で参照する。この参照は削ってはいけない依存である。
どうしても依存する場合、読者の理解を損なわない範囲で、より変わりづらい根幹的で抽象的な情報、相手方の内容が改訂されたときにこちらの内容を書き換えなくてもよい可能性が高い情報にのみ依存すること。
