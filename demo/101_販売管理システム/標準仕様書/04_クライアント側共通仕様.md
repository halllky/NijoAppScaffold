# 4. クライアント側共通仕様

ブラウザで動く画面に共通する仕様を扱う。画面の枠とナビゲーション、メッセージの表示、サーバーの呼び出しの打ち切り、表示する値によるスクリプトの埋め込み（XSS）への備え、画面の登録と共通部品である。

## 4.2 限界

- 呼び出しを打ち切っても（API-006）、サーバー側の処理は止まらない。サーバー側には、処理1回の時間の上限もない。更新が行われたかどうかは、利用者が画面を読み込み直して確認する。
- リバースプロキシやロードバランサーが60秒より早く接続を切ると、利用者には API-006 のエラーではなく、それらが返すエラーが表示される。待ち時間は60秒より長くする。
- 派生アプリケーションで、値を HTML として表示する画面（書式付きの文章を表示するなど）を作ると、SEC-004 の対象外になる。その画面で、表示する HTML を無害にする処理を加える。
- 本番環境では、画面の URL を開いたときに HTML にキャッシュさせない指示が付かないので（UI-008）、リリースの後も古い画面が使われることがある。リリースの後は利用者に再読み込みを案内するか、リバースプロキシで指示を付ける。
- 画面の読み込み中の例外では問い合わせ番号が出ないので（UI-004）、利用者の問い合わせからは、時刻とユーザー ID でログを探す。

## 4.3 開発者向け情報

### 画面の番号と登録

- 画面には番号を付け、画面のファイル名を `P{3桁の番号}_{画面名}` とする。P000 はトップページ、P001 はログイン、P002 はログアウト、P003 は通知（12章）、P004 はジョブ（13章）である。
- 業務ごとに画面の番号の百の位を割り当て、一覧を `P*00` 、その詳細を `P*01` のように付ける。
- 画面のフォルダに画面のファイルを置き、決まった形でルーティングとメニューの項目を公開すると、自動で登録される。画面のファイルを削除するだけで画面がなくなる。
- この性質を保つため、共通の部分（アプリの枠、ルーティング、ナビゲーション、検索ダイアログの対応表、画面の共通部品）から業務画面を参照しない。業務に固有のコード（特定のデータ構造を扱う部品や関数）は、業務画面のフォルダの中に置く。画面の共通部品は、特定のデータ構造の生成された型を参照しない。
- ほかの画面へ移るための URL は、遷移先の画面が関数として公開する。URL の文字列をほかの画面のファイルに直接書かない。
- サーバーからリンクする画面（通知のリンク先など）は、URL の正本を nijo.xml のテンプレート文字列（Templates）に置き、サーバーと画面の両方がそこから組み立てる。サーバーと画面で URL が食い違うのを、手で合わせなくても防げるようにするため。それ以外の画面の URL は、画面のファイルに書く。
  - すべての画面の URL をテンプレート文字列に置かないのは、画面のファイルを置くだけで画面を追加でき、削除するだけで画面がなくなる性質を保つため。
- 業務画面のルーティングには、ログインしていなければ画面の読み込み処理（loader）を行わない設定を付ける（AUTH-004）。

### 画面の作り方

- 一覧検索・詳細編集・一括編集・検索ダイアログは、共通部品を使って作る。部品の一覧と使い方は、共通部品のソースのコメントを正とする。部品の動きは、開発支援機能の見本の画面（21.2）で確かめられる。

### サーバーの呼び出し

- 呼び出しの打ち切り（API-006）は、画面からサーバーを呼ぶ共通の関数が、リクエスト1回ごとに行う。確認メッセージの後の2回目の呼び出しや、ログインし直した後の送り直しは、それぞれ改めて60秒を数える。
