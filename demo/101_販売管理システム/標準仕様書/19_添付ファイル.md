# 19. 添付ファイル

画面からファイルを送り、データに添付し、ダウンロードする機能を扱う。
最終的にファイルを格納する場所は案件によって千差万別なので、テンプレートが用意するのは、ブラウザからサーバーにファイルを送り、データと結び付けて管理するところまでである。格納先は差し替えられるように作っている。

添付ファイルを使わない案件では、この機能を削除する（19.3 の「添付ファイルを使わない場合」）。

## 19.2 限界

- 参照なしにするのはクリーンナップのとき（毎日1回）なので、ファイルを差し替えたりデータを物理削除したりしても、次のクリーンナップまでは、識別子を知っていればダウンロードできる。論理削除したデータのファイルは参照なしにならないので、ダウンロードできるままである。すぐに止めたいときの手段は 19.3。
- 参照なしのファイルを削除するまでの期間は、DB のバックアップを残す期間より長くする。短いと、DB をバックアップから戻したときに、参照されているファイルが保存先に無い状態になる。
- ファイルの中身を編集する機能と、版を管理する機能はない。内容を変えたいときは、新しいファイルを添付し直す。
- 次のものは扱っていない。必要なら案件で、一時保存のときの確認として作る。
  - 拡張子や種類による制限
  - ウイルスチェック
  - 1件のデータあたりの、ファイルの数や合計サイズの上限
- ファイルの種類（Content-Type）は、ブラウザが送ってきた値をそのまま記録する。ダウンロードは必ず保存させるので（FIL-008）、画像のプレビューやブラウザでの PDF の表示はできない。
- 参照として数えるのは、nijo.xml で添付ファイルを参照している項目だけである。手書きのテーブルや、変更前後の値の記録（11.3）に識別子を文字列で残しただけのものは数えないので、そのファイルは参照なしになり、一定期間の後に削除される。数え方の変え方は 19.3。
- 保存先と DB は1つのトランザクションに入らない。一時保存の途中や削除の途中でサーバーが停止したときや、削除のときに保存先のファイルを消せなかったときは、保存先に、管理テーブルに行の無いファイルが残ることがある。このファイルはクリーンナップでも削除されず、見つける手段もない。気になる場合は、保存先のファイルの一覧と管理テーブルを突き合わせて消す処理を、案件で作る。
- 既定の保存先はサーバーごとのフォルダなので、サーバーが複数台のときは、共有の保存先に変える必要がある（19.3）。

## 19.3 主なカスタマイズ方法

### 保存先を変える

- ファイルの保存先は、保存・読み出し・削除だけをもつインターフェースの実装で決まる。既定の実装は、設定ファイルで指定したフォルダに識別子の名前で保存する（FIL-004）。
- S3 や Azure Blob Storage などに変える場合は、そのインターフェースの実装を作り、DI の設定で登録し直す。
- 保存先は外部システム（12章）としては扱わない。モックも置かないので、開発環境では、既定のフォルダの実装を使うか、開発用のバケットなどを用意する。
- 実装を差し替えても、一時保存・確定・参照なし（FIL-002、FIL-005、FIL-006）の振る舞いは変わらない。
- Salesforce のように、保存先の側で識別子を採番したり、どのデータに結び付けるかを指定したりする必要があるシステムは、保存先にしない。保存先は S3 などにしておき、データの保存に合わせて、外部システムの更新（12章）として送る。

### ダウンロードの確認を足す

- アプリケーションサービスに、ダウンロードしてよいかを判断するメソッドがある（FIL-007）。既定では確認しない。
- ファイルの側は、どのデータから参照されているかを知らない。「そのファイルが添付されたデータを見る権限があるか」で判断する場合は、そのファイルを参照しているテーブルを検索する処理を、案件で書く。
- この確認を足す場合は、添付できるファイル（FIL-009）も同じ条件で絞る。絞らないと、識別子を知っている人が自分のデータにそのファイルを添付し、自分のデータとしてダウンロードできてしまう。

### 参照として数えるものを足す

- 手書きのテーブルや変更前後の値の記録に残したファイルを、参照なしにしたくない場合は、クリーンナップで参照を集める処理に、そのテーブルを足す（19.2）。
- 変更前後の値の画面などから古いファイルをダウンロードさせたい場合も、同じく参照として数えるようにする。参照なしのままでは、ダウンロードできないため（FIL-010）。

### 誤って添付したファイルをすぐに使えなくする

- テンプレートには、ファイルを個別に削除する画面はない。
- まず、そのファイルを添付しているデータを差し替えるか物理削除する。そのうえで、システム管理者がクリーンナップを実行すれば、参照なしになり、ダウンロードできなくなる。
- 論理削除したデータのファイルや、保存先からもすぐに消す必要があるファイルは、識別子を指定して保存先のファイルと管理テーブルの行を消す処理を、案件で作る。業務のテーブルから参照されているファイルの行は、DB の外部キー制約によって消せない。削除済みテーブルには外部キー制約が無いので、行を消す前に、削除済みテーブルのその値も空にしておく。

### 添付ファイルを使わない場合

次のものを削除する。

- nijo.xml の次の定義と、それらを参照している項目。削除したら再生成する。
  - データモデル「添付ファイル」、クエリモデル「添付ファイルRef」、静的区分「添付ファイルの状態」
  - テンプレート文字列 API_URL の、一時保存とダウンロードの URL
  - テンプレート文字列 MSG の、添付ファイルのエラーのメッセージ。クリーンナップの結果のメッセージからも、添付ファイルの件数を除く
- Core の添付ファイルのフォルダと、添付ファイルの単体テスト。
- 共通の保存の処理の中の、添付ファイルを確定の状態にする呼び出しと、それが失敗したときの保存の失敗の種類。
- 設定クラスの添付ファイルの設定（設定の検証を含む）と、設定ファイルの添付ファイルのセクション。
- DI の設定にある、保存先の登録。
- WebApi の、一時保存とダウンロードのエンドポイントと、それらの登録。
- クライアントの、ファイルを一時保存する処理と、ファイルを選ぶボタンとダウンロードのリンク。
- クリーンナップの中の、添付ファイルを削除する呼び出し。
- 添付ファイルのテーブルを削除するマイグレーションを追加する。

## 19.4 開発者向け情報

### データの持ち方

- 添付ファイルは、1ファイルにつき1行の管理テーブルで管理する。管理テーブルは nijo.xml のデータモデル「添付ファイル」で、識別子・名前・サイズ・種類（Content-Type）・状態・参照なしになった日時をもつ。一時保存したユーザーと日時は、全データモデル共通の作成者・作成日時の列（UPD-001、UPD-002）を使う。
- 状態は、一時保存・確定・参照なしのいずれかである。
- 業務のデータにファイルを添付するときは、データモデルの項目を「添付ファイル」への参照（`ref-to:添付ファイル`）にする。業務のテーブルには、識別子の列と外部キー制約だけができる。ファイルの名前やサイズは業務のテーブルにもたず、管理テーブルを結合して取る。
- 画面のデータ（クエリモデル）とコマンドの引数では、クエリモデル「添付ファイルRef」への参照にする。従業員の参照と同じ形である。
- 1件のデータに複数のファイルを添付するときは、子配列（children）の中に、ファイルの項目を1つ置く。ファイルが何の書類か（納品書、見積書など）を区別したい場合は、子配列に備考や区分の項目を足す。1つの項目に複数のファイルを入れる方法は用意していない。
- 列名やテーブル名を変えるときは、ほかのデータモデルと同じく nijo.xml の DbName で指定する。

### 一時保存

- 画面でファイルを選ぶと、その場で一時保存の API にファイルを送る。画面は、返ってきた識別子・名前・サイズ・種類を入力中のデータに入れる。処理を呼ぶときに送るのは、この識別子だけである。
- 一時保存の API は、ログインしているかを確認し、サイズの上限を超えるファイルを拒否する。ASP.NET Core のリクエストの本体の上限も、この上限に合わせる（FIL-003）。
- 一時保存では、ファイルの中身を保存先に書いてから、管理テーブルに一時保存の行を足す。行を足せなかったら、保存先に書いたファイルを消す。
- ジョブのようにログインユーザーのいない処理では、API を経由せず、アプリケーションサービスの一時保存のメソッドを直接呼ぶ。このメソッドは中で独自にトランザクションを開始してコミットするので、トランザクションの外で呼ぶ。そのファイルを添付できるのは、同じ処理だけである（作成者には処理の名前が記録されるため。UPD-002）。

### 添付したファイルを確定の状態にする

- 状態の変更は、手書きの保存の共通の処理（11.4 の「保存の処理」）で、DB に保存する直前に行う。追加・変更されるデータの中から、管理テーブルへの参照を探し、一時保存や参照なしの行を確定に変える。この変更は業務のデータと一緒に保存するので、データの保存が失敗すれば、ファイルの状態も変わらない。
- 同じ場所で、添付できるファイルかどうかを確かめる（FIL-009）。
- コマンドの引数で受け取ったファイルも、処理の中でデータモデルに入れて保存すれば、同じ仕組みで確定する。ファイルの中身を読んで捨てるだけの処理（CSV の取込など）では確定せず、一時保存のまま削除される。
- 保存先へのファイルの書き込みは一時保存のときに済んでいるので、データの保存では保存先に触れない。そのため、外部システムの更新（EXT-001）としては扱わない。

### 中身の読み出しとダウンロード

- 処理の中でファイルの中身が必要なときは、アプリケーションサービスのメソッドに識別子を渡して読み出す。
- ダウンロードの API は、ログインしているか、状態がダウンロードできるものか（FIL-007、FIL-010）、手書きで追加した確認を通るかを確かめてから、ファイルを返す。ファイル名と種類は管理テーブルから取る。
- 応答には `Content-Disposition: attachment` を付けて、ブラウザで開かせない（FIL-008）。中身の種類を推測させない指示は、SEC-006 で全応答に付く。

### クリーンナップ

クリーンナップは、添付ファイルについて次の順に処理する。

1. 一時保存から24時間が過ぎたファイルを削除する（FIL-005）。
2. 管理テーブルへの参照をもつ全テーブルと、論理削除の削除済みテーブルから、参照されている識別子を集める。確定のファイルのうち参照されていないものを参照なしにし、参照なしのファイルのうち参照されているものを確定に戻す（FIL-006）。
3. 参照なしになってから設定の期間が過ぎたファイルを削除する（FIL-006）。

参照をもつテーブルは、Entity Framework Core のモデルの外部キーから探す。削除済みテーブルには外部キー制約が無いので、元のテーブルの外部キーと同じ列を見る。そのため、添付ファイルを使うデータモデルを増やしても、クリーンナップを直す必要はない。

ファイルの削除では、管理テーブルの行を消してから、保存先のファイルを消す。行を消すときに状態を確かめるので、削除する対象を探してから消すまでの間にデータに添付されたファイルは消さない。保存先のファイルを消せなかった場合は、行の無いファイルとして保存先に残る（19.2）。
