# 9. 外部システム連携

外部システム（1.2）のうち、環境によってはモックに切り替えて動かすものを扱う。データベースやログファイルは、アプリケーションの外にあっても、ここでいう外部システムではない。メールサーバーは、開発中の誤送信を防ぐためにモックで動かすので、外部システムとして扱う。

ここでは、外部システムの更新を伴う処理の決まりと、外部システムの代わりに動くモックを扱う。モックは、外部システムの環境を用意しなくても開発環境で動作を確かめられるようにするためのもので、本番稼働を始めた後も削除せず残す。

テンプレートに実際の外部システムとの連携サンプルはなく、連携を追加するための枠がある。

## 9.1 外部仕様

| ID | 仕様 | 確認方法 | 関連非機能要件 | 備考 |
|---|---|---|---|---|
| EXT-001 | 外部システムの更新を伴う処理では、原則として、外部システムの更新をすべて先に行い、1つでも失敗したら DB をコミットしない | 検査 | | DB の確定の後に外部システムを更新する必要がある処理は、個別に決める |
| EXT-002 | 外部システムごとに、どの実装（本物の実装、モックなど）を使うかを設定で切り替えられる。一部の外部システムだけをモックにして動かせる | 検査 | | 見本は、テンプレートではエラーの通知のメールの送信（ALR-005）、デモ101では参考実装の商品管理システムとの連携。 |
| EXT-003 | どの実装を使うかの設定を省略したときは、起動を止める | 検査 | 運用・保守性 | モックのまま本番環境が動き続け、誰も気付かない事態を防ぐため。開発環境やテスト環境でも、モックを使うことを設定に明記する |
| EXT-004 | 本番環境でモックを使っているときは、起動のときに、モックを使っている外部システムの名前をログに Warning で出力する | 検査 | 運用・保守性 | 意図してモックで動かすときも、どれがモックかをログで確かめられるようにするため |

## 9.2 限界

- 成功済みの外部システムの更新は、後続の外部システムの更新や DB のコミットが失敗しても取り消されない（EXT-001）。失敗した更新は、その名前とともに Error でログに出て、それより後の更新は実行されなかったことが Warning で出る。それより前の更新は成功している。運用担当者は、これらのログから、どのデータの更新かを特定して復旧する。
- 失敗した後に利用者が保存し直すと、同じ冪等キーで送り直されるが、DB の変更は取り消されているので処理し直される（UPD-008）。成功済みだった外部システムの更新は、もう一度実行される。二重に更新されて困る外部システムでは、外部システムの側で重複を見分けるか、案件で対策する。
- 外部システムの更新は、DB のトランザクションを開いたまま実行する。外部システムが応答しない間は DB の書き込みのロックが残り、ほかの利用者の更新が待たされる。待ち時間（既定は30秒）を過ぎると予期しない例外になる（API-004）。外部システムの呼び出しには、案件で時間の上限を設ける。
- モックを使っていることの Warning（EXT-004）は、エラーの通知（ALR-001）の対象ではない。リリースの後は、起動のときのログを確かめる。
- 外部システムの呼び出しのリトライ・タイムアウトの仕組みはない。外部システムごとに実装する。

## 9.3 主なカスタマイズ方法

### 外部システム連携を追加する

- 外部システムごとにインターフェースを定め、本物の実装とモックを作り、設定で切り替える（EXT-002）。EXT-003 と EXT-004 は共通の仕組みではないので、追加する外部システムごとに実装する。本物の実装は、接続のしかたの違いなどで複数あってもよい。モックが何をするか（送る内容をファイルに書き出す、決まった応答を返すなど）は、外部システムごとに決める。実装を登録する場所はテンプレートにある。
- 更新を伴う連携は、EXT-001 の順序で行われるよう、アプリケーションサービスのトランザクションに参加させる（9.4）。

## 9.4 開発者向け情報

- 外部システムの更新は、その場で実行せず、トランザクションに予約する。予約した更新は、コミットのときに、DB の確定より先に、予約した順に実行される（EXT-001）。途中で失敗したら、それ以降の更新は実行せず、DB の変更を取り消す。コミットせずに終わると、予約した更新は実行されない。
- 予約には、どのデータを更新しようとしたか（キーなど）が分かる名前を付ける。失敗より前に成功した更新を、運用担当者が復旧するため（9.2）。1つの操作で複数の更新を予約するときは、途中で失敗したときの復旧のしかたを決めてから実装する。
- 外部システムの更新の失敗による例外は捕まえない（6.3）。
- 外部システムからの読み取りは、予約せずにその場で行ってよい。
- どの実装を使うかの設定の確認（EXT-003）と、モックを使っていることの Warning（EXT-004）は、共通の仕組みにはしていない。外部システムを DI コンテナに登録する処理の中で、外部システムごとに書く。実装の選択肢が外部システムごとに異なるため。
- 予約のしかたの細部（どこから予約するか、リトライをどこに書くか）は、トランザクションのクラス（`ExternalResourceTransaction`）の予約のメソッドのコメントを参照する。
