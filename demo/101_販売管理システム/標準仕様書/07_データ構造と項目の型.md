# 7. データ構造と項目の型

データ構造の分け方の考え方と、項目に指定する型ごとの保存のされ方、画面での入力、入力チェック、検索のしかたを扱う。nijo.xml を定義する人が知っておくべきことをまとめている。型の種類と、DB・C#・検索での扱いは nijo が決めていて、変えられない。画面の入力欄での変換と、クライアントとサーバーの間の値の受け渡しは手書きのコードだが、すべての画面で使われるので、変えると広い範囲に影響する。

## 7.1 データ構造の分け方

- `IsStored` を指定するデータ構造（データモデル）は、データの整合性を保つ単位で分ける。1つのデータモデルは、子（`child`）や子の配列（`children`）を含めて、まとめて登録・更新・削除される。
- `IsQueryable` を指定するデータ構造（クエリモデル）は、画面に表示する粒度で分ける。
- ほかのデータ構造は、外部参照（`ref-to`）で参照する。多対多の関係は、子の配列と外部参照で表す。

## 7.2 型の一覧

| 型（nijo.xml の指定） | 向いている値 | C# と DB での扱い | 画面の入力欄 | 検索条件 |
|---|---|---|---|---|
| 単語型（`word`） | 名前など、改行を含まない文字列 | 文字列 | 1行の入力欄 | 部分一致（既定）・前方一致・後方一致・完全一致・範囲のどれかを、項目ごとに nijo.xml で選ぶ |
| 文章型（`description`） | 備考など、改行を含む文字列 | 文字列 | 複数行の入力欄 | 単語型と同じ。検索条件の入力欄は1行 |
| 整数型（`int`） | 数量、回数 | 32ビットの整数 | 数値の入力欄 | 範囲（以上・以下） |
| 実数型（`decimal`） | 金額、割合 | 10進の実数 | 数値の入力欄 | 範囲 |
| 日付型（`date`） | 年月日 | 日付。時刻をもたない | ブラウザの日付の入力欄 | 範囲 |
| 日付時刻（`datetime`） | 日時 | 日時。タイムゾーンをもたない | ブラウザの日時の入力欄。分までを入力する | 範囲 |
| 年（`year`） | 西暦年 | 4桁の整数 | 4桁の数値の入力欄 | 範囲 |
| 年月型（`yearmonth`） | 西暦の年月 | DB では6桁の整数（yyyymm） | ブラウザの年月の入力欄 | 範囲 |
| 真偽値型（`bool`） | フラグ | 真偽値 | チェックボックス。値がないときは偽として表示する | 「該当する」「該当しない」のどちらか、または絞り込まない |
| 静的区分型（静的区分の名前） | 区分、ステータス | nijo.xml に定義した静的区分。C# では enum | ドロップダウン。先頭に未選択がある | 複数の値を選び、いずれかに一致するもの |
| 値オブジェクト型（値オブジェクトの名前） | 「○○コード」など、特別な意味をもつ文字列 | C# では専用の型、DB では文字列 | 単語型と同じ | 単語型と同じ |
| シーケンス型（`sequence`） | 自動で採番する番号 | 整数。DB が連番を振る | 数値の入力欄 | 範囲 |
| バイト配列（`bytearray`） | バイナリ | バイト列 | なし。画面では使えない | なし。検索できるデータ構造には使えない |

ファイルを扱う型は 20章（未実装）。

## 7.4 限界

- TYP-001 と TYP-004 の変換は画面の入力欄で行う。サーバー側では行わないので、画面を経由しない値（ジョブ、バッチ、ファイルの取り込み、API の直接の呼び出し）は変換されない。これらはデータの整合性のための変換ではなくUIの操作性向上のための変換なので。
- 参照（Ref）の項目でコードを手入力したときは、項目の指定によらず、前後の空白の削除と NFKC を行ってから参照先を照合する。
- 大文字と小文字、ひらがなとカタカナをそろえる変換は行わない。
- 文字の種類（半角英数字だけ、など）を制限する指定はない。カスタム属性による入力チェック（12.4）で作る。
- 日付時刻はタイムゾーンをもたず、業務のタイムゾーンの現地時刻として扱う（ENV-004）。秒は画面から入力できない。

## 7.5 開発者向け情報

### 文字列と数値の扱い

- 型ごとの入力チェック（文字列の長さ、数値の桁数、必須）の中身は、手書きのコード（`Core/OverridedDbContext.Validation.cs`）にある。nijo は、これらを DbContext の abstract メソッドとして生成し、登録・更新のコマンドの入力チェックから項目ごとに呼ぶ。手書きのコードは、TYP-002・TYP-005・TYP-008 のとおりに書いたテンプレートの初期値で、案件の事情に合わせて書き換えてよい。
- 例えば、TYP-002 の数え方のままでは、SQL Server などで、絵文字や結合文字を含む値が、入力チェックを通っても DB の列の長さを超えることがある。DB の製品が長さを数える単位（UTF-16 の単位など）に合わせるときは、文字列の長さのチェック（`ValidateMaxLength`）を書き換える。
- 未入力の項目は、空の文字列ではなく、値なし（null）として保存する。画面は、空の文字列をサーバーに送らない。
- 金額や数量の計算結果の丸めは、計算する業務処理の中で行う。丸めの共通の処理はない。

### 区分値の設計

区分値は、その性質によって、静的区分、汎用参照テーブル、普通のデータモデル、nijo.xml を介さない手書きの enum を使い分ける。汎用参照テーブルは、「コード、名称、表示順」程度の項目しかもたない区分値を、区分の種類ごとにテーブルを作らず、1つのテーブルにまとめて保存する nijo の仕組みである。区分の種類ごとに DB のビューを作る（6.3）。

#### A. 本番運用中に区分値が増減しない区分の場合

1. DB の列や、クエリモデルの検索条件・検索結果、コマンドの引数や戻り値に登場する
   **→ nijo の静的区分として実装する（自動生成後に C# の enum や TypeScript のユニオン型になる）。**
2. 登場しない
   **→ C# の enum などを手書きのコードで宣言して使う。**

#### B. 本番運用中に区分値が増減する区分の場合

1. 「コード、名称、表示順」程度を超えて、「オプション1, 2, ...」「属性1, 2, ...」などのキー以外の項目をもつ
   **→ それはもはやコード/名称だけの区分と同列に扱ってよい存在ではないので、普通のデータモデルとして設計する。**
2. 「コード、名称、表示順」程度の項目しかもたない
   **→ nijo の汎用参照テーブルを使う。**

### 汎用参照テーブル

テンプレートとデモ101では使っていないが、区分値の設計（B-2）で使う。

- キーは複数の項目からなる。そのうち、区分の種類を表す項目（例：業務分類・コード種別）は nijo.xml に書いた値に固定され（`IsHardCodedPrimaryKey`）、残りの項目（例：コード値）だけを運用中に登録する。区分の種類と、固定される値の組み合わせは、nijo.xml の `GenericLookupTableCategories` に定義する。
- 項目は「コード、名称、表示順」程度にとどめる。それを超える項目をもたせたくなった区分は、普通のデータモデルに切り離す（B-1）。
- 登録・更新・削除は、普通のデータモデルと同じく生成された処理で行う。区分の種類を表す項目の値は、生成された補助のプロパティから取り出して設定する。区分の種類ごとの値の一覧（ドロップダウンの選択肢など）も、同じ補助のプロパティから取り出す。
- 区分値を参照するデータは、区分の種類を表す項目をもたず、残りの項目（コード値）だけをもつ。nijo.xml では、参照の項目に区分の種類（`Category`）を指定する。
- DB の外部キーの制約は付かない。代わりに、生成された入力チェックが、参照先の区分値が存在するかを確かめる。ただし、入力チェックと保存の間に区分値が削除されると、存在しない区分値を参照したデータが保存されることがある。
- 参照するデータを検索するときは、区分の種類ごとに作られた DB のビューと結合して、その時点の名称や表示順を取り出す。ビューの列と結合の関係は、nijo が Entity Framework Core の設定として生成するが、ビューを作る SQL は生成しない。ビューを作る SQL は、テンプレートの Management のコマンドが、nijo が生成したビューの情報をもとに作る（6.3）。このコマンドは SQLite を対象にしているので、ほかの DB の製品にする場合は書き換える。生成されたコードはビューがあることを前提にしているので、汎用参照テーブルを使う場合は、ビューを常に最新に保つ。
- 汎用参照テーブルは、外部キーの制約が効かない、ER 図で依存関係が見えない、1つのテーブルに参照が集中する、という理由で、一般にはアンチパターンとされることが多い。使う区分は慎重に選ぶ。
