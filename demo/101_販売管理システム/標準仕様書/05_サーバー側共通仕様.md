# 5. サーバー側共通仕様

サーバーが、受ける要求と返す応答、DB の読み書きに共通にかける仕様を扱う。CSRF やクリックジャッキングなどほかのサイトを使った攻撃への備え、応答に付けるヘッダー、SQL インジェクションへの備え、要求の大きさや頻度の扱いである。エラーの扱いは6章、検索と更新に固有のものは7章と8章で扱う。

## 5.1 外部仕様

| ID | 仕様 | 変え方 | 確認方法 | 関連非機能要件 | 備考 |
|---|---|---|---|---|---|
| SEC-005 | DB を読み書きするときは、利用者の入力などの値を SQL の文に埋め込まず、パラメーターとして DB に渡す。テンプレートの処理と、自動生成の処理が対象である | コード改修 | 検査 | セキュリティ | 入力で SQL を書き換えられる攻撃（SQL インジェクション）を防ぐため。開発支援機能の DB ビューアは、入力した条件を SQL にそのまま埋め込むが、本番用のビルドには含まれない（DEV-001） |
| SEC-006 | すべての応答に、表「SEC-006 応答に付けるヘッダー」のヘッダーを付ける。エラーの応答、静的なファイル、死活の確認（OPS-001）の応答も対象である。開発環境で、画面の開発サーバーが返す応答にも付ける。表のほかに、セキュリティのためのヘッダーは付けない。API の応答（ファイルのダウンロードを含む）には、キャッシュを制限するヘッダー（`Cache-Control` など）も付けない | コード改修 | 実演 | セキュリティ | スクリプトの読み込み元を制限しない理由は 5.2。API の応答のキャッシュの制限は未対応。`X-Frame-Options`、`Content-Security-Policy`、`Referrer-Policy` が意味をもつのは画面の HTML に対してだけだが、付け漏れを防ぐため、応答の種類で付け分けない。画面の HTML のキャッシュは UI-008。HSTS（SEC-001）と CORS（SEC-002）のヘッダーは付けない |
| SEC-007 | ほかのサイトのページから、ログイン中の利用者として処理を呼ばせる攻撃（CSRF）への対策は、この仕様と、セッションキーの Cookie の SameSite 属性（SES-002）の2つである。CSRF のトークンは使わない。本番環境では、GET・HEAD・OPTIONS 以外のメソッドの要求（処理の呼び出し、添付ファイルの一時保存など）に、`X-Requested-With` ヘッダーを必須にする。値は問わない。ヘッダーがなければ、処理を実行せず、状態コード 400 を本文なしで返す。このとき、LOG-007 のログに状態コード 400 で出るほかには、ログを出力しない。死活の確認（OPS-001）は対象外である。開発環境では確かめない。画面は、サーバーを呼ぶときに、メソッドによらず必ずこのヘッダーを付ける。テンプレートと自動生成の API のうち、GET・HEAD・OPTIONS で呼べるもの（ファイルのダウンロードなど）は、業務のデータを変えない | コード改修 | 実演 | セキュリティ | ほかのオリジンのページは、このヘッダーを付けて送れない（SEC-002）。開発環境で確かめないのは、API の一覧（Swagger）から呼び出せるようにするため |
| SEC-008 | 応答に `Server` ヘッダーを付けない | コード改修 | 実演 | セキュリティ | 使っているソフトウェアを外に知らせないため |
| SEC-009 | ログインの一時ロック（AUTH-010）のほかに、呼び出しの回数や頻度を制限しない。要求の本文の大きさの上限は、ASP.NET Core の既定の 30,000,000 バイト（約 28.6MB）である。添付ファイルの一時保存だけは、1ファイルの大きさの上限（FIL-003）に 64KB を足した大きさである | コード改修 | 検査 | セキュリティ、可用性、性能・拡張性 | 未対応 |

### SEC-006 応答に付けるヘッダー

| ヘッダー | 値 | 理由 |
|---|---|---|
| `X-Frame-Options` | `SAMEORIGIN` | ほかのサイトのページの枠（iframe）の中に、画面を表示させないため。見えないように重ねた画面を、利用者に知らずに操作させる攻撃（クリックジャッキング）を防ぐ。古いブラウザ向けで、今のブラウザは次の `frame-ancestors` に従う |
| `Content-Security-Policy` | `frame-ancestors 'self'` | 上と同じ。同じオリジンの画面の枠の中には表示できる。スクリプトやスタイルの読み込み元を制限する指定は付けない |
| `X-Content-Type-Options` | `nosniff` | 応答の中身の種類をブラウザに推測させず、テキストなどをスクリプトや HTML として扱わせないため |
| `Referrer-Policy` | `same-origin` | 画面からほかのサイトに移るときや、ほかのサイトの画像などを読むときに、画面の URL を送らないため |

## 5.2 限界

- IIS の上で動かすと、IIS が `Server` などのヘッダーを付ける。テンプレートでは外していないので、IIS の設定で外す。リバースプロキシやロードバランサーが付けるヘッダーも、その装置の設定で外す（SEC-008）。
- スクリプトの読み込み元を制限する指定がないので（SEC-006）、画面に不正なスクリプトを埋め込まれたときの多層防御がない。制限をそのまま付けると画面が動かなくなるので、付けるなら、派生アプリケーションで画面のビルドとあわせて調整が要る。
- ほかのオリジンからの呼び出しを許可すると（SEC-002）、許可した相手のページには、SEC-007 の対策が効かない。許可するなら、相手を信頼できるオリジンに限る。
- 派生アプリケーションで、GET で業務のデータを変える API を作ると、SEC-007 の対象外になる。SameSite 属性が `Lax` の Cookie は、ほかのサイトのリンクから開いたときにも送られるので、そのリンクを踏ませるだけで実行させられる。データを変える API は、POST などのメソッドで呼ぶ形にする。
- 大量の呼び出しによる負荷（DoS）への備えはない（SEC-009）。必要なら、リバースプロキシやロードバランサー、WAF で、呼び出しの頻度や大きさを制限する。

## 5.3 開発者向け情報

### 攻撃への備え

- SEC-006 のヘッダーは、`WebApi/SecurityHeadersMiddleware.cs` と `client/vite.config.ts` の2か所に書いている。
- `X-Requested-With` ヘッダー（SEC-007）は、画面からサーバーを呼ぶ共通の関数で付けている。派生アプリケーションでこの関数を通さずに GET・HEAD・OPTIONS 以外のメソッドで API を呼ぶと、開発環境では動くが、本番環境でだけ 400 になる。
- 手書きの SQL では、値を文字列の連結で SQL に埋め込まない。Entity Framework Core の `FromSql` や `SqlQuery` に補間文字列で渡すと、値はパラメーターになる。`FromSqlRaw` や `ExecuteSqlRaw` に値を連結した文字列を渡すと、SEC-005 が成り立たなくなる。

### API の形

- nijo.xml に定義した検索処理と更新処理の API は、自動生成される。自動生成によらない API を手で作ることもできる。見本が WebApi プロジェクトにあるので参照のこと。
- 自動生成された API は、REST の形ではなく、処理ごとの URL に POST で呼ぶ形である。検索も POST で呼ぶ。
- 手で作る API を画面から呼ぶ場合は、URL の正本を nijo.xml のテンプレート文字列（Templates）に置き、サーバーのルート定義と画面からの呼び出しの両方がそこから組み立てる。サーバーと画面で URL が食い違うのを防ぐため。ルート定義は、引数の位置にルートパラメーターをそのまま置く変換で組み立てるので、引数は文字列にする。
- 自動生成された API の、入力の受け取りと、メッセージ・確認メッセージ・戻り値の返却は、サーバー側の共通の処理が行う。これと、クライアントからサーバーの処理を呼ぶ共通の関数が対になっている。
- 応答は、完了・エラーまたは確認待ち・未ログイン・入力の形式の誤り・予期しない例外を、画面が区別できる形にしている。応答の形はこの2つの共通処理の間の取り決めなので、両方を一緒に変える。

### オペレーションコンテキスト (OperationContext)

オペレーションコンテキスト（1.6）は、アプリケーションサービスのメソッドの入出力のうち、次の表の最後の種類を受け渡す。

| 情報 | 受け渡し方 | データ構造 |
|---|---|---|
| 入力 | 処理の引数 | 自動生成 |
| 戻り値 | 処理の戻り値 | 自動生成 |
| エラー・情報のメッセージ | 入力と同じ構造のメッセージのオブジェクト | 自動生成 |
| 入力チェックだけを行うかの指定、確認メッセージなど、すべての処理に共通の入出力 | オペレーションコンテキスト | 手書き |

- オペレーションコンテキストは、nijo が生成するものではなく、テンプレートの手書きのクラスである。nijo はその中身を見ない。呼び出し1回ごとの情報を、派生アプリケーションでプロパティとして追加してよい。画面に返す情報を追加した場合は、サーバー側の共通の処理とクライアントの呼び出しの共通の関数の両方に、同じものを手で加える。
- 呼び出し元（画面からの API、単体テスト、ジョブ）は、呼び出しのたびにオペレーションコンテキストを作って処理に渡し、処理の後に中身を読む。ログインユーザーや現在時刻のように、呼び出しの回数によらず同じ値になるものは入れず、DI から取得する。
- 処理の中から別の処理を呼ぶときは、同じ呼び出しの続きなので、同じオペレーションコンテキストを渡す。入力チェックだけを行うかの指定などを変えて呼びたいときは、新しく作って渡す。
- メッセージのオブジェクトの使い方（項目ごと、明細の行ごとのメッセージなど）は、nijo が生成するコードの使い方なので、nijo のリファレンスを参照する。
