# 11. 権限

ログインユーザーがどの機能を使えるかを扱う。ログインユーザーが誰かを確かめる仕組みは10章にある。

権限は、画面ごとではなく、処理ごとに決める。処理とは、画面がサーバーに頼む1つ1つの検索や更新のことである。画面を使えるかどうかは、その画面が呼ぶ処理を呼び出せるかどうかで決まる。

処理ごとに、呼び出せる利用者を「ログイン不要」「ログインユーザー全員」「権限で指定」「内部処理のみ」のいずれかで宣言する（AUZ-007）。「権限で指定」では、ユーザーに付ける権限の種類（権限区分）を指定する。サーバーは処理を実行する前に、画面は表示を切り替えるときに、この宣言を使う。

### AUZ-007 機能公開レベル

| 機能公開レベル | 呼び出せる利用者 |
|---|---|
| ログイン不要 | ログインしていない利用者を含め、誰でも呼び出せる。テンプレートの該当の処理は AUTH-009 にある |
| ログインユーザー全員 | ログインしていれば、誰でも呼び出せる |
| 権限で指定 | 宣言した権限区分のいずれかを持つユーザーだけが呼び出せる。システム管理者は常に呼び出せる（AUZ-003） |
| 内部処理のみ | 画面からは誰も呼び出せない。API として公開せず、ジョブなどサーバーの中からだけ呼ぶ |

## 11.2 限界

- データ単位の権限（部署や拠点などで、見られるデータを絞る）の共通の仕組みはない。必要なら 11.3 の方法で加える。
- 権限区分は、ユーザーに直接付ける。いくつかの権限区分をまとめたロールや、ユーザーのグループに権限区分を付ける仕組みはない。必要なら案件で作る。
- ほかのデータを選ぶ必要のある利用者は、参照検索と同じ宣言の、選ぶ対象のデータの検索も呼び出せる（AUZ-009）。選ぶ対象の検索の項目を見せたくない利用者がいる場合は、選ぶのに必要な項目だけを返す検索を別に作り、そちらから選ばせる。
- 画面の表示の切り替え（AUZ-004）は、画面ごとに指定した処理で判定する。ボタンは、指定し忘れると表示されたままになる。ナビゲーションのリンクは、指定した処理と、画面を開くときに実際に呼ぶ処理が違うと、リンクは出るのに開くとエラーになる。どちらもサーバーで弾かれるので（AUZ-001）、呼び出せない処理が実行されることはない。画面を足したり変えたりしたときは、指定した処理を見直す。
- どの画面や処理にどの権限区分が要るかを、ソースを読まずに知る手段はない。必要なら、案件で nijo.xml の宣言から一覧を用意する。

## 11.3 主なカスタマイズ方法

### 処理を追加する

- nijo.xml で、クエリモデルまたはコマンドのルート要素に、カスタム属性「機能公開レベル」を指定する。値は AUZ-007 の表のいずれかである。「権限で指定」のときは、カスタム属性「機能利用可能権限」に権限区分を指定する。
- 画面のボタンなど、処理を呼ぶ部品は、その処理を呼び出せるかどうかで表示を切り替える（11.4）。
- ほかのデータを参照する画面を足したときは、参照先のクエリモデルの宣言に、その画面の利用者の権限区分を足す（AUZ-009）。足し忘れると、画面でデータを選ぼうとしたときにサーバーで弾かれる。

### 権限区分を追加する

- nijo.xml の静的区分「権限区分」に値を追加して再生成する。
- その権限区分で使えるようにする処理の「機能利用可能権限」に、追加した値を足す。

### データ単位の権限を加える

- Entity Framework Core のグローバルクエリフィルターを使う。手書きの DbContext で、データモデルごとに生成されるモデル定義のメソッド（`OnModelCreating{データモデル名}`）を上書きし、ログインユーザーが見てよい行だけに絞る条件を付ける。
- 条件の中のログインユーザーの値は、DbContext のインスタンスのメンバーを通して参照する。モデルは最初の1回だけ組み立てられてキャッシュされるので、ローカル変数などで渡した値は、最初のユーザーの値に固定される。
- ログインユーザーは、DbContext でユーザー（従業員）とセッションを読んで特定する。そのため、DbContext を組み立てる途中（コンストラクタ）でログインユーザーを取得すると循環する。条件を評価するときに取得する。
- 同じ理由で、ユーザーやセッションに条件を付けると、ログインユーザーの特定とログインの処理の検索にも効いてしまう。
- 条件は、一覧の検索、参照検索、編集のための読み込みのすべてに効く。手書きの SQL と、MapToView のビュー（7.3）には効かないので、ビューの側でも絞る。すべての行を扱ってよい処理（ジョブなど）では、条件を外して検索する。
- 書き込みは絞られない。自分の部署以外の値を指定した新規登録などは、入力チェックで防ぐ。

## 11.4 開発者向け情報

- 権限に関わる処理は、次の場所から読み始める。
  - サーバー：`Core/ログイン・認証/`（名前空間は Authorization）の `処理の呼び出し可否.cs` に、判定の規則と、すべての処理が本体の前に通る関門がある。システム管理者をすべての権限区分を持つものとする規則は、同じフォルダの `LoginUser` にある。`WebApi/Authorization/` にあるのは認証（ログインユーザーの特定）の処理だけである。403 の応答は `WebApi/OperationEndpoints.cs` で返す。
  - 画面：`client/src/login/canInvoke.ts`（判定と、システム管理者の規則）、各画面の `navigationItem`（ナビゲーションのリンクと、その判定に使う処理）
  - 単体テスト：`UnitTest/Tests/処理の呼び出し可否.cs`（宣言の権限区分の数と、判定の規則）
- 処理の宣言は、nijo が生成する処理の一覧（サーバーの `Operation<OperationContext>.All` の各処理の `Metadata`、画面の `Operation.Metadata`）に入る。
