# 10. 検索

自動生成されるクエリモデルの検索処理の仕様を扱う。

サーバー側で発行されるSELECT文全般の話ではなく、一覧検索画面の検索処理が主な対象。（「主な」と書いたのは、クエリモデルの検索処理はExcel出力処理などに流用することもできるので、厳密には一覧検索画面だけに留まらないから）

## 10.2 限界

- キーを定義していないクエリモデルでは、並び順にキーを加えない（QRY-001）。並び順の値が同じ行の順番は決まらず、ページを切り替えたときに行が重複したり抜けたりすることがある。順番を一意にするには、クエリモデルにキーを定義する。
- クエリモデルの検索は、ページを切り替えるたびに全件数も数える（QRY-005）。件数と応答時間の関係は未計測。足りないときは MapToView で DB のビューから取得する（10.3）。
- 大文字と小文字、全角と半角などを区別するかは、DB の照合順序に従う。テンプレートの側でそろえる変換はしない。
- MapToView のビューの作成と保守は手で行う。マイグレーションでは作られない。
- データ単位での閲覧権限について、特別な仕組みは用意していない。追加したい場合は 14.3 の「データ単位の権限を加える」を参照。

## 10.3 開発者向け情報

### 検索処理の作り

クエリモデルの検索処理は、次の部品からなる。条件・並び順・件数・ページングは、DB 側の SQL に組み込まれ、1ページ分だけが読み込まれる。

| 部品 | SQL でいうと | 書くもの |
|---|---|---|
| 検索の元になるデータの定義（`CreateQuerySource`） | FROM 句と SELECT 句 | 手書き。データモデルから生成されたクエリモデルでは、生成されている |
| 絞り込み（`AppendWhereClause`） | WHERE 句 | 生成される。上書きできる |
| 並び替え（`AppendOrderByClause`） | ORDER BY 句 | 生成される。上書きできる |
| 件数の取得とページング | COUNT、OFFSET・LIMIT | 生成される |
| 読み込み後の処理（`OnAfterLoaded`） | なし（メモリー上） | 必要なら手書きで上書きする |
| 検索の前のチェック（`ValidateSearchCondition`） | なし | 必要なら手書きで上書きする |

- CreateQuerySource の処理は DB で実行される。JOIN・GROUP BY・UNION ALL などで算出した項目にも、生成された絞り込み・並び替え・件数・ページングがそのまま効く。
- そのクエリモデルに固有の、利用者に見せてよい行の制限は、 CreateQuerySource の中で行う。画面で隠したり、 OnAfterLoaded で除いたりすると、件数とページングが狂ううえ、API を直接呼ばれると見えてしまう。すべてのクエリモデルに共通の制限は 14.3 の方法による。
- OnAfterLoaded は、現在のページの行だけに対して動く。ここで設定した値では、絞り込みも並び替えもできず、件数にも反映されない。ここで行を除いてはならない。ページの中で完結する表示用の加工や、DB の外（外部システムなど）にしかない情報を付け加える処理に使う。外部の情報は、ページの中のキーをまとめて1回で取得する。
- 特定の条件が未入力のとき、または権限によって、検索そのものを実行させたくない場合は、 ValidateSearchCondition をオーバーライドする。
- 絞り込みや並び替えをオーバーライドして条件を足すときは、生成された処理（基底の実装）を呼ぶ。呼ばないと、生成された条件がすべて効かなくなる。
- 検索の処理の中では、ログの出力を除き、DB・外部システム・ファイルの更新をしない。
- 他のデータを参照する項目には Ref を使う（nijo.xml で ref-to:... を指定する）。参照先から読み込む項目は、参照に必要な最低限にとどめると、検索が重くなりにくい。

### DB のビューから取得する検索（MapToView）

複雑な集計・結合やチューニングが必要な検索は、nijo.xml の MapToView で、DB のビューから取得するようにする。このとき、検索の元になるデータの定義もビューを読む形で生成されるので、ビューを作る SQL だけを手で書く。

- ビューの名前・列名・キーは、生成された Entity Framework Core の設定に合わせる。子の配列のビューも含めて、すべて一致させる。キーがある場合は、ビューの結果でキーが一意になるように書く。一意でないと、行を取り違える。
- ビューはマイグレーションでは作られない。ビューを作る SQL は、マイグレーションの SQL と同じフォルダ（5.3）に、ビュー1つにつき1ファイル、`V{4桁の連番}_{ビュー名}.sql` という名前で置く。`V` で始めることで、数字で始まるテーブル定義の SQL より後に流れる。ほかのビューを参照するビューは、参照先より大きい連番にする。
- ファイルの先頭で既存のビューを消してから作り直す（`DROP VIEW IF EXISTS` の後に `CREATE VIEW`）。文字コードは BOM 付きの UTF-8 にする。
- SQL は使う DB の製品の方言で書く。開発環境と本番環境で DB の製品が違う場合は、両方で動くことを確かめる。
- 参照しているテーブルの構造が変わっても、ビューは自動では追随しない。nijo.xml を変えたら、ビューも直す。ビューとの食い違いはビルドでは見つからないので、すべての列で絞り込みと並び替えを実行して確かめる。
