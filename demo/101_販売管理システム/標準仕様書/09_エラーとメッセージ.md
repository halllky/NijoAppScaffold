# 9. エラーとメッセージ

業務処理や共通処理で起きるエラーの扱いと、メッセージの文言の管理を扱う。エラーの扱いには、運用担当者に知らせるかと、利用者にどう返すかの2つの軸があり、互いに独立している。

## 9.1 外部仕様

| ID | 仕様 | 確認方法 | 関連非機能要件 | 備考 |
|---|---|---|---|---|
| ERR-001 | 運用担当者が知るべきエラーは、例外として扱うか、ログに Error として出力する。運用担当者が知る必要のないエラーは、Error より低いレベルで出力するか、出力しない | 検査 | | Error を運用担当者への通知の対象にできるようにするため。例えば、一意制約違反は Error より低いレベルで出力する |
| ERR-002 | 画面から呼ばれた処理のエラーは、エラーの種類によらず、メッセージの構造体として画面に返す。画面はエラー画面に移らず、入力中の内容を残したままメッセージを表示する | 実演 | | エラー画面に移ると、利用者がそれまで入力した内容が失われるため。予期しない例外も、共通の処理がメッセージにして返す（API-004） |

## 9.2 主なエラーの扱い

テンプレートの共通処理では、主なエラーを次のように扱う。

| エラー | 運用担当者への知らせ（ERR-001） | 利用者への返し方（ERR-002） |
|---|---|---|
| 入力チェックの違反、業務ルールの違反 | 出力しない | メッセージ。項目に関するものは項目の近くに表示する（API-002） |
| 権限がない | Warning | メッセージ（AUZ-010） |
| 楽観排他、一意制約違反 | Warning | メッセージ（UPD-004） |
| 未ログイン | 出力しない | ログインのダイアログを表示する（SES-005） |
| DB の障害 | Error | 固定の文言のメッセージ。保存の共通処理が返す（11.4） |
| 外部システムの更新の失敗 | 例外（Error） | 固定の文言のメッセージ（EXT-001） |
| 予期しない例外 | 例外（Error） | 固定の文言のメッセージ（API-004、API-005） |
| 画面の読み込み中の例外 | サーバーで起きたものは Error | エラー画面（UI-004）に遷移 |

## 9.3 限界

- ダミーデータの作成処理と、運用担当者へのエラーの通知の文言は、テンプレート文字列に集めず、処理の中に直接書いている。利用者に見せるものではないため。

## 9.4 主なカスタマイズ方法

### 入力チェックや保存処理の共通部分の文言を変える

- 入力チェックや保存処理の共通部分が使う文言（必須、桁数、楽観排他、一意制約など）は、nijo.xml のテンプレート文字列のグループ `MSG` に定義している。文言を変えるには、ここを書き換えて再生成する。
- 自動生成されたコードは文言を持たない。文言が要る箇所では DbContext のメソッドを呼び、手書きの DbContext がそのメソッドの中で `MSG` の文言を返す。

### メッセージを追加する

- 利用者に見せるメッセージ（エラー、確認、完了の知らせ、通知の本文、ジョブの結果）は、nijo.xml のテンプレート文字列（Templates）に定義する。値を埋め込む位置は、引数として文言の中に書く。値を埋め込まない文言も、メッセージの一覧を一か所にまとめるため、引数の無いテンプレート文字列として同じ場所に定義する。
- 業務ごとのメッセージは、`MSG` とは別のグループにまとめる（デモ101 の販売管理なら `MSG_DEMO101`）。業務を削除するときに、グループごと削除できるようにするため。
- 各処理では、文言を直接書かず、生成されたテンプレート文字列を参照する。
- テンプレート文字列の各要素の名前が、そのままメッセージの ID になる。nijo.xml のテンプレート文字列の一覧が、メッセージの一覧を兼ねる。

## 9.5 開発者向け情報

- 入力チェックや保存処理の共通部分が使う文言（必須、桁数、楽観排他、一意制約など）は、nijo.xml のテンプレート文字列のグループ `MSG` にまとまっている。変え方は 9.4。
- 利用者に見せるメッセージは、処理の中に直接書かず、テンプレート文字列に定義して呼ぶ（9.4）。
- 業務処理で、エラーをメッセージで返すか例外を投げるかは、そのエラーに最初に対処するのが誰かで決める。想定内かどうか、業務上起こりうるかどうかでは決めない。
  - 利用者が画面で対処できるもの（入力の誤り、権限のない操作、ほかの人の更新との競合、業務上の前提を満たさない操作など）は、メッセージで返して処理を終える。
  - 利用者には対処できず、運用担当者がログを見て対処するもの（外部システムの障害、設定の欠落、あるはずのマスタのデータがない、データの不整合、バグなど）は、例外を投げる（ERR-001）。利用者には「管理者に連絡してください」と伝えるしかないものは、例外にする。
  - 例外を捕まえて利用者向けのメッセージに変えない。運用担当者に届くべき情報が消える。例外のメッセージには、運用担当者が原因と対象を特定できる情報（処理の名前、キー、外部システムの名前など）を含める。
- メッセージは、できるだけ具体的な位置（項目、明細の何行目の項目など）に付ける。どの項目にも属さないものだけを、全体のメッセージにする。独立して確かめられるものは、最初のエラーで打ち切らずにすべて確かめてから終える。後の確認が前提を失う場合（キーが空など）だけ、その場で打ち切る。
