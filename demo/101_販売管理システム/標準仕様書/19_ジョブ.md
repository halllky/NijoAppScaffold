# 19. ジョブ

画面からの呼び出しとは別に、サーバーのプロセス内で後から実行する処理をジョブと呼ぶ。日次処理などの定期実行する処理と、画面から起動する時間のかかる処理に使う。画面から起動したジョブの終了は、通知（18章）で知らせる。

ジョブを使わない案件では、この機能を削除する（19.3 の「ジョブを使わない場合」）。

## 19.2 限界

- WebApi のプロセスが停止している間は、定期実行のジョブも動かない。アイドル時にプロセスを停止するホスティング環境では使えない。
- 曜日や月末などを指定する複雑なスケジュールには対応していない。
- ジョブの中断操作、進捗の表示、自動での再実行の機能はない。異常終了したジョブは、利用者か運用担当者が起動し直す。
- ジョブ一覧画面は自動では更新されない。ジョブが終了したかどうかは、再検索するか通知で確認する。
- 待機中のジョブの有無と定期実行の予定時刻は、5秒おきに DB をポーリングして確認する。そのため、ジョブは登録されてから開始するまでに最大5秒かかる。定期実行のジョブも、予定時刻から最大5秒遅れて登録される。
- 1回の処理の中で複数のジョブを登録すると、それらの開始順は保証されない。現在時刻は1回の処理の中で固定されるので、登録日時が同じになるため。
- ジョブの引数は登録時点の形式で保存される。待機中のジョブが残っている状態で、引数の型を変えたプログラムをリリースすると、そのジョブは引数を読み込めずに異常終了する。ジョブの種類を削除したプログラムをリリースした場合も、その種類の待機中のジョブは異常終了する。
- サーバーが複数台の場合
  - 作業フォルダはジョブを実行したサーバーにしかないので、スプールのダウンロードのリクエストはそのサーバーで受ける必要がある。ほかのサーバーが受けると、ファイルが無いものとして扱う。一覧にも、そのサーバーで実行したジョブのファイルだけが表示される。
  - 定期実行のジョブはサーバーの台数分登録されるので、1台だけが登録するように改修する必要がある。
  - 起動時に異常終了にするのは、自身と同じサーバー名（マシン名）で実行中だったジョブだけである。サーバー名が変わると、そのジョブは実行中のまま残る。
  - クリーンナップが削除する作業フォルダは、クリーンナップを実行したサーバーのものだけである。

## 19.3 主なカスタマイズ方法

### ジョブを追加する

- アプリケーションサービスに、ジョブの種類のインスタンスを static フィールドとして定義する。コンストラクタには、種類の名前とジョブの本体のメソッドを渡す。種類の名前は重複してはいけない。
- 定義した種類は自動で収集されるので、一覧などに登録する必要はない。業務のフォルダを削除すれば、その業務のジョブも消える。
- 本体のメソッドは、正常終了なら何も返さず、異常終了なら例外を投げる。
- 利用者向けの結果のメッセージは、本体が引数で受け取るオブジェクト（実行中のジョブ）に設定する。例外を投げる前に設定しておけば、異常終了の場合もそのメッセージを表示する。
- 本体は、サーバーの停止時にキャンセルされる CancellationToken を受け取る。時間のかかる処理では、キャンセルされたらなるべく早く処理を打ち切る（JOB-005）。
- 引数が必要なら、引数の型を指定したジョブの種類を使う。引数は JSON にシリアライズして保存するので、単純な値だけをもつ型にする（19.2）。
- 画面から起動する場合は、トランザクションの中でジョブを登録するコマンドを作る。見本はデモ101の商品データ取込にある。

### 定期実行する

- ジョブの種類に予定（毎日決まった時刻、または一定の間隔）を指定する。引数をとる種類には指定できない。
- 定期実行のジョブはログインユーザーのいない処理として実行されるので、権限の確認（AUZ-001）があるコマンドは呼べない。コマンドを経由せず、処理の本体のメソッドを直接呼ぶ。クリーンナップのジョブがその例である。

### 他のジョブ実行基盤を使いたい場合

ジョブのスケジュール（JOB-006）で足りない場合や、外部のスケジューラから起動したい場合は、別途作る必要がある。

業務ロジックは、極力、アプリケーションサービスを呼び出すこと（4.2）。ログには、ジョブと同じく処理名と処理1回分の識別子を付ける（LOG-003）。

### ジョブを使わない場合

次のものを削除する。

- nijo.xml のデータモデル「ジョブ」、クエリモデル「ジョブ一覧」、静的区分「ジョブの状態」と、テンプレート文字列 画面のURL の「ジョブ」。削除したら再生成する。
- Core のジョブのフォルダと、ジョブの単体テスト。
- 設定クラスのジョブの設定と、設定ファイルのジョブのセクション。
- DI の設定にあるジョブキューの登録。
- WebApi の、ジョブを実行するバックグラウンドサービスと、スプールのファイルをダウンロードするエンドポイント、およびそれらの登録。
- ジョブ一覧画面（P004）のファイル。ナビゲーションの項目もこれで消える。
- クリーンナップの中の、ジョブを削除する呼び出しと、クリーンナップのジョブの定義。
- ジョブのテーブルを削除するマイグレーションを追加する。

ジョブを登録する処理（デモ101の商品データ取込など）や、ジョブの終了の通知（JOB-010）を使っていれば、それも外す。

## 19.4 開発者向け情報

- ジョブは1つのテーブルで管理する。ジョブの登録とは、このテーブルに待機中の行を1行追加することである。登録日時には、全データモデル共通の作成日時の列（UPD-001）を使う。
- ジョブの登録は、業務処理のトランザクションの中で行う。業務データと一緒に確定させるためで、トランザクションの外で登録すると例外になる。
- 登録時にログインユーザーがいれば画面から起動したジョブとみなし、そのユーザーを起動したユーザーとして記録する。いなければ定期実行のジョブとして扱う。起動したユーザーは従業員番号の文字列で記録し、従業員を ref-to で参照しない。ジョブの記録が残っているユーザーも削除できるようにするため。
- WebApi のプロセス内で常駐するバックグラウンドサービス（ASP.NET Core のホステッドサービス）が、待機中のジョブを登録順に取り出し、ジョブの種類に対応するアプリケーションサービスのメソッドを呼ぶ。設定した同時実行数の分だけ、このループを並行して動かす（JOB-002）。
- DB に接続できないなどでループ内の処理が連続して失敗している間は、最初の1回だけ Error レベルでログを出力する。DB の障害中に、同じエラーのログがポーリングのたびに出力され続けるのを防ぐため。
- ジョブの取り出し・本体の実行・結果の記録は、それぞれ別の DI スコープで行う。理由は次の2つ。
  - 本体が失敗しても、結果の記録に影響しないようにするため。
  - 現在時刻はスコープ内で固定される（4.2）ので、開始日時と終了日時をそれぞれの時点の時刻にするため。
- ジョブを取り出すときは、状態を実行中に更新して楽観排他（UPD-004）で保存する。ほかのスレッドやサーバーが先に取り出していれば保存に失敗するので、そのジョブは実行せずに次の待機中のジョブを探す（JOB-004）。
- ジョブの処理では、セッションの代わりにジョブの記録からログインユーザーを決める。画面から起動したジョブは起動したユーザーをログインユーザーとし、定期実行のジョブや、起動したユーザーが削除済みの場合はログインユーザーなしとする。作成者・更新者には、ログインユーザーがいればそのユーザーを、いなければジョブの種類を記録する（UPD-002）。
- ジョブには確認メッセージを見せる利用者がいないので、本体から呼んだ業務処理の確認メッセージは無視され、確認なしで処理が続く（12.4 の「確認メッセージ」）。
- ジョブの取り出しから結果の記録までの間、ログに処理名とジョブ ID を付ける（JOB-011）。
- サーバーの停止は、ジョブの本体に CancellationToken で伝える。終了を待つ時間は、ホストのシャットダウンのタイムアウトとして設定する（JOB-005）。
- 定期実行の予定は、スケジューラのライブラリを使わず、ソースコード上で「毎日決まった時刻」か「一定の間隔」で定義する。バックグラウンドサービスがポーリングのたびに予定時刻を過ぎたかを確認し、過ぎていればジョブを登録する。前回の確認日時はプロセスのメモリ上にだけ保持し、起動後の初回の確認では何も登録しないので、停止中に過ぎた予定は実行されない（JOB-007）。
- 作業フォルダは、設定した場所の下にジョブ ID ごとに作る。スプールは作業フォルダ内の決まったフォルダである。どちらも本体を呼ぶ前に作成する。
- スプールのファイルは DB に保存していないので、ジョブ一覧では、表示中のページのジョブについてだけサーバーのフォルダからファイル名を取得する。ファイル名では絞り込めない。
- ダウンロードの API は、一覧と同じ絞り込みで権限を確認する（JOB-009）。".." やパスの区切り文字を含むファイル名は受け付けないので、スプールの外のファイルは指定できない。
- 画面から起動したジョブの終了の通知は、結果の記録と同じトランザクションで作る（JOB-010）。
