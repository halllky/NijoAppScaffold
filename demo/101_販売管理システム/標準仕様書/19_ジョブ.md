# 19. ジョブ

画面からの呼び出しとは別に、サーバーのプロセスの中で後から実行する処理を、ジョブと呼ぶ。日次処理などの定期的な処理と、画面から起動する時間のかかる処理に使う。画面から起動したジョブの終了は、通知（18章）で知らせる。ほかの業務処理から使われる機能で、使わない案件は取り外す（19.3 の「ジョブを使わない場合」）。

## 19.2 限界

- WebApi のプロセスが止まっている間は、定期的なジョブも動かない。アイドル時にプロセスを止める環境では動かない。
- 曜日・月末などを指定する複雑なスケジュールはない。
- ジョブの中断の操作、進捗の表示、自動の再実行はない。異常終了したジョブは、利用者か運用担当者が起動し直す。
- ジョブの一覧は、ジョブの状態が変わっても自動では表示し直さない。終わったかどうかは、検索し直すか、通知で確かめる。
- 待機中のジョブがあるかどうかは、数秒おきに DB に問い合わせて確かめる。そのため、登録してから開始するまで、また予定の時刻から登録するまで、最大でその間隔だけ遅れる。
- 同じ処理の中で登録したジョブ同士は登録の日時が同じになるので、その間で開始する順は決まらない。
- ジョブの引数は、登録した時点の形で保存される。待機中のジョブがある状態で、引数の形を変えたプログラムに入れ替えると、そのジョブは引数を読めずに異常終了する。ジョブの種類を削除したプログラムに入れ替えた場合も、その種類の待機中のジョブは異常終了する。
- サーバーが複数台のとき
  - 作業フォルダはジョブを実行した台にあるので、スプールのダウンロードはその台で受ける必要がある。ほかの台で受けると、ファイルが無いものとして扱う。一覧にも、その台で実行したジョブのファイルだけが載る。
  - 定期的なジョブは台数分登録されるので、1台だけが登録するよう手を加える。
  - 中断として異常終了にするのは、起動したサーバーと同じ名前のサーバーで実行中だったジョブだけである。台の名前が変わると、実行中のまま残る。
  - クリーンナップが削除する作業フォルダは、クリーンナップを実行した台のものだけである。ほかの台の作業フォルダは、その台でクリーンナップを実行したときに削除される。

## 19.3 主なカスタマイズ方法

### ジョブを追加する

- アプリケーションサービスに、ジョブの種類を static のフィールドとして定義する。種類の名前と、ジョブの本体のメソッドを渡す。種類の名前は重複できない。種類は自動で集められるので、どこかに列挙する必要はない。業務のフォルダを削除すれば、その業務のジョブも消える。
- 本体のメソッドは、正常終了なら何も返さず、異常終了なら例外を投げる。利用者に見せる結果は、本体に渡される実行中のジョブの情報に設定する。例外を投げる前に設定しておけば、異常終了のときもそれを表示する。
- 本体は、サーバーの停止の合図を受け取る。時間のかかる処理では、合図があったらなるべく早く打ち切る（JOB-005）。
- 引数が必要なら、引数の型を指定した種類を使う。引数は JSON にして保存するので、単純な値だけをもつ型にする（19.2）。
- 画面から起動するには、ジョブを登録するコマンドを作る。コマンドは、トランザクションの中でジョブを登録して、応答を返す。見本は、デモ101の参考実装の「ジョブ」を参照。

### 定期的に実行する

- ジョブの種類に、予定（毎日決まった時刻、または一定の間隔）を指定する。引数をとる種類には指定できない。
- 定期的なジョブは、ログインユーザーのいない処理として実行する。画面から呼び出すための権限の確認（AUZ-001）を通らないよう、コマンドではなく処理の本体を直接呼ぶ。クリーンナップのジョブがその例である。

### 他のジョブ実行基盤を使いたい場合

ジョブのスケジュール（JOB-006）で足りない場合や、外部のスケジューラから起動したい場合は、別途作る必要がある。

業務ロジックは、極力、アプリケーションサービスを呼び出すこと（4.2）。ログには、ジョブと同じく処理名と処理1回分の識別子を付ける（LOG-003）。

### ジョブを使わない場合

次のものを削除する。ジョブの機能の外から参照しているのは、クリーンナップの処理だけである。

- nijo.xml のデータ構造「ジョブ」「ジョブ一覧」と、静的区分「ジョブの状態」、定数「画面のURL」の「ジョブ」。削除したら再生成する。
- Core のジョブのフォルダと、ジョブの単体テスト。
- 設定のクラスのジョブの設定と、設定ファイルのジョブの区画。
- DI の設定の中の、ジョブの列の登録。
- WebApi の、ジョブを実行するサービスとその登録、スプールのダウンロードとその登録。
- 画面の P004 ジョブのファイル。ナビゲーションの項目も、これで消える。
- クリーンナップの処理の中の、ジョブを削除する呼び出しと、クリーンナップのジョブの定義。
- ジョブのテーブルを削除するマイグレーションを追加する。

ジョブを登録する処理（デモ101の商品データ取込など）があれば、それも外す。

## 19.4 開発者向け情報

- ジョブは1つのテーブルに、種類・引数（JSON）・状態・起動したユーザー・開始と終了の日時・実行したサーバー・結果のメッセージをもつ。登録の日時には、すべてのデータモデルにある作成日時の列（UPD-001）を使う。ジョブの登録は、このテーブルに待機中の行を1つ追加することである。業務処理のトランザクションの中で登録すれば、業務データと一緒に確定する。トランザクションの外で登録すると例外になる。
- 起動したユーザーは、登録したときのログインユーザーである。ログインユーザーがいれば画面から起動したジョブ、いなければ定期的なジョブとして扱う。起動したユーザーは従業員番号の文字列で持ち、ユーザーへの外部参照にしない。ジョブの記録が残っているユーザーも削除できるようにするため。
- WebApi のプロセスの中で常に動くサービス（ASP.NET Core のホステッドサービス）が、待機中のジョブを登録の順に取り出して、ジョブの種類に対応するアプリケーションサービスのメソッドを呼ぶ。設定で決めた数だけ、取り出して実行する繰り返しを並行して動かす（JOB-002）。DB に接続できないなどで繰り返しの処理が失敗し続けている間は、最初の1回だけを Error としてログに出力する。
- 取り出し・本体の実行・結果の記録は、それぞれ別の DI スコープで行う。本体の失敗が結果の記録に影響しないようにするためと、開始と終了の日時をそれぞれの時点の時刻にするため（現在時刻は1つのスコープの中で同じ値を返す。4.2）。オペレーションコンテキストは本体が業務処理を呼ぶときに作るので、確認メッセージは無視される（12.4 の「確認メッセージ」）。
- 取り出すときは、状態を実行中に変えて楽観排他（UPD-004）で保存する。他のスレッドや他の台が先に取り出していれば保存に失敗するので、そのジョブは実行せず、次の待機中のジョブを探す（JOB-004）。
- ジョブの各スコープでは、セッションの代わりにジョブの情報からログインユーザーを決める。画面から起動したジョブは起動したユーザーを、定期的なジョブはログインユーザーなしとする。作成者・更新者にはログインユーザーを、いなければジョブの種類を記録する（UPD-002）。起動したユーザーが削除されていれば、ログインユーザーなしとする。
- ログの処理名・識別子（JOB-011）は、ジョブを取り出してから結果を記録するまでの間、ログの付加情報として付ける。
- サーバーの停止を、ジョブのメソッドに取り消しの合図（CancellationToken）として渡す。終わるのを待つ時間は、ホストの停止の待ち時間として設定する（JOB-005）。
- 定期的なジョブの予定は、スケジュールのライブラリを使わずに、ソースに「毎日決まった時刻」か「一定の間隔」で定義する。サービスが一定の周期で予定の時刻を過ぎたかを確認し、過ぎていればジョブを登録する。前回確認した時刻はプロセスのメモリーにだけ持ち、起動した後の最初の確認では何も登録しないので、止まっている間の予定は実行されない（JOB-007）。台ごとに確認するので、複数台では台数分登録される。
- 作業フォルダは、設定で決めた場所の下に、ジョブの識別子ごとに作る。スプールは作業フォルダの中の決まったフォルダである。どちらも本体を呼ぶ前に作る。
- ジョブの一覧は、スプールのファイルの名前を、表示するページのジョブについてだけサーバーのフォルダから読む。DB に無いので、ファイルの名前では絞り込めない。
- ダウンロードの API は、起動したユーザーかシステム管理者かを、一覧と共通の絞り込みで確認してから返す（JOB-009）。ファイルの名前にフォルダの区切りなどを含めて、スプールの外のファイルを指定することはできない。
- ジョブが終わったら、画面から起動したジョブなら、結果の記録と同じトランザクションで通知を作る（JOB-010）。
- クリーンナップは、保存期間を過ぎたジョブの記録を削除した後、作業フォルダのうち記録が無くなったジョブのものを削除する（JOB-013）。
