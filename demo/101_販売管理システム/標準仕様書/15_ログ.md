# 15. ログ

アプリケーションが出力するログについて、出力先とレベル、1行の項目、ログファイルの置き場所と保存期間、マスキングを扱う。認証や権限のように、ほかの章が扱う出来事のログは、その章にある。それらは表「補足：ほかの章にあるログの仕様」から辿れる。

## 15.1 外部仕様

| ID | 仕様 | 確認方法 | 関連非機能要件 | 備考 |
|---|---|---|---|---|
| LOG-001 | ログを、サーバーのコンソール（標準出力）とログファイルに出力する。コンソールには、すべてのログを出力する。ログファイルには、ロガー名が `Microsoft.AspNetCore.` か `Microsoft.EntityFrameworkCore.` で始まるログ（ASP.NET Core と Entity Framework Core のログ）は Warning 以上だけを、それ以外のログはすべてのレベルを出力する。本番環境でも開発環境でも同じである。設定ファイルの `Logging` セクション（ASP.NET Core が標準で読むログのレベルの設定）は効かない | 実演 | 運用・保守性 | |
| LOG-002 | ログファイルの1行は、表「LOG-002 ログファイルの項目」の項目を、この順にタブで区切ったものである。文字コードは UTF-8 である。本文や例外が改行を含むときは、1件のログが複数の行にわたる。コンソールの1行は、日時・レベル・ロガー名・本文と例外を「\|」で区切ったもので、ログインユーザー ID・処理名・処理1回分の識別子は出ない。コンソールの日時には、タイムゾーンのオフセットが付かない | 実演 | 運用・保守性 | 日時にオフセットを付けるのは、サーバーの OS のタイムゾーンが業務のタイムゾーン（ENV-004）と違っても、データの日時と突き合わせられるようにするため |
| LOG-003 | HTTP のリクエストでは、処理名は URL のパス（例：`/api/x7cda55dc0744dd2c61802153d4af8aed/execute`）で、処理1回分の識別子はリクエストごとに振る。ログインユーザー ID は、リクエストを受けた時点のログインユーザーである | 検査 | 運用・保守性 | 識別子は、予期しない例外のときに画面に表示する問い合わせ番号と同じ値である（API-005）。ジョブの場合は JOB-011 |
| LOG-004 | カスタム属性「マスキング」を付けた項目（パスワードなど）は、オブジェクトを JSON にしてログに出力するとき（LOG-009 の引数など）に、値を `***` に置き換える。本文の文章に直接埋め込んだ値と、保存したデータのキー（LOG-009）は、マスキングされない | 実演 | セキュリティ | どの項目に付けるかは nijo.xml で指定する。マスキングを付けても、キーなら値が出る。例：セッションキーのハッシュ値（SES-001）。本文に埋め込まれて出る例：ログインのログの、入力されたユーザー ID（AUTH-011） |
| LOG-006 | ログファイルは、ログのフォルダにある拡張子 `.log` のファイルを、更新日時の新しいほうから30個（当日分を含めて最大31個）残し、それより古いものを自動で削除する。ログファイルではない `.log` のファイル（`NLog.Fatal.log` など）も、数に入れて削除する。ログファイルの大きさには上限がない | 実演 | 運用・保守性 | 日数ではなくファイルの数で数えるので、ログを出力しなかった日（サーバーを止めていた日など）があると、30日より前のファイルも残る |
| LOG-007 | HTTP のリクエストごとに、処理が終わったときに、メソッド・パス・処理時間・応答の状態コードを Info でログに出力する（例：`POST /api/…/execute 完了: 70ms, Status: 422`）。要求と応答の本文、クエリ文字列、接続元の IP アドレス、User-Agent などのヘッダーは出力しない。死活の確認（OPS-001）と、画面の JavaScript や CSS などの静的なファイルの配信は対象外である。画面の URL を開いたときにサーバーが返す HTML は対象である | 検査 | 運用・保守性 | 本番環境で「遅い」「エラーになった」という問い合わせを調べるため。処理の引数は LOG-009 |
| LOG-008 | 起動の途中で例外が起きてサーバーが止まるときは、その例外を Fatal でログに出力してから止まる。ただし、ログの設定が終わる前（設定ファイルの読み込みと検証など）に起きた例外は、ログには出力されず、標準エラー出力にだけ出る | 実演 | 運用・保守性 | 起動しない理由を、ログファイルで調べられるようにするため。設定の誤り（CFG-004）は、標準エラー出力にだけ出る |
| LOG-009 | 自動生成の処理（検索と更新）を HTTP で呼び出したときは、受け取った引数を Debug でログに出力する。Entity Framework Core が Info 以上で出力する出来事（実行した SQL、DB のエラーなど）は、ロガー名 `MyApp.OverridedDbContext` の Debug のログとして出力し直す。データを保存したときは、データ構造の名前、操作（新規登録・更新・削除）、キーを Info でログに出力する | 実演 | セキュリティ | 出力し直したログは、LOG-001 の「それ以外のログ」に当たるので、本番環境でもログファイルに残る。元の Entity Framework Core のログは Warning 以上だけがファイルに残るので、DB のエラーは、ファイルに Warning と Debug の2回出る。SQL のパラメーターの値は出ない。引数のログは、引数を読み取れなかったときと、手書きの API・添付ファイルの API では出ない。ログファイルには、利用者が入力した業務のデータ（個人情報を含むことがある）が残る |
| LOG-010 | ログファイルは、サーバーごとに、そのサーバーのフォルダに出力する。フォルダは設定ファイルの `LogDirectory` で指定し、設定ファイルの初期値は `../WebApi.Log` である。相対パスは、設定ファイルのあるフォルダからの相対パスになる。ファイルは日ごとに分け、ファイル名はサーバーの OS のタイムゾーンでの日付にする（例：`2026-11-21.log`）。NLog 自身の重大なエラーは、同じフォルダの `NLog.Fatal.log` に書く。ログファイルに書き込めないとき（ディスクの空きがないなど）は、そのログは失われ、書き込めなかったことも記録されない。ファイルのアクセス権は、テンプレートでは設定しない | 実演 | 運用・保守性 | アクセス権は、ログのフォルダに対して案件で設定する |

### LOG-002 ログファイルの項目

| 項目 | 内容 |
|---|---|
| 日時 | サーバーの OS のタイムゾーンの時刻に、そのオフセットを付けたもの（例：`2026-11-21 08:29:44.5829+09:00`） |
| レベル | TRACE、DEBUG、INFO、WARN、ERROR、FATAL のいずれか。この文書では、それぞれ Trace、Debug、Info、Warning、Error、Fatal と書く |
| ログインユーザー ID | ログを出力した処理のログインユーザーのユーザー ID（従業員番号）。HTTP のリクエストでは LOG-003 による。ジョブでは起動したユーザーで、定期実行のジョブでは空 |
| 処理名 | LOG-003、JOB-011 による。どの処理にも属さないログ（起動と停止、ジョブの待ち受けなど）では空 |
| 処理1回分の識別子 | 処理名と同じ |
| ロガー名 | ログを出力した部品の名前。業務処理のログ（AUTH-011、LOG-007、API-004 など）は、どの処理のものでも `MyApp.AutoGeneratedApplicationService` になる。起動のログはアプリケーションの名前（デモ101では `Demo101.WebApi`）、LOG-008 のログは `Program` になる |
| 本文 | ログの本文 |
| 例外 | ログに付けた例外の種類、メッセージ、スタックトレース。例外がなければ空 |

### 補足：ほかの章にあるログの仕様

| ログ | 仕様 |
|---|---|
| レベルの使い分け（保存の失敗を含む） | ERR-001 |
| 予期しない例外 | API-004、API-005 |
| ログイン・ログアウト・パスワードの変更と初期化、ログインの一時ロック | AUTH-010、AUTH-011 |
| ログインでセッションを保存したとき | SES-001 |
| 権限のない処理の呼び出し | AUZ-010 |
| 外部システムの実装の設定がなく起動を止めたとき | EXT-003 |
| 本番環境で外部システムのモックを使っているとき | EXT-004 |
| DB に適用されていないマイグレーションがあるとき | MIG-001 |
| ジョブの処理名と識別子、ジョブの異常終了 | JOB-011、JOB-012 |
| エラーの通知のメール | ALR-001、ALR-007、ALR-008 |

## 15.2 限界

- サーバーが複数台のときは、ログが台ごとに分かれる（LOG-010）。まとめて調べる必要があれば、ログの集約を案件で行う。
- 処理1回分の識別子は短いので、一意とは限らない（API-005）。ログを探すときは、日時と合わせて探す。
- 処理名（自動生成の処理では英数字の識別子）とロガー名からは、どの処理のログかが分からない（LOG-002、LOG-003）。処理の日本語の名前との対応は、開発者がソースで調べる。
- コンテナなどでコンソールの出力だけを集めると、問い合わせ番号からログを探せない（LOG-002）。ログファイルも集めるか、コンソールの出力の形式をログファイルと同じ項目に変える（15.3）。
- ASP.NET Core と Entity Framework Core の Warning より低いログが本番環境で必要なときは、サーバーの起動の方法（サービス、コンテナなど）に合わせてコンソールの出力を受け取る。
- サービスとして動かすときは、標準エラー出力にだけ出る起動の失敗の理由（LOG-008）を受け取る手段を、案件で用意する。用意しないと、起動しない理由を調べられない。
- 出力するレベルや出力先、残すファイルの数を変えるには、プログラムを改修する（15.3）。
- ログファイルの大きさに上限はなく（LOG-006）、ディスクの空きは死活の確認でも確かめない（OPS-001）。ディスクの空きの監視は案件で行う。
- Error 以上はメールで知らせるが（ALR-001）、Warning 以下を知らせる仕組みはない。Warning で出力する出来事（権限のない処理の呼び出し、エラーの通知のメールを送れなかったこと（ALR-008）など）に気付くには、ログを定期的に調べる手順を案件で用意する。

## 15.3 主なカスタマイズ方法

### 出力先・レベル・形式・保存期間を変える

- ログの設定は `Core/Logging.cs` にまとめている。出力先ごとのレベル（LOG-001）、ログファイルとコンソールの項目（LOG-002）、残すファイルの数（LOG-006）は、ここで変える。
- SQL などのログ（LOG-009）が要らない場合は、DbContext（`OverridedDbContext`）で Entity Framework Core のログを Debug で出力し直す設定を外す。

## 15.4 開発者向け情報

- オブジェクトをログに出力するときは、アプリケーションサービスの `SerializeForLog` で JSON にする。マスキング（LOG-004）は、これを通したときだけ効く。
