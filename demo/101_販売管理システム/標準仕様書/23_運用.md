# 23. 運用

本番環境で運用するときに知っておくべきことを扱う。エラーの通知のメールは、テンプレートのままでは送られない（ALR-006）。本番で使うには、案件でメールの送信を実装する（23.7）。

## 23.1 外部仕様：リリースと配置

| DPL-002 | サーバーは、.NET の実行環境（ASP.NET Core）が入った環境で動かす。リリース用のモジュールに .NET の実行環境は含めない | 検査 | システム環境・エコロジー |  |
| DPL-003 | リリース用のモジュールには設定ファイルを含めない。設定ファイルは、リリース先の環境に置いたものを使う | 検査 | セキュリティ | 環境ごとに DB の接続先などが異なるため |

## 23.3 外部仕様：エラーの通知

| ID | 仕様 | 確認方法 | 関連非機能要件 | 備考 |
|---|---|---|---|---|
| ALR-001 | Error 以上のログを、運用担当者にメールで知らせる | テスト | 運用・保守性 | ERR-001 |
| ALR-002 | メールは既定の宛先に送る。ログを出力するときに宛先の区分を付けた場合は、その区分の宛先にも送る。宛先の区分と宛先は設定で決める。既定の宛先が1件もなければ、起動を止める（CFG-004） | テスト | 運用・保守性 | 誰にも届かない状態で運用するのを防ぐため。例えば、ある外部システムとの連携で起きたエラーのログに、その外部システムの担当者の区分を付ける |
| ALR-003 | サーバーでは、宛先の区分ごとに、短い時間に送るメールの数を抑える。直前の一定時間に1通も送っていなければ、すぐに送る。その一定時間に出力された Error 以上のログは貯めておき、時間が経ったときに1通にまとめて送る。まとめた1通には、件数の合計と、最初の数件の内容を載せる | テスト | 運用・保守性 | DB に接続できないときのような横断的なエラーで、大量のメールが届くのを防ぐため。一定時間は設定で決める |
| ALR-004 | サーバーの外で動かす処理（テンプレートでは、マイグレーションの手順で使う管理用のコマンドだけ）では、メールの数を抑えず、Error 以上のログをすぐに送る | テスト | 運用・保守性 |  |
| ALR-005 | メールの送信は、実機とモックを設定で切り替える。設定を省略したときは起動を止める（EXT-003） | 検査 | 運用・保守性 | 開発中に誤ってメールを送るのを防ぐため。モックは、宛先・件名・本文を書いたテキストファイルを、1通につき1つ作る |
| ALR-006 | 実機の送信は実装していない。設定で実機を選ぶと、アプリケーションは起動しない | 実演 | 運用・保守性 | 送信の方法（ライブラリ、メールサーバー）は案件で決める。実機を選んだまま、気付かずにメールが届かない状態で運用するのを防ぐため |
| ALR-007 | メールの本文には、ログの日時・レベル・ロガー名・ログインユーザー ID・処理名・処理1回分の識別子・本文・例外を載せる | 検査 | 運用・保守性 | ログのマスキング（LOG-004）は、メールにも適用される |
| ALR-008 | メールの送信は、業務処理のトランザクションに参加しない。送信に失敗しても業務処理には影響せず、失敗は Warning としてログに出力する | 検査 | 運用・保守性 | Error として出力すると、それがまたメールの対象になるため |

ALR-003 の例：一定時間を10分とする。10時から10時30分まで DB に接続できない状態が続くと、メールは10時（最初のエラー）と、10時10分・10時20分・10時30分（直前の10分間のまとめ）の4通になる。10時30分に復旧してエラーが止まると、10時40分に抑止が終わる。11時に再発したときは、最初のエラーをすぐに送る。

## 23.4 補足：バックアップの対象

テンプレートで、バックアップの対象になるのは次のものである。どれを、どの頻度でバックアップするかは案件で決める。

- DB
- 添付ファイルの保存先（FIL-004）。参照なしのファイルを削除するまでの期間は、DB のバックアップを残す期間より長くする（19.2）
- リリース先の環境に置いた設定ファイル（DPL-003）
- ログのフォルダ（LOG-010）。ログファイルは自動で削除されるので（LOG-006）、残すならフォルダの外へ移す

## 23.5 補足：サーバーを複数台にするとき

サーバーを複数台にするときは、次の箇所を確認する。

- DB とセッション：SES-007
- ログ：LOG-010
- ログインの失敗の回数：AUTH-012
- ジョブ：JOB-002、JOB-004、JOB-009、18.2
- 添付ファイル：FIL-004、19.2
- エラーの通知：ALR-003

## 23.6 限界

- 本番の DB へのマイグレーションの適用は、リリースの手順に含まれない（5.2）。
- リリースのためにサーバーを止めると、ジョブに影響する。実行中のジョブはキャンセルされ（JOB-005）、止めている間に予定時刻を過ぎた定期実行のジョブは実行されない（JOB-007）。待機中のジョブがあるときの注意は 18.2。
- エラーの通知について
  - ログを出力するときに宛先の区分を付けなかったエラーは、既定の宛先にだけ送る。業務処理で例外を捕まえず、サーバーの共通の処理でログに出力された例外もこれに当たる。
  - まだ送っていないメール（ALR-003 で貯めているもの）は、サーバーのプロセスが止まるときに送る。プロセスが異常終了したときは失われる。
  - 送信に失敗したメールは、送り直さない。
  - サーバーの外で動かす処理で1件ごとに Error のログを出力すると、件数分のメールが届く（ALR-004）。
  - 送る数を抑える処理（ALR-003）はサーバーごとに行うので、サーバーが複数台のときは、横断的なエラーで台数分のメールが届く。

## 23.7 主なカスタマイズ方法

### エラーの通知の実機を実装する

- メールを送る部品のインターフェース（`IErrorMailSender`）を実装したクラスを作り、設定で実機を選んだときに使う。エラーの通知を作る処理で起動を止めている部分（ALR-006）を、この実装に置き換える。
- 実機の送信は、送るスレッドから呼ばれる。送信に時間がかかっても業務処理は待たされないが、次のメールの送信は遅れる。
- サーバーが止まるときは、まだ送っていないメールを、その場で送り終えてから止まる（23.6）。メールサーバーの応答が遅いと止まるまでに時間がかかるので、実機の送信には時間の上限を設ける。

### エラーの通知の宛先の区分を追加する

- 設定に宛先の区分と宛先を追加し、その担当者が知るべきエラーのログを出力するときに、その区分を付ける。区分は、ロガーの拡張メソッド（`BeginErrorNotificationCategory`）で、ログのスコープとして付ける。

## 23.8 開発者向け情報

- 死活の確認は、ASP.NET Core のヘルスチェックの機能に、DB への接続の確認を1つだけ登録し、ログイン不要として公開する。ロードバランサーなどから短い間隔で呼ばれるので、リクエストごとのログ（LOG-007）は出さない。
- バージョン番号は、プロジェクトのフォルダの直下の `VERSION` ファイルに書く。サーバーと画面のビルドは、どちらもこのファイルを読む。
- サーバーのバージョンは .NET のアセンブリの情報バージョンとして埋め込み、コミットの識別子は .NET SDK がビルドのときに付ける。画面のバージョンは、画面のビルドのときに同じバージョン番号とコミットの識別子を埋め込む。
- エラーの通知は、ログの出力の仕組み（NLog）に、Error 以上のログを受け取る出力先を追加して行う。出力先は、ログを出力した時点で、ログファイルの1行と同じ情報を文字列にして渡す。画面からの処理を待たせないよう、受け取ったログは貯めておき、別のスレッドで1秒ごとにメールにして送る。抑止の状態は、サーバーのプロセスのメモリーに持つ。
- 既定では、ログを1件ずつすぐに送る（ALR-004）。サーバーは、起動のときに送る数を抑えるように切り替える（ALR-003）。
- いつ、どのログをメールにするかの判断は、時刻を引数で受け取る部品にまとめていて、単体テストで ALR-003 の例を確かめている。
