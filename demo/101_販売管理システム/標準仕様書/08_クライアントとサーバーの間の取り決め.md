# 8. クライアントとサーバーの間の取り決め

クライアントからサーバーの処理を呼び出す方法と、その結果（メッセージ、エラー）をクライアントでどう扱うかのうち、検索と更新に共通のものを扱う。確認メッセージなど更新に固有のものは11章、検索に固有のものは10章で扱う。

## 8.1 外部仕様

| ID | 仕様 | 確認方法 | 関連非機能要件 | 備考 |
|---|---|---|---|---|
| API-001 | サーバーから返されたメッセージを、エラー・警告・情報に分けて表示する | 実演 | |  |
| API-002 | 特定の項目に関するメッセージはその項目の近くに、項目に関係しないメッセージは画面の上部に表示する | 実演 | |  |
| API-003 | 処理中はボタンを押せなくし、処理中の表示を出す | 実演 | |  |
| API-004 | 予期しない例外が起きたときは、Error でログに出力し、利用者には固定の文言のエラーを返す | 検査 | セキュリティ、運用・保守性 | 例外の内容を利用者に見せないため。Error なのでエラーの通知の対象になる（ALR-001） |
| API-005 | 予期しない例外が起きたときは、ログの処理1回分の識別子（LOG-002）と同じ値を、問い合わせ番号として画面のエラーに表示する | 実演 | 運用・保守性 | 利用者からの問い合わせを受けたとき、ログを探す手がかりにするため。口頭でも伝えられるよう、読み違えやすい文字（I・L・O・U）を除いた英大文字と数字の8文字を、4文字ずつハイフンで区切った形（例：7KQ2-M9XD）にする |
| API-006 | 画面からの処理の呼び出しは、60秒のあいだ応答がなければ打ち切り、処理が終わったかどうか分からないことを伝えるエラーを表示する | 実演 | 性能・拡張性 | リバースプロキシやロードバランサーの多くが60秒前後で接続を切るので、それに合わせた値である。時間のかかる処理はジョブ（18章）にする。この時間で足りない処理は、ジョブにできない事情があれば、処理ごとに個別に決める |

## 8.2 限界

- 呼び出しを打ち切っても（API-006）、サーバー側の処理は止まらない。更新が行われたかどうかは、利用者が画面を読み込み直して確認する。
- サーバー側には、処理1回の時間の上限を設けていない。
- リバースプロキシやロードバランサーが60秒より早く接続を切ると、利用者には API-006 のエラーではなく、それらが返すエラーが表示される。待ち時間は60秒より長くする。

## 8.3 開発者向け情報

### API の形

- nijo.xml に定義した検索処理と更新処理の API は、自動生成される。自動生成によらない API を手で作ることもできる。見本が WebApi プロジェクトにあるので参照のこと。
- 自動生成された API は、REST の形ではなく、処理ごとの URL に POST で呼ぶ形である。検索も POST で呼ぶ。
- 手で作る API を画面から呼ぶ場合は、URL の正本を nijo.xml のテンプレート文字列（Templates）に置き、サーバーのルート定義と画面からの呼び出しの両方がそこから組み立てる。サーバーと画面で URL が食い違うのを防ぐため。ルート定義は、引数の位置にルートパラメーターをそのまま置く変換で組み立てるので、引数は文字列にする。
- 自動生成された API の、入力の受け取りと、メッセージ・確認メッセージ・戻り値の返却は、サーバー側の共通の処理が行う。これと、クライアントからサーバーの処理を呼ぶ共通の関数が対になっている。
- 応答は、完了・エラーまたは確認待ち・未ログイン・入力の形式の誤り・予期しない例外を、画面が区別できる形にしている。応答の形はこの2つの共通処理の間の取り決めなので、両方を一緒に変える。
- 予期しない例外の応答には、ログの処理1回分の識別子と同じ値の識別子を付けている。クライアントの呼び出しの共通の関数は、それを問い合わせ番号として表示する（API-005）。
- 呼び出しの打ち切り（API-006）は、クライアントからサーバーを呼ぶ共通の関数が、リクエスト1回ごとに行う。確認メッセージの後の2回目の呼び出しや、ログインし直した後の送り直しは、それぞれ改めて60秒を数える。

### オペレーションコンテキスト (OperationContext)

オペレーションコンテキスト（1.6）は、アプリケーションサービスのメソッドの入出力のうち、次の表の最後の種類を受け渡す。

| 情報 | 受け渡し方 | データ構造 |
|---|---|---|
| 入力 | 処理の引数 | 自動生成 |
| 戻り値 | 処理の戻り値 | 自動生成 |
| エラー・情報のメッセージ | 入力と同じ構造のメッセージのオブジェクト | 自動生成 |
| 入力チェックだけを行うかの指定、確認メッセージなど、すべての処理に共通の入出力 | オペレーションコンテキスト | 手書き |

- オペレーションコンテキストは、nijo が生成するものではなく、テンプレートの手書きのクラスである。nijo はその中身を見ない。呼び出し1回ごとの情報を、案件でプロパティとして追加してよい。画面に返す情報を追加した場合は、サーバー側の共通の処理とクライアントの呼び出しの共通の関数の両方に、同じものを手で加える。
- 呼び出し元（画面からの API、単体テスト、ジョブ）は、呼び出しのたびにオペレーションコンテキストを作って処理に渡し、処理の後に中身を読む。ログインユーザーや現在時刻のように、呼び出しの回数によらず同じ値になるものは入れず、DI から取得する。
- 処理の中から別の処理を呼ぶときは、同じ呼び出しの続きなので、同じオペレーションコンテキストを渡す。入力チェックだけを行うかの指定などを変えて呼びたいときは、新しく作って渡す。
- メッセージのオブジェクトの使い方（項目ごと、明細の行ごとのメッセージなど）は、nijo が生成するコードの使い方なので、nijo のリファレンスを参照する。
