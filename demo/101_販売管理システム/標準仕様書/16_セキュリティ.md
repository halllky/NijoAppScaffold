# 16. セキュリティ

特定の機能に属さない、Web アプリケーションとしての防御を扱う。HTTPS の扱い、ほかのサイトを使った攻撃（CSRF、クリックジャッキング）、画面や SQL への不正な入力（XSS、SQL インジェクション）、大量の呼び出しへの備えである。ログインや権限のように機能に属する防御は、その機能の章にある。

## 16.1 外部仕様

| ID | 仕様 | 確認方法 | 関連非機能要件 | 備考 |
|---|---|---|---|---|
| SEC-001 | HTTP で受けた要求を、HTTPS の URL にリダイレクトしない。応答に HSTS のヘッダー（`Strict-Transport-Security`）を付けない | 検査 | セキュリティ | SES-003 |
| SEC-002 | ほかのオリジンからの呼び出しを許可するヘッダー（CORS の `Access-Control-Allow-Origin` など）を返さない。そのため、ほかのオリジンのページのプログラム（JavaScript）は、API の応答を読めず、独自のヘッダーを付けた呼び出しも送れない | 検査 | セキュリティ | 画面と API が同じオリジンなので（ENV-002）、許可は要らない |
| SEC-004 | 画面は、表示する値（利用者が入力した値や DB の値など）を HTML として扱わず、文字のまま表示する。値に HTML のタグやスクリプトが含まれていても、文字として見えるだけで、実行されない。テンプレートの画面と、自動生成の画面の部品が対象である | 実演 | セキュリティ | 画面に不正なスクリプトを埋め込む攻撃（XSS）を防ぐため。画面の部品の仕組み（React）が、値を文字として表示することによる |
| SEC-005 | DB を読み書きするときは、利用者の入力などの値を SQL の文に埋め込まず、パラメーターとして DB に渡す。テンプレートの処理と、自動生成の処理が対象である | 検査 | セキュリティ | 入力で SQL を書き換えられる攻撃（SQL インジェクション）を防ぐため。開発支援機能の DB ビューアは、入力した条件を SQL にそのまま埋め込むが、本番用のビルドには含まれない（DEV-001） |
| SEC-006 | すべての応答に、表「SEC-006 応答に付けるヘッダー」のヘッダーを付ける。エラーの応答、静的なファイル、死活の確認（OPS-001）の応答も対象である。開発環境で、画面の開発サーバーが返す応答にも付ける。表のほかに、セキュリティのためのヘッダーは付けない。API の応答（ファイルのダウンロードを含む）には、キャッシュを制限するヘッダー（`Cache-Control` など）も付けない | 実演 | セキュリティ | `X-Frame-Options`、`Content-Security-Policy`、`Referrer-Policy` が意味をもつのは画面の HTML に対してだけだが、付け漏れを防ぐため、応答の種類で付け分けない。画面の HTML のキャッシュは UI-008 |
| SEC-007 | ほかのサイトのページから、ログイン中の利用者として処理を呼ばせる攻撃（CSRF）への対策は、この仕様と、セッションキーの Cookie の SameSite 属性（SES-002）の2つである。CSRF のトークンは使わない。本番環境では、GET・HEAD・OPTIONS 以外のメソッドの要求（処理の呼び出し、添付ファイルの一時保存など）に、`X-Requested-With` ヘッダーを必須にする。値は問わない。ヘッダーがなければ、処理を実行せず、状態コード 400 を本文なしで返す。このとき、LOG-007 のログに状態コード 400 で出るほかには、ログを出力しない。死活の確認（OPS-001）は対象外である。開発環境では確かめない。画面は、サーバーを呼ぶときに、メソッドによらず必ずこのヘッダーを付ける。テンプレートと自動生成の API のうち、GET・HEAD・OPTIONS で呼べるもの（ファイルのダウンロードなど）は、業務のデータを変えない | 実演 | セキュリティ | ほかのオリジンのページは、このヘッダーを付けて送れない（SEC-002）。開発環境で確かめないのは、API の一覧（Swagger）から呼び出せるようにするため |
| SEC-008 | 応答に `Server` ヘッダーを付けない | 実演 | セキュリティ | 使っているソフトウェアを外に知らせないため |
| SEC-009 | ログインの一時ロック（AUTH-010）のほかに、呼び出しの回数や頻度を制限しない。要求の本文の大きさの上限は、ASP.NET Core の既定の 30,000,000 バイト（約 28.6MB）である。添付ファイルの一時保存だけは、1ファイルの大きさの上限（FIL-003）に 64KB を足した大きさである | 検査 | セキュリティ | |

### SEC-006 応答に付けるヘッダー

| ヘッダー | 値 | 理由 |
|---|---|---|
| `X-Frame-Options` | `SAMEORIGIN` | ほかのサイトのページの枠（iframe）の中に、画面を表示させないため。見えないように重ねた画面を、利用者に知らずに操作させる攻撃（クリックジャッキング）を防ぐ。古いブラウザ向けで、今のブラウザは次の `frame-ancestors` に従う |
| `Content-Security-Policy` | `frame-ancestors 'self'` | 上と同じ。同じオリジンの画面の枠の中には表示できる。スクリプトやスタイルの読み込み元を制限する指定は付けない |
| `X-Content-Type-Options` | `nosniff` | 応答の中身の種類をブラウザに推測させず、テキストなどをスクリプトや HTML として扱わせないため |
| `Referrer-Policy` | `same-origin` | 画面からほかのサイトに移るときや、ほかのサイトの画像などを読むときに、画面の URL を送らないため |

## 16.2 限界

- HTTPS の URL へのリダイレクトと HSTS が必要なら、リバースプロキシやロードバランサーで行うか、アプリのソースを変えて有効にする（16.3）。設定ファイルでは切り替えられない（SEC-001）。
- IIS の上で動かすと、IIS が `Server` などのヘッダーを付ける。テンプレートでは外していないので、IIS の設定で外す。リバースプロキシやロードバランサーが付けるヘッダーも、その装置の設定で外す（SEC-008）。
- スクリプトの読み込み元を制限する指定がないので（SEC-006）、画面に不正なスクリプトを埋め込まれたときの多層防御がない。制限をそのまま付けると画面が動かなくなるので、付けるなら、案件で画面のビルドとあわせて調整が要る。
- 案件で、値を HTML として表示する画面（書式付きの文章を表示するなど）を作ると、SEC-004 の対象外になる。その画面で、表示する HTML を無害にする処理を加える。
- ほかのオリジンからの呼び出しを許可すると（SEC-002）、許可した相手のページには、SEC-007 の対策が効かない。許可するなら、相手を信頼できるオリジンに限る。
- 案件で、GET で業務のデータを変える API を作ると、SEC-007 の対象外になる。SameSite 属性が `Lax` の Cookie は、ほかのサイトのリンクから開いたときにも送られるので、そのリンクを踏ませるだけで実行させられる。データを変える API は、POST などのメソッドで呼ぶ形にする。
- 開発環境かどうかは、環境の名前で決まる（2章）。検証用の環境などを誤って開発環境の名前で動かすと、SEC-007 の確認が外れる。
- 大量の呼び出しによる負荷（DoS）への備えはない（SEC-009）。必要なら、リバースプロキシやロードバランサー、WAF で、呼び出しの頻度や大きさを制限する。

## 16.3 主なカスタマイズ方法

### HTTPS の URL へのリダイレクトと HSTS をアプリで行う

- WebApi の起動処理に、ASP.NET Core のリダイレクト（`UseHttpsRedirection`）と HSTS（`UseHsts`）を、コメントにして置いている。リダイレクトは、死活の確認の後、応答を返すほかの処理より前に置く。死活の確認までリダイレクトすると、ロードバランサーが HTTP で死活を確かめる構成で失敗する。
- リダイレクト先のポートは、設定（`https_port`、環境変数 `ASPNETCORE_HTTPS_PORTS` など）か、アプリが HTTPS で待ち受けていることから決まる。どちらもなければリダイレクトせず、警告のログを出すだけになる。テンプレートの設定ファイルにはどちらもない。
- リバースプロキシやロードバランサーで HTTPS を終端する構成では、アプリには HTTP で届く。元の要求のプロトコルを受け取る設定（ASP.NET Core の Forwarded Headers）をしないと、HSTS のヘッダーは付かず、リダイレクト先のポートを設定していればリダイレクトが繰り返される。

## 16.4 開発者向け情報

- SEC-006 のヘッダーは、`WebApi/SecurityHeadersMiddleware.cs` と `client/vite.config.ts` の2か所に書いている。
- `X-Requested-With` ヘッダー（SEC-007）は、画面からサーバーを呼ぶ共通の関数（`client/src/http/callAspNetCoreApiAsync.ts`）で付けている。案件でこの関数を通さずに GET 以外のメソッドで API を呼ぶと、開発環境では動くが、本番環境でだけ 400 になる。
- 手書きの SQL では、値を文字列の連結で SQL に埋め込まない。Entity Framework Core の `FromSql` や `SqlQuery` に補間文字列で渡すと、値はパラメーターになる。`FromSqlRaw` や `ExecuteSqlRaw` に値を連結した文字列を渡すと、SEC-005 が成り立たなくなる。
