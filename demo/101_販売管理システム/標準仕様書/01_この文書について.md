# 1. この文書について

## 1.1 この文書の性格と読者

- この文書は、コピー時点のテンプレートに何が入っていて、どこまで対応しているか、変更したい場合にどこまで変えることができるか、よくある変更の場合は具体的にどこを編集すればよいかを説明する。
- この文書もテンプレートと一緒にコピーされる。コピーした後は、案件の文書として残して保守してもよいし、捨ててもよい。
- 想定読者は、テンプレートの採用を検討する人や、開発者・運用担当者。これらの人は皆、自分の立場だけでなく、完成したアプリケーションの関係者（一般の利用者、システム管理者、運用担当者、連携する外部のシステム）の立場からも問題がないかを確かめるために読む。
- 業務のデータ構造・画面・処理は扱わない。それらは案件ごとに別途定める。
- 開発環境の準備と開発の始め方は README を参照。
- デモ101特有の処理は別ファイル `標準仕様書_参考実装.md`（このフォルダの外）にまとめているが、こちらはテンプレートのコピー後には残らない。

## 1.2 各章の書き方

```
【以下の方針になおす】
- 1章
  - 各章の概要を理解するためまでの全体概要を書く。例えばアプリケーションサービスは書くがmap to viewは書かない。
- 各章
  - 先頭に概要を書く。理解のため。読者全員がこのあとに続く仕様や開発者向け情報を理解批判検討評価し、共通の理解で議論できるようにするため。1章の説明を理解していることを前提にしてよい
  ― 外部仕様を書く。ここの役目は責任分界。
  - 限界、開発者向け情報など。ここの役目はここまでに拾いきれない情報を全部拾うこと。限界には外部仕様を書かない。開発者向け情報にはソースコードやソースのコメントに書くべきことを書かない。
  - ボリュームがある章は複数の話題に区切ったうえで上記をやる。区切る単位は読者の関心事。区切る場合でも章全体の概要は書く。
- 図は矢印の解釈が揺れがちになるなどの危険があるので、図には仕様を書かないものとする。基本的にはより抽象的な書き方にして。どうしても図に仕様が紛れざるを得ないなら文や表にも重複して書き、文や表を正とする。
```

1章、2章は概要説明。
3章以降は、関係者が仕様の矛盾や抜け漏れを検証しやすくするため、トピックごとに章を立てる。各章では、冒頭に概要を書き、続けて次の節のうち必要なものを置く。

| 節 | 内容 |
|---|---|
| 外部仕様 | 完成したアプリケーションの外から見える振る舞い。仕様項目の表で書く（1.3） |
| 限界 | 仕様の振る舞いでは足りなくなる条件と、足りないときに取れる手段。 |
| 主なカスタマイズ方法 | テンプレートそのままではなく改変して使う可能性が高い部分について、変更手順や注意点を示す。 |
| 開発者向け情報 | 外部仕様には当たらないが、開発者が知っておくべきこと。テンプレートの作りと、それに沿って作るときの決まりを、話題ごとに文章で書く。 |

外部仕様かどうかは、誰に向けたものかではなく、アプリケーションの外から見えるかどうかで分ける。画面、API の応答、ログ、メールなど、ソースコードを読まなくても動かせば分かる振る舞いは外部仕様である。運用担当者が開発者を兼ねていても、ログの内容は外部仕様である。プロジェクトの分け方やトランザクションの扱いのように、ソースコードの中だけで完結することは、開発者向け情報である。

このほか、章の内容を説明するための節（一覧の表など）を置くことがある。

## 1.3 仕様項目の書き方と属性

| 列 | 内容 |
|---|---|
| ID | 仕様の識別子。接頭辞は仕様の表ごとに決める（14章のように1つの章に表が複数あるときは、表ごとに接頭辞が異なる）。ID は振り直さないこととし、仕様をやめたときはその ID を欠番にする。章を組み替えて別の表に移った仕様も、元の ID のままにする。 |
| 仕様 | テンプレートの振る舞いを動詞で書く。nijoが自動生成するコードに由来する仕様は【自動生成コード由来のため変更不可】と書く。 |
| 確認方法 | 振る舞いを確認する方法。テスト（自動テストがある）、実演（動かして見る）、検査（ソースや定義を読む）のいずれか |
| 関連非機能要件 | その仕様が関わる非機能要件。値は IPA の非機能要求グレードの大項目（可用性、性能・拡張性、運用・保守性、移行性、セキュリティ、システム環境・エコロジー）から選ぶ。関わるものがない仕様は空にする |
| 備考 | 根拠、関係する仕様 |

## 1.4 用語

| 用語 | 意味 |
|---|---|
| nijo.xml | アプリケーションのデータ構造と処理を定義するファイル。データ構造の正本 |
| 再生成 | nijo.xml を変えた後、nijo のコマンドラインツールでコードを生成し直すこと |
| データモデル | nijo.xml で、DB に保存すると指定したデータ構造（`IsStored`）。テーブルと登録・更新・削除の処理が生成される |
| クエリモデル | nijo.xml で、検索できると指定したデータ構造（`IsQueryable`）。検索条件・検索結果の型と検索処理が生成される |
| コマンド | nijo.xml で定義する、更新などの処理。API と処理の枠が生成される |
| カスタム属性 | nijo.xml の項目に付ける、アプリケーション独自の属性。テンプレートには「最大長」「金額項目」「数量」「マスキング」があるが、これら以外も自由に追加可能。 |
| Ref | あるデータ構造が他のデータ構造を参照すること。RDBMSの外部キーや、画面上でマスタデータを検索ダイアログで検索して選択するときの親画面のデータとダイアログのデータの間の関係性のようなイメージ。 |
| MapToView | クエリモデルの検索結果を、DB のビューから取得するようにする nijo.xml の指定 |
| アプリケーションサービス(ApplicationService) | 業務ロジックを書くクラス。画面からの API、単体テスト、ジョブ、バッチから呼ばれる |
| オペレーションコンテキスト(OperationContext) | アプリケーションサービスのpublicメソッドの呼び出し1回ごとに、呼び出し元が作って処理に渡し、処理の後に中身を読む情報。入力チェックだけを行うかの指定と、確認メッセージをもつ |
| 確認メッセージ | 更新の前に利用者に了承を求めるメッセージ（UPD-006） |
| マイグレーション | DB のテーブル定義の変更を、変更1回ごとに記録して適用する仕組み |
| クライアント | ブラウザで動く部分（client プロジェクト）。利用者から見える画面と、サーバーを呼び出す処理からなる |
| サーバー | WebApi のプロセスで動く部分。API の受け口と、業務処理・DB へのアクセスからなる |
| ユーザー | ログインする人。テンプレートでは、nijo.xml のデータ構造「従業員」で表す |
| 案件 | テンプレートをコピーして作る、個々のアプリケーション |
| 開発環境 | ASP.NET Core の環境の名前が Development のとき。それ以外を本番環境と呼ぶ。ビルドの種類（Debug・Release）とは別の区別である（23.2） |
