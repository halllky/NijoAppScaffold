# 13. 認証

利用者が誰であるかを確かめる仕組みとして、ログイン、ログイン状態、パスワードと、ユーザーアカウントの保守を扱う。

テンプレートの認証の方式は、ユーザー ID とパスワードを入力してログインする方式だけである。外部の認証基盤を使う方式などは含まない。ログイン画面やユーザーアカウントの保守の画面も含め、案件に合わせて作り直すことを想定している。

ログインに成功すると、サーバーはセッションキーという推測できない値を発行し、Cookie でブラウザに渡す。DB には、セッションキーのハッシュ値を、ユーザーと最後に操作した日時とともに保存する。この DB の行をセッションと呼ぶ。ブラウザはサーバーへの問い合わせのたびに Cookie を付けて送り、サーバーは Cookie のセッションキーに対応するセッションから、ログインユーザーを決める。ログイン状態が出来事によってどう変わるかは、13.1 の状態遷移表にまとめている。

#### AUTH-006 複数タブ間のログイン状態の同期

この節は、AUTH-006 の仕様の詳細である。見出しに「補足」とある引用は、仕様ではなく説明である。

**タブのユーザー**

- 各タブは、画面を開いたとき（読み込み直したときを含む）に、ログイン状態をサーバーに問い合わせる。そのとき返ったログインユーザーを、そのタブの「タブのユーザー」と呼ぶ。ログインしていなければ、タブのユーザーはいない。
- タブのユーザーは、そのタブで画面を読み込み直すまで変わらない。
- 画面の表示と、業務画面に移ったときの振る舞いは、ブラウザのログイン状態ではなく、タブのユーザーで決まる。

| タブのユーザー | 画面の表示 | 業務画面に移ったとき |
|---|---|---|
| いる | ナビゲーションと業務画面を、そのユーザーで表示する | サーバーに問い合わせる |
| いない | 業務画面の代わりにログイン画面を表示する（AUTH-004） | サーバーに問い合わせず、ログイン画面を表示する（AUTH-004） |

- サーバーは、タブのユーザーを知らない。どのタブからの問い合わせも、Cookie のセッションのユーザーとして実行する。

**ほかのタブへの通知**

- タブは、次のときに、ブラウザの localStorage にあるユーザー ID を書き換える。書くのはユーザー ID だけで、セッションキーは書かない。

| とき | localStorage のユーザー ID |
|---|---|
| ログインに成功したとき（ログイン画面とログインのダイアログの両方） | ログインしたユーザーの ID を書く |
| ログアウトしたとき | 消す |
| 画面を開いたとき（読み込み直したときを含む） | タブのユーザーがいれば、その ID を書く。いなければ何もしない |

- ほかのタブがこの値を変えると、ブラウザが各タブに通知する（storage イベント）。値が変わらない書き換え（いまと同じ ID を書く、ないものを消す）では、通知しない。
- 通知を受けたタブは、変わった後の値と、タブのユーザーの ID とを比べ、違えば画面を読み込み直す。値がないことと、タブのユーザーがいないことは、同じとみなす。
- 読み込み直す前に UI-007 の確認を行う。利用者がやめると、読み込み直さない。
- localStorage を使えないブラウザでは、ほかのタブに通知しない。そのタブでのログインやログアウトの振る舞いは変わらない。

> **補足：タブのユーザーとブラウザのログイン状態が食い違う場合**
>
> 上の仕様から、次の場合はタブが読み込み直さず、タブのユーザーとブラウザのログイン状態が食い違う。
>
> - 期限切れやパスワードの初期化のように、通知を伴わずにログイン状態が終わった場合。次にサーバーに問い合わせたときに、ログインのダイアログを表示する（SES-005）。
> - ほかのタブでログインしたが、localStorage の値が変わらなかった場合。値はブラウザを閉じても残るので、前回と同じユーザーでログインし直したときがこれに当たる。ログイン画面を表示していたタブは、読み込み直すまでログイン画面のままである。
> - 読み込み直す前の確認で利用者がやめた場合と、localStorage を使えない場合。ほかのタブで別のユーザーがログインしていれば、このタブでの操作は、そのユーザーとして実行される（限界を参照）。

#### AUTH-011 認証のログ

AUTH-011 と AUTH-010 のログの内容は次のとおりである。ログの1行の形式は LOG-002 による。本文の「{ID}」には、入力されたユーザー ID がそのまま入る。そのため、パスワードを誤ってユーザー ID の欄に入力すると、そのパスワードが平文でログに残る。ログインユーザー ID の列には、どの出来事でも、その問い合わせを受けた時点でのブラウザのログインユーザーが入る。ログインしていないブラウザからなら空である。

| 出来事 | レベル | 本文 |
|---|---|---|
| ログインの成功 | Info | ログインしました。従業員番号: {ID} |
| 存在しないユーザー ID でのログインの失敗 | Info | ログインに失敗しました（従業員番号が存在しない）。従業員番号: {ID} |
| パスワードの誤りでのログインの失敗 | Info | ログインに失敗しました（パスワードの誤り）。従業員番号: {ID} |
| 一時ロック中のログイン | Info | ログインを受け付けませんでした（ログインの失敗が続いたため）。従業員番号: {ID} |
| 一時ロックの始まり | Warning | ログインの失敗が続いたため、この従業員番号のログインを一時的に受け付けません。従業員番号: {ID} |
| ログアウト（Cookie にセッションキーがあるとき） | Info | ログアウトしました。 |
| パスワードの変更 | Info | パスワードを変更しました。 |
| パスワードの初期化 | Info | パスワードを再発行しました。対象の従業員番号: {対象者の ID} |

#### 補足：ログイン状態

ログイン状態は、ブラウザごとに、次の3つの条件の組み合わせで決まる。

- ブラウザが、セッションキーの Cookie を持っているか
- その Cookie のセッションキーに対応するセッションが、DB にあるか
- そのセッションに記録された最後に操作した日時から、24時間以内か（SES-004）

| 状態 | Cookie | セッション | 最後に操作した日時から | サーバーの扱い |
|---|---|---|---|---|
| 未ログイン | なし | （関係しない） | （関係しない） | ログインしていない |
| ログイン中 | あり | あり | 24時間以内 | ログインしている |
| 期限切れ | あり | あり | 24時間を過ぎている | ログインしていない |
| セッション削除済み | あり | なし | （関係しない） | ログインしていない |

- 条件の組み合わせは、この4つですべてである。Cookie のセッションキーがどのセッションにも当たらない場合（改ざんされた値など）も、セッション削除済みとして扱う。
- 同じブラウザのタブとウィンドウは Cookie を共有するので、同じ状態になる。シークレットウィンドウ（プライベートブラウズ）は、通常のウィンドウと Cookie も localStorage も共有しないので、別のブラウザとして扱う。
- ブラウザを閉じたり、同じブラウザでログインし直したりして Cookie から使われなくなったセッションも、DB には残る。その後は、期限が切れたセッションと同じに扱われる（SES-008）。

#### 補足：状態遷移表

出来事ごとに、上の4つの状態がどう変わるかを、仕様から導いて示す。このブラウザでの出来事と、ほかの場所での出来事に分ける。行には、3つの条件のどれかを変えうる出来事を挙げる。開発環境だけで使う DB の作り直し（22章）は、すべてのセッションを消すが、この表には入れていない。

**このブラウザでの出来事**

- 状態の列のセルには、出来事の前にその状態だったブラウザが、出来事の後にどの状態になるかを書く。「変わらない」は、出来事の前の状態のままであることを表す。
- 仕様 ID の列には、状態の変わり方の根拠になる仕様を書く。

| 利用者が、ブラウザの Cookie やサイトのデータを消す | 変わらない | 未ログイン | 未ログイン | 未ログイン | |

### 限界

- 応答時間からユーザー ID の有無を推測されないようにするには（AUTH-003）、存在しないユーザー ID のときも、ダミーの値でパスワードの照合と同じ計算をするよう作り替える。
- ログインの失敗の回数の制限（AUTH-010）について
  - アカウントのロックではない。ロック（テンプレートには含まれない）は、システム管理者が解除するまでそのユーザーをログインできなくするものである。この制限は時間が経てば解ける。
  - IP アドレスごとの制限は行わないので、多数のユーザー ID を少しずつ試す攻撃は防げない。防ぐ必要があれば、リバースプロキシやロードバランサー、Web アプリケーションへの攻撃を防ぐ WAF などで制限するか、アプリに追加する。アプリに追加する場合は、それらを通ってきたリクエストでも、利用者の本来の IP アドレスが分かるように設定する必要がある。攻撃元を調べるには、それらのログを使う（AUTH-011）。
  - 入力されたユーザー ID ごとに数えるので、他人のユーザー ID で失敗を繰り返すことで、その利用者を一時的にログインできない状態にできてしまう。
  - 失敗の記録をサーバーごとのメモリーに持つので（AUTH-012）、サーバーが複数台のときは台数の分だけ多く失敗でき、リリースのための再起動でも一時ロックが解ける。台数や再起動によらずに制限するには、失敗の記録を DB などの共有の場所に置くよう作り替える。
- 別のユーザーがログインした後に読み込み直さなかったタブでは、前のユーザーの画面のまま、新しいユーザーとして操作できてしまう（AUTH-006）。テンプレートには防ぐ手段がないので、ユーザーを替える前にほかのタブを閉じるよう、利用者に案内する。
- ログインからの最大継続時間による期限はない（SES-004）。
- セッションキーの Cookie はブラウザを閉じると消える設定にしているが（SES-002）、ブラウザが前回のタブを開き直す機能などで Cookie が残り、閉じた後もログイン状態が続くことがある。共用の端末では、使い終わったらログアウトするよう、利用者に案内する。
- システム管理者が、特定のユーザーのログイン状態だけを終わらせる手段はない。パスワードを初期化すれば終わるが（PWD-006）、パスワードも初期パスワードに戻る。

## 13.2 パスワード

### 外部仕様

| ID | 仕様 | 確認方法 | 関連非機能要件 | 備考 |
|---|---|---|---|---|
| PWD-001 | パスワードは平文で保存しない。ユーザーごとのソルトを付けてストレッチングしたハッシュ値を保存する。方式は PBKDF2（HMAC-SHA256）で、ストレッチングの回数は600,000回である。ソルトは、パスワードを設定するたびに暗号用の乱数生成器で作る256ビットの乱数で、ハッシュ値とは別の列に保存する。ハッシュ値の列には、形式の版（1バイト）、ストレッチングの回数（4バイト）、PBKDF2 で作った256ビットの値をつなげた37バイトを保存する。形式の版を持たない古い形式（32バイト）の値も照合する。古い形式の値は、PBKDF2（600,000回）か、ストレッチングをしない HMAC-SHA256（ソルトを鍵とする）のどちらかに一致すれば、正しいパスワードとする。古い形式の値と、今より少ない回数で保存した値は、次にログインしたときに、今の形式と回数で保存し直す | テスト | セキュリティ | DB の内容が漏れても、元のパスワードを割り出しにくくするため。回数は OWASP の Password Storage Cheat Sheet の推奨値。HMAC-SHA256 の形式は、鍵のソルトも DB にあるので、DB の内容が漏れたときにストレッチングによる守りがない |
| PWD-002 | ログイン中のユーザーが、自分のパスワードを変更できる。変更には、現在のパスワードの入力が必要である。現在のパスワードの誤りは、ログインの失敗（AUTH-010）に数えず、ログにも出力しない | 実演 | セキュリティ | 席を離れた端末などで、本人以外がパスワードを変えられないようにするため |
| PWD-003 | パスワードの変更では、新しいパスワードを確認用と2回入力させ、一致しなければエラーにする | 実演 | セキュリティ | |
| PWD-004 | システム管理者が、ユーザーのパスワードを初期パスワードに戻せる（パスワードの初期化）。自分のパスワードも戻せる。新しく登録したユーザーのパスワードも初期パスワードになる。初期パスワードは全員共通の固定値で、テンプレートでは「pass」である | 実演 | セキュリティ | 初期パスワードを本人に伝える手段は提供しない |
| PWD-006 | パスワードを変更したときは、その操作をしたセッション以外の本人のセッションを消す。パスワードを初期化したときは、対象者のセッションをすべて消す | 検査 | セキュリティ | 変更前のパスワードでログインしている状態を残さないため |
| PWD-007 | パスワードは、空や空白だけにはできない。それ以外に長さと文字種の制限はなく、1文字でもよい。前後の空白も含めて、入力されたとおりに扱う。画面では、50文字を超えるとその項目にエラーを表示する | 実演 | セキュリティ | 50文字の制限は、画面の入力欄で入力の誤りに気付かせるためのもので（TYP-003）、サーバーでは確かめない。画面を通さずに API を直接呼ぶと、50文字を超えるパスワードにも変更できる |

### 限界

- 初回ログイン時のパスワードの変更を強制しないので、利用者が変更するまでは、初期パスワード（PWD-004）を知っている人がその利用者としてログインできる。
- パスワードの長さや文字種の制限（パスワードポリシー）はない（PWD-007）。必要なら、パスワードの変更の処理に入力チェックを加える。
- ログイン中の端末を他人に使われると、パスワードの変更で現在のパスワードを何度でも試され、気付く手段もない（PWD-002）。防ぐには、変更の処理でも失敗を数え、ログに出すよう加える。
- 利用者が自分でパスワードを戻す手段（パスワードを忘れたときの再設定など）はない。システム管理者に初期化してもらう。

### 外部仕様

| ID | 仕様 | 確認方法 | 関連非機能要件 | 備考 |
|---|---|---|---|---|
| USR-001 | システム管理者が、ユーザーの登録・変更・削除と権限の付け外しを、一覧の画面でまとめて行える | テスト | | |
| USR-002 | ユーザーの一覧を検索できる | 実演 | |  |
| USR-003 | 自分自身の削除と、自分自身のシステム管理者の権限を外すことはできない | 実演 | セキュリティ | ユーザーアカウントの保守はシステム管理者だけが使えるので（AUZ-005）、1人ずつ操作する限り、システム管理者が1人もいなくなることも防げる |
| USR-004 | ユーザーの権限や氏名を変えると、そのユーザーがログイン中でも、サーバーは次の呼び出しから変えた後の値を使う。画面のメニューやボタン、氏名の表示は、そのユーザーが画面を読み込み直すまで変わらない | 検査 | セキュリティ | AUZ-001、AUZ-004 |

### 限界

- 本番の最初のシステム管理者を作る手段はない。システム管理者が1人もいなくなったときや、ただ1人のシステム管理者がパスワードを忘れたときに、画面から元に戻す手段もない。DB を直接操作するなど、案件で手段を用意する。
- 2人のシステム管理者が同時に、互いのシステム管理者の権限を外すと、両方とも成功し、システム管理者が1人もいなくなる（USR-003）。
- セッションが残っているユーザーをすぐに削除したいときは、先にそのユーザーのパスワードを初期化して、セッションを消す（USR-005、PWD-006）。

## 13.4 主なカスタマイズ方法

### 認証の方式を差し替える

- サーバーでは、リクエストからログインユーザーを特定する部分（LoginUserProvider と、ASP.NET Core の認証の処理）を入れ替える。業務処理、権限の確認、作成者・更新者の記録は、ここで特定したログインユーザーを使うので、変えなくてよい。
- 画面とサーバーの間には、ログインしていなければサーバーは 401 を返し、画面は 401 を受け取るとログインのダイアログを表示し、ログインし直したら同じ呼び出しを送り直す、という取り決めがある（SES-005）。外部の認証基盤の画面に移ってログインする方式にするときは、401 を受け取ったときの画面の扱いを入れ替える。
- 手書きの API を足したときは、既定でログインが必要になり、ログインしていなければ 401 を返す。ログインせずに呼び出せるようにするには、その API ごとに許可する。

### 期限・回数・初期パスワードを変える

- ログイン状態の期限（SES-004）、ログインの失敗の回数の制限（AUTH-010）、初期パスワード（PWD-004）の値は、設定ファイルではなくソースの定数で決めている。変えるにはソースを修正して、ビルドし直す。

### ユーザーを別のデータ構造に置き換える

ユーザーを表すデータ構造は、デモから引き継いだ「従業員」である。多くの箇所から参照されているので、置き換えると広い範囲に影響する。

追随させる箇所は、次の手順で漏れなく見つかる。

1. nijo.xml を「従業員」で検索する。ユーザーとセッションの定義、ユーザーを参照する項目、ユーザーを削除できるよう、参照にせずユーザー ID（従業員番号）を文字列で持つ項目が見つかる。これらを変えて再生成する。
2. 手書きのソース（自動生成されたフォルダとマイグレーションを除く C# と TypeScript）を「従業員」で検索する。ユーザーのデータ構造やユーザー ID（従業員番号）を直接使う箇所が見つかる。作成者・更新者やログに記録するユーザー ID のように、ユーザー ID を文字列として扱う箇所も、変数名などに「従業員番号」を含むので見つかる。
3. サーバーのビルドと、画面の型チェック（`npm run tsc`）を通す。ログインユーザーを型（サーバーの `LoginUser`、画面の「ログインユーザー情報」）を通してだけ使う箇所は、その型の項目を変えなければ直さなくてよい。変えた場合は、ビルドと型チェックのエラーで見つかる。

## 13.5 開発者向け情報

- ログイン状態に関わる処理は、次の場所から読み始める。
  - サーバー：`Core/ログイン・認証/`、`WebApi/Authorization/`、WebApi の起動処理での認証と認可の登録（ログインを必須にする既定と、ログインせずに呼び出せる処理の許可）
  - 画面：`client/src/login/`、ログイン画面とログインのダイアログ（P001）、ログアウトの画面（P002）、画面の起動処理（ログイン状態の問い合わせと、タブ間の同期の開始）、ルーティングの定義（業務画面にログインを必須にする設定を付ける）
- 13.1 の状態遷移表は、ログイン状態を決める3つの条件と、タブのユーザーと、それらを変えたり使ったりする処理から作っている。処理を変えたり足したりしたときは、表を見直す。セッションのテーブル、セッションキーの Cookie、localStorage を扱う処理は、`セッションDbSet`、`ISessionKeyProvider`、`localStorage` で検索すれば見つかる。次のものは、この検索では見つからない。
  - ユーザー（従業員）の削除。セッションが残っていると、外部キーの制約で失敗する（USR-005）。
  - ジョブを実行するときのログインユーザー（SES-009）。
  - 画面からサーバーを呼び出す共通の処理。401 を受け取ると、ログインのダイアログを要求し、ログインし直したら送り直す。ダイアログそのものは、ログイン画面の側にある。
  - ログにログインユーザー ID を付けるミドルウェア。ASP.NET Core の認証の処理より前に動き、最初にログインユーザーを特定する。そのため、Cookie を消させることや、最後に操作した日時の記録は、実際にはここで起きる。認証の方式を差し替えるときは、ここも関わる。
