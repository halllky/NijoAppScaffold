# 13. 認証

利用者が誰であるかを確かめる仕組みとして、ログイン、ログイン状態、パスワードと、ユーザーアカウントの保守を扱う。

テンプレートの認証の方式は、ユーザー ID とパスワードを入力してログインする方式だけである。外部の認証基盤を使う方式などは含まない。ログイン画面やユーザーアカウントの保守の画面も含め、案件に合わせて作り直すことを想定している。

ログインに成功すると、サーバーはセッションキーという推測できない値を発番し、Cookie でブラウザに渡す。DB には、セッションキーのハッシュ値を、ユーザーと最後に操作した日時とともに保存する。この DB の行をセッションと呼ぶ。ブラウザはサーバーへの問い合わせのたびに Cookie を付けて送り、サーバーは Cookie のセッションキーに対応するセッションから、ログインユーザーを決める。ログイン状態がどの出来事でどう変わるかは、13.1 の状態遷移表ですべて示している。

### 外部仕様

#### ログイン状態

ログイン状態は、ブラウザごとに、次の3つの条件の組み合わせで決まる。同じブラウザのタブは Cookie を共有するので（AUTH-006）、同じ状態になる。

- ブラウザが、セッションキーの Cookie を持っているか
- その Cookie のセッションキーに対応するセッションが、DB にあるか
- そのセッションに記録された最後に操作した日時から、24時間以内か（SES-004）

| 状態 | Cookie | セッション | 最後に操作した日時から | サーバーの扱い |
|---|---|---|---|---|
| 未ログイン | なし | （関係しない） | （関係しない） | ログインしていない |
| ログイン中 | あり | あり | 24時間以内 | ログインしている |
| 期限切れ | あり | あり | 24時間を過ぎている | ログインしていない |
| セッションなし | あり | なし | （関係しない） | ログインしていない |

条件の組み合わせは、この4つですべてである。

どのブラウザの Cookie からも使われなくなったセッションも、DB には残る。ブラウザを閉じた後や、同じブラウザでログインし直した後の、前のセッションがこれに当たる。こうしたセッションも、期限が切れた後にクリーンナップで消える（CLN-001）。消えるまでは、そのユーザーを削除できない（USR-005）。

#### サーバーへの問い合わせのたびの判定

死活の確認（OPS-001）と、画面の JavaScript や CSS などのファイルの配信を除き、サーバーは問い合わせのたびに、次の表でログインユーザーを決める。上の行から順に判定し、最初に当てはまった行による。

| Cookie | セッション | 記録されている最後の操作 | ログインユーザー | 応答での Cookie の扱い | 最後の操作の記録 | 仕様 ID |
|---|---|---|---|---|---|---|
| なし | — | — | なし | そのまま | — | AUTH-009 |
| あり | なし | — | なし | 消させる | — | SES-008 |
| あり | あり | 24時間より前 | なし | 消させる | 変えない。セッションも消さない | SES-004、SES-008 |
| あり | あり | 5分より前 | セッションのユーザー | そのまま | 今の日時に記録し直す | SES-004 |
| あり | あり | 5分以内 | セッションのユーザー | そのまま | 変えない | SES-004 |

ログインユーザーがなしのときは、ログインが必要な処理には 401 を返し（AUTH-009）、ログインしていなくても呼べる処理はログインユーザーなしで実行する。ログインユーザーがいるときは、処理を呼び出せるかを権限で確かめてから実行する（AUZ-001）。

#### ログインの判定

ログインの処理は、次の表の順に判定し、最初に当てはまった行による。

| 順 | 条件 | 結果 | 失敗の記録 | 仕様 ID |
|---|---|---|---|---|
| 1 | ユーザー ID が空か、空白だけ | ユーザー ID の項目にエラーを表示する | 数えない | AUTH-002 |
| 2 | パスワードが空か、空白だけ | パスワードの項目にエラーを表示する | 数えない | AUTH-002、PWD-007 |
| 3 | そのユーザー ID のログインを受け付けない期間中 | しばらくログインできないことを伝えるメッセージを表示する。パスワードは照合しない | 数えない | AUTH-010 |
| 4 | そのユーザー ID のユーザーがいない | ユーザー ID とパスワードのどちらが誤っているかを区別しないメッセージを表示する | 数える | AUTH-003、AUTH-010 |
| 5 | パスワードが一致しない | 4 と同じメッセージを表示する | 数える | AUTH-003、AUTH-010 |
| 6 | 上のどれにも当たらない | ログインに成功する。新しいセッションを作り、Cookie を渡す。パスワードが古い回数で保存されていれば、保存し直す | 消す | SES-001、SES-002、AUTH-010、PWD-001 |

| SES-005 | ログイン中に開いた画面でログインが必要な処理を呼び、サーバーが 401 を返したときは、ログインのダイアログを表示する。ユーザー ID の欄には、その画面を開いたときのユーザーの ID が入っている。同じユーザーでログインし直すと、呼んだ処理を送り直して操作を続け、画面と入力中の内容はそのまま残る。別のユーザーでログインした場合は、画面を読み込み直す。ログインし直さずにダイアログを閉じた場合は、ログイン状態が切れていることを伝えるエラーを表示する。複数の処理が同時に 401 を受け取っても、ダイアログは1つだけ表示し、ログインし直したらそれぞれを送り直す | 実演 | セキュリティ | 長時間操作しなかった後に、入力中の内容が失われないようにするため。リンクで開くファイルのダウンロードでは、ダイアログは表示されず、ファイルを受け取れない |
| SES-006 | 同じユーザーが複数の端末で同時にログインできる。ログインのたびに別のセッションを作る | 検査 | セキュリティ | 同じブラウザでログインし直したときも、前のセッションは消さない |
| SES-007 | セッションは DB に置くので、サーバーを再起動しても、ログイン状態は続く。サーバーを複数台にしても、同じ DB を見ていればセッションは共有される | 検査 | | 複数台から同じ DB を使うには、SQLite 以外の DB にする必要がある（5.2） |
| SES-008 | Cookie のセッションキーに対応するセッションが DB にないか、期限が切れているときは、ログインしていないものとして扱い、応答でブラウザに Cookie を消させる（有効期限を過去にした Cookie を返す）。期限が切れたセッションは、このときには DB から消さない | 検査 | セキュリティ | 期限が切れたセッションは、クリーンナップで消える（CLN-001） |

### 限界

- 応答時間から、ユーザー ID が存在するかを推測できる（AUTH-003）。防ぐには、存在しないユーザー ID のときも、ダミーの値でパスワードの照合と同じ計算をするよう作り替える。
- ログインの失敗の回数の制限（AUTH-010）について
  - アカウントのロックではない。ロック（テンプレートには含まれない）は、システム管理者が解除するまでそのユーザーをログインできなくするものである。この制限は、入力されたユーザー ID を一定の時間だけ受け付けないもので、時間が経てば解ける。システム管理者が途中で解く手段はない。
  - IP アドレスごとの制限は行わないので、多数のユーザー ID を少しずつ試す攻撃は防げない。防ぐ必要があれば、前段の装置（ロードバランサーや、Web アプリケーションへの攻撃を防ぐ WAF など）で制限するか、アプリに追加する。アプリに追加する場合は、前段の装置を通ってきたリクエストでも、利用者の本来の IP アドレスが分かるように設定する必要がある。
  - 入力されたユーザー ID ごとに数えるので、他人のユーザー ID で失敗を繰り返すことで、その利用者を一時的にログインできない状態にできてしまう。
  - 失敗の記録をサーバーごとに持つので（AUTH-012）、サーバーが複数台のときは、実際には台数の分だけ多く失敗できる。台数や再起動によらずに制限するには、失敗の記録を DB などの共有の場所に置くよう作り替える。
- ほかのタブが画面を読み込み直さないと、そのタブは前のユーザーの画面のまま残る。ブラウザがサイトのデータの保存を許していない場合（AUTH-006）と、読み込み直す前の確認（UI-007）で、利用者が読み込み直さないことを選んだ場合に起こる。Cookie は共有しているので、別のユーザーがログインした後なら、そのタブでの操作は新しいユーザーとして実行される。ログアウトした後なら、次の操作でログインのダイアログが表示される（SES-005）。テンプレートには防ぐ手段がないので、ユーザーを替える前にほかのタブを閉じるよう、利用者に案内する。
- ログインからの最大継続時間による期限はない（SES-004）。
- セッションキーの Cookie はブラウザを閉じると消える設定にしているが（SES-002）、ブラウザが前回のタブを開き直す機能などで Cookie が残り、閉じた後もログイン状態が続くことがある。共用の端末では、使い終わったらログアウトするよう、利用者に案内する。
- ログイン状態が切れていたことはログに出力しない（AUTH-011）。利用者から「急にログインのダイアログが出た」と問い合わせがあったときは、ログアウトやパスワードの変更・初期化のログと突き合わせて原因を調べる。どれにも当たらなければ、期限切れによるものである。
- システム管理者が、特定のユーザーのログイン状態だけを終わらせる手段はない。パスワードを初期化すれば終わるが（PWD-006）、パスワードも初期パスワードに戻る。

## 13.2 パスワード

### 外部仕様

| ID | 仕様 | 確認方法 | 関連非機能要件 | 備考 |
|---|---|---|---|---|
| PWD-001 | パスワードは平文で保存しない。ユーザーごとのソルトを付けてストレッチングしたハッシュ値を保存する。方式は PBKDF2（HMAC-SHA256）で、ストレッチングの回数は600,000回である。ソルトは、パスワードを設定するたびに暗号用の乱数生成器で作る256ビットの乱数で、ハッシュ値とは別の列に保存する。ハッシュ値の列には、形式の版（1バイト）、ストレッチングの回数（4バイト）、PBKDF2 で作った256ビットの値をつなげた37バイトを保存する | テスト | セキュリティ | DB の内容が漏れても、元のパスワードを割り出しにくくするため。回数は OWASP の Password Storage Cheat Sheet の推奨値。形式の版を持たない古い形式（32バイト）の値も照合できる。古い形式には、ストレッチングをしない HMAC-SHA256 で保存した値も含まれる。古い形式の値と、今より少ない回数で保存した値は、次にログインしたときに今の形式と回数で保存し直す |
| PWD-002 | ログイン中のユーザーが、自分のパスワードを変更できる。変更には、現在のパスワードの入力が必要である | 実演 | セキュリティ | 席を離れた端末などで、本人以外がパスワードを変えられないようにするため |
| PWD-003 | パスワードの変更では、新しいパスワードを確認用と2回入力させ、一致しなければエラーにする | 実演 | セキュリティ | |
| PWD-004 | システム管理者が、ユーザーのパスワードを初期パスワードに戻せる（パスワードの初期化）。自分のパスワードも戻せる。新しく登録したユーザーのパスワードも初期パスワードになる。初期パスワードは全員共通の固定値で、テンプレートでは「pass」である | 実演 | セキュリティ | 値は設定では変えられず、変えるにはソースを修正する（13.4）。初期パスワードを本人に伝える手段は提供しない |
| PWD-006 | パスワードを変更したときは、その操作をしたセッション以外の本人のセッションを消す。パスワードを初期化したときは、対象者のセッションをすべて消す | 検査 | セキュリティ | 変更前のパスワードでログインしている状態を残さないため |
| PWD-007 | パスワードは、空や空白だけにはできない。それ以外に長さと文字種の制限はなく、1文字でもよい。前後の空白も含めて、入力されたとおりに扱う。画面では、50文字を超えるとその項目にエラーを表示する | 実演 | セキュリティ | 50文字の制限は画面だけで行い、サーバーでは確かめない（TYP-003） |

### 限界

- 初期パスワードは全員共通の固定値で（PWD-004）、初回ログイン時の変更も強制しない。新しく登録された利用者や、パスワードを初期化された利用者が変更するまでは、初期パスワードを知っている人がその利用者としてログインできる。
- パスワードの長さや文字種の制限（パスワードポリシー）はない（PWD-007）。必要なら、パスワードの変更の処理に入力チェックを加える。
- パスワードの変更で現在のパスワードを誤っても、ログインの失敗の回数の制限（AUTH-010）には数えず、ログにも出力しない。ログイン中の端末を他人に使われると、現在のパスワードを何度でも試され、気付く手段もない（PWD-002 の目的に対して足りない）。防ぐには、変更の処理でも失敗を数えるよう加える。
- 利用者が自分でパスワードを戻す手段（パスワードを忘れたときの再設定など）はない。システム管理者に初期化してもらう。

| USR-002 | ユーザーの一覧を検索できる | 実演 | |  |
| USR-003 | 自分自身の削除と、自分自身のシステム管理者の権限を外すことはできない | 実演 | セキュリティ | ユーザーアカウントの保守はシステム管理者だけが使えるので（AUZ-005）、1人ずつ操作する限り、システム管理者が1人もいなくなることも防げる |

### 限界

- 本番の最初のシステム管理者を作る手段はない。システム管理者が1人もいなくなったときや、ただ1人のシステム管理者がパスワードを忘れたときに、画面から元に戻す手段もない。DB を直接操作するなど、案件で手段を用意する。
- 2人のシステム管理者が同時に、互いのシステム管理者の権限を外すと、両方とも成功し、システム管理者が1人もいなくなる（USR-003）。
- セッションが残っているユーザーは削除できない（USR-005）。すぐに削除したいときは、先にそのユーザーのパスワードを初期化して、セッションを消す。

## 13.4 主なカスタマイズ方法

### 認証の方式を差し替える

- サーバーでは、リクエストからログインユーザーを特定する部分（LoginUserProvider と、ASP.NET Core の認証の処理）を入れ替える。業務処理、権限の確認、作成者・更新者の記録は、ここで特定したログインユーザーを使うので、変えなくてよい。
- 画面とサーバーの間には、ログインしていなければサーバーは 401 を返し、画面は 401 を受け取るとログインのダイアログを表示し、ログインし直したら同じ呼び出しを送り直す、という取り決めがある（SES-005）。外部の認証基盤の画面に移ってログインする方式にするときは、401 を受け取ったときの画面の扱いを入れ替える。
- 手書きの API を足したときは、既定でログインが必要になり、ログインしていなければ 401 を返す。ログインせずに呼び出せるようにするには、その API ごとに許可する。

### 期限・回数・初期パスワードを変える

- ログイン状態の期限（SES-004）、ログインの失敗の回数の制限（AUTH-010）、初期パスワード（PWD-004）の値は、設定ファイルではなくソースの定数で決めている。変えるにはソースを修正して、ビルドし直す。

### ユーザーを別のデータ構造に置き換える

ユーザーを表すデータ構造は、デモから引き継いだ「従業員」である。多くの箇所から参照されているので、置き換えると広い範囲に影響する。

追随させる箇所は、次の手順で漏れなく見つかる。

1. nijo.xml を「従業員」で検索する。ユーザーとセッションの定義、ユーザーを参照する項目、ユーザーを削除できるよう、参照にせずユーザー ID（従業員番号）を文字列で持つ項目が見つかる。これらを変えて再生成する。
2. 手書きのソース（自動生成されたフォルダとマイグレーションを除く C# と TypeScript）を「従業員」で検索する。ユーザーのデータ構造やユーザー ID（従業員番号）を直接使う箇所が見つかる。作成者・更新者やログに記録するユーザー ID のように、ユーザー ID を文字列として扱う箇所も、変数名などに「従業員番号」を含むので見つかる。
3. サーバーのビルドと、画面の型チェック（`npm run tsc`）を通す。ログインユーザーを型（サーバーの `LoginUser`、画面の「ログインユーザー情報」）を通してだけ使う箇所は、その型の項目を変えなければ直さなくてよい。変えた場合は、ビルドと型チェックのエラーで見つかる。

## 13.5 開発者向け情報

- 13.1 の状態遷移表と判定の表は、ログイン状態を決める3つの条件と、それを変える処理から作っている。次のものを変えたり足したりしたときは、表を見直す。ソースを括弧の中の語で検索すると、関わる箇所が見つかる。
  - セッションを作る・消す・記録し直す処理（`セッションDbSet`、`StartCreatingセッション`）
  - セッションキーの Cookie を渡す・消す処理（`ISessionKeyProvider`）
  - ログイン状態の期限（`SessionKey.IdleTimeout`）
  - ほかのタブへの知らせ（画面の `localStorage`）
  - ユーザーのデータを変える処理（`LoadForEdit従業員`、`StartCreating従業員`）
