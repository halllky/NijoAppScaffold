# 13. 認証

利用者が誰であるかを確かめる仕組みとして、ログイン、ログイン状態、パスワードと、ユーザーアカウントの保守を扱う。

テンプレートの認証の方式は、ユーザー ID とパスワードを入力してログインする方式だけである。外部の認証基盤を使う方式などは含まない。ログイン画面やユーザーアカウントの保守の画面も含め、案件に合わせて作り直すことを想定している。

## 13.1 ログインとログアウト

ログイン画面からのログインと、ログアウトを扱う。

次の図は、ログインとログアウトのときの流れである。セッションキーは Cookie でサーバーとブラウザの間を受け渡す。ログインユーザーが変わったことは、ブラウザの localStorage を通じて、同じブラウザのほかのタブに知らせる。

![ログインとログアウトの流れ](images/ログインの流れ_ログインとログアウト.drawio.svg)

### 外部仕様

| ID | 仕様 | 確認方法 | 関連非機能要件 | 備考 |
|---|---|---|---|---|
| AUTH-001 | ユーザー ID（従業員番号）とパスワードでログインする。ユーザー ID は、前後の空白を除き、全角の英数字を半角にそろえてから照合する。大文字と小文字は区別する | 実演 | | 大文字と小文字を区別するのは、テンプレートの DB（SQLite）での振る舞いである。DB を替えると、その DB の設定によっては区別しなくなる |
| AUTH-002 | ユーザー ID かパスワードが空のときは、その項目にエラーを表示する。両方が空のときは、ユーザー ID の項目にだけエラーを表示する | 実演 | |  |
| AUTH-003 | ログインに失敗したときは、ユーザー ID とパスワードのどちらが誤っているかを区別しないメッセージを表示する | 実演 | セキュリティ | 存在するユーザー ID を推測されないようにするため |
| AUTH-004 | ログインしていない利用者には、どの URL を開いてもログイン画面を表示し、業務画面を表示しない | 実演 | セキュリティ | |
| AUTH-005 | ログインに成功したら、開いていた URL の画面をそのまま表示する | 実演 | |  |
| AUTH-006 | 同じブラウザの複数のタブで、ログイン状態を共有する。画面を開いたときにサーバーに問い合わせて、ログイン状態を復元する。あるタブでログインユーザーが変わったとき（ログアウトを含む）は、他のタブも画面を読み込み直す | 実演 | | 読み込み直す前に UI-007 の確認を行う |
| AUTH-007 | ログアウトすると、セッションを無効にしてトップページに戻る | 実演 | セキュリティ | |
| AUTH-008 | 編集中の画面からログアウトしようとしたときは、UI-007 の確認を行う | 実演 | |  |
| AUTH-009 | ログインしていない状態で呼び出せる API は、「ログイン不要」と宣言した処理と、死活の確認の API（OPS-001）だけである | テスト | セキュリティ | 宣言の方法は AUZ-007。Debug ビルドでは、開発支援機能の API もログインせずに呼び出せる（DEV-001） |
| AUTH-010 | ログインに15分間で5回失敗したユーザー ID は、その後15分間ログインを受け付けない。受け付けない間は、正しいパスワードを入力してもログインできず、AUTH-003 とは別の、しばらくログインできないことを伝えるメッセージを表示する。受け付けない間の失敗は数えないので、期間は延びない。存在しないユーザー ID の失敗も数える。失敗は、ユーザー ID の大文字と小文字を区別せずに数える。ログインに成功すると、それまでの失敗は数えない。IP アドレスごとの制限は行わない。受け付けない期間が始まったときは、Warning でログに出力する | テスト | セキュリティ | 存在しないユーザー ID の失敗も数えるのは、受け付けるかどうかで、ユーザー ID の有無が分からないようにするため。Warning のログはエラーの通知（ALR-001）の対象ではないので、他人のユーザー ID で失敗を繰り返されていることには、ログを見て気付くことになる |
| AUTH-011 | ログインの成功と失敗、ログアウト、パスワードの変更と初期化を、Info でログに出力する。失敗のログには、入力されたユーザー ID を出力する | 検査 | セキュリティ | パスワードはログではマスキングされる（LOG-004） |

### 限界

- ログインの失敗の回数の制限（AUTH-010）について
  - アカウントのロックではない。ロック（テンプレートには含まれない）は、システム管理者が解除するまでそのユーザーをログインできなくするものである。この制限は、入力されたユーザー ID を一定の時間だけ受け付けないもので、時間が経てば解ける。システム管理者が途中で解く手段はない。
  - IP アドレスごとの制限は行わないので、多数のユーザー ID を少しずつ試す攻撃は防げない。防ぐ必要があれば、前段の装置（ロードバランサーや、Web アプリケーションへの攻撃を防ぐ WAF など）で制限するか、アプリに追加する。アプリに追加する場合は、前段の装置を通ってきたリクエストでも、利用者の本来の IP アドレスが分かるように設定する必要がある。
  - 入力されたユーザー ID ごとに数えるので、他人のユーザー ID で失敗を繰り返すことで、その利用者を一時的にログインできない状態にできてしまう。
  - 失敗の回数は DB に保存せず、動いているサーバーのプログラムの中だけで覚えている。そのため、サーバーを再起動すると消え、受け付けない期間も解ける。サーバーが複数台のときは台ごとに数えるので、実際には台数の分だけ多く失敗できる。
- ブラウザがサイトのデータの保存を許していないと、ログインユーザーが変わったことを他のタブに知らせられない（AUTH-006）。そのとき他のタブは、前のユーザーの画面のまま残る。ログアウトした後なら、次の操作でログインのダイアログが表示される（SES-005）。別のユーザーがログインした後なら、次の操作は新しいユーザーとして実行される。
- ログイン状態が切れた後に、あるタブで切れる前と同じユーザーでログインし直しても、ログイン画面を表示している他のタブは読み込み直さない。ログインユーザーが変わったことにはならないため。

## 13.2 ログイン状態

ログインしてからログイン状態が終わるまでの扱いと、終わった後に操作したときの扱いを扱う。

次の図は、ログイン状態が切れていたときの流れである。利用者が、保存・検索・画面の移動など、サーバーへの問い合わせを伴う操作をしたところ、ログイン状態が切れていた場合を示す。

![ログイン状態が切れていたときの流れ](images/ログインの流れ_ログイン状態が切れていたとき.drawio.svg)

### 外部仕様

| ID | 仕様 | 確認方法 | 関連非機能要件 | 備考 |
|---|---|---|---|---|
| SES-001 | ログインのたびに、推測できないセッションキーを発番する。DB には、セッションキーそのものではなく、セッションキーに戻せない形に変換した値を保存して照合する | 検査 | セキュリティ | DB の内容が漏れても、そこからほかの利用者になりすませないようにするため。セッションキーはログではマスキングされる（LOG-004） |
| SES-002 | セッションキーは Cookie でブラウザに持たせる。この Cookie は、画面のプログラム（JavaScript）からは読めず、ほかのサイトのページから送られる更新の呼び出しには付かない | 検査 | セキュリティ | 画面に不正なスクリプトを埋め込まれても、セッションキーを盗まれないようにするため。ほかのサイトのページから、ログイン中の利用者として勝手に操作させられないようにするため（SEC-003） |
| SES-003 | 開発環境以外では、セッションキーの Cookie を、HTTPS の通信でだけ送らせ、同じドメインの下にあるほかのサイト（サブドメイン）から上書きされないようにする | 検査 | セキュリティ | 通信の途中でセッションキーを盗み見られないようにするため。そのため、開発環境以外では HTTPS でアクセスしないとログインできない。開発環境は HTTP で動かすので、この設定をしない |
| SES-004 | ログイン状態は、ブラウザを閉じるか、ログアウトするか、最後に操作してから24時間が経つまで続く。操作には、画面を開いたときなどに画面が自動で行うサーバーの呼び出しも含む。期限は、サーバーを呼び出すたびにサーバーで確かめる。最後に操作した日時は、前回の記録から5分以上経った操作のときだけ記録し直すので、最後の操作から24時間より最大5分早く切れることがある | テスト | セキュリティ | 最後に操作した日時を、操作のたびに DB に記録しないのは、DB の負荷を抑えるため |
| SES-005 | ログイン状態が切れた後に操作したときは、ログインのダイアログを表示する。ログインし直すと、その操作をそのまま続け、画面と入力中の内容はそのまま残る。別のユーザーでログインした場合は、画面を読み込み直す。ログインし直さずにダイアログを閉じた場合は、ログイン状態が切れていることを伝えるエラーを表示する | 実演 | セキュリティ | 長時間操作しなかった後に、入力中の内容が失われないようにするため |
| SES-006 | 同じユーザーが複数の端末で同時にログインできる。ログインのたびに別のセッションを作る | 検査 | セキュリティ | |
| SES-007 | セッションは DB に置くので、サーバーを複数台にしても、同じ DB を見ていればセッションは共有される | 検査 | | 複数台から同じ DB を使うには、SQLite 以外の DB にする必要がある（5.2） |

### 限界

- ログインからの最大継続時間による期限はない（SES-004）。
- セッションキーの Cookie はブラウザを閉じると消える設定にしているが、ブラウザが前回のタブを開き直す機能などで Cookie が残り、閉じた後もログイン状態が続くことがある。
- ログイン状態が切れたこと自体はログに出力しないので、切れた原因（期限切れ、ログアウト、パスワードの初期化など）はログでは区別できない。

## 13.3 パスワード

### 外部仕様

| ID | 仕様 | 確認方法 | 関連非機能要件 | 備考 |
|---|---|---|---|---|
| PWD-001 | パスワードは、DB の内容が漏れても元のパスワードを割り出しにくい形に変換して保存する。同じパスワードでも、ユーザーごとに違う値になる。変換にはわざと時間がかかるようにして、総当たりで割り出すのにかかる時間を長くしている | 検査 | セキュリティ | |
| PWD-002 | ログイン中のユーザーが、自分のパスワードを変更できる。変更には、現在のパスワードの入力が必要である | 実演 | セキュリティ | 席を離れた端末などで、本人以外がパスワードを変えられないようにするため |
| PWD-003 | パスワードの変更では、新しいパスワードを確認用と2回入力させ、一致しなければエラーにする | 実演 | セキュリティ | |
| PWD-004 | システム管理者が、他のユーザーのパスワードを初期パスワードに戻せる（パスワードの初期化）。新しく登録したユーザーのパスワードも初期パスワードになる。初期パスワードは全員共通の固定値で、テンプレートでは「pass」である | 実演 | セキュリティ | 値は設定では変えられず、変えるにはソースを修正する（13.5）。初期パスワードを本人に伝える手段は提供しない |
| PWD-006 | パスワードを変更したときは、その操作をしたセッション以外の本人のセッションを消す。パスワードを初期化したときは、対象者のセッションをすべて消す | 検査 | セキュリティ | 変更前のパスワードでログインしている状態を残さないため |

### 限界

- 初期パスワードは全員共通の固定値で（PWD-004）、初回ログイン時の変更も強制しない。新しく登録された利用者や、パスワードを初期化された利用者が変更するまでは、初期パスワードを知っている人がその利用者としてログインできる。
- パスワードの長さや文字種の制限はない。空白だけのパスワードにはできないが、1文字のパスワードにはできる。画面で入力できるのは50文字までである。
- 利用者が自分でパスワードを戻す手段（パスワードを忘れたときの再設定など）はない。システム管理者に初期化してもらう。

## 13.4 ユーザーアカウントの保守

### 外部仕様

| ID | 仕様 | 確認方法 | 関連非機能要件 | 備考 |
|---|---|---|---|---|
| USR-001 | システム管理者が、ユーザーの登録・変更・削除と権限の付け外しを、一覧の画面でまとめて行える | テスト | | |
| USR-002 | ユーザーの一覧を検索できる | 実演 | |  |
| USR-003 | 自分自身の削除と、自分自身のシステム管理者の権限を外すことはできない | 実演 | セキュリティ | ユーザーアカウントの保守はシステム管理者だけが使えるので（AUZ-005）、1人ずつ操作する限り、システム管理者が1人もいなくなることも防げる |
| USR-004 | ユーザーの権限を変えると、そのユーザーがログイン中でも、サーバーは次の呼び出しから変えた後の権限で確認する。画面のメニューやボタンの表示は、そのユーザーが画面を読み込み直すまで変わらない | 検査 | セキュリティ | AUZ-001、AUZ-004 |

### 限界

- 本番の最初のシステム管理者を作る手段はない。システム管理者が1人もいなくなったときや、ただ1人のシステム管理者がパスワードを忘れたときに、画面から元に戻す手段もない。DB を直接操作するなど、案件で手段を用意する。
- 2人のシステム管理者が同時に、互いのシステム管理者の権限を外すと、両方とも成功し、システム管理者が1人もいなくなる（USR-003）。
- セッションが残っているユーザーは削除できず、保存のときにエラーになる。セッションは、ログアウトしたときと、パスワードを初期化したときに消える。期限が切れたセッションも、定期的なクリーンナップで消えるまでは残る。すぐに削除したいときは、先にそのユーザーのパスワードを初期化する。

## 13.5 主なカスタマイズ方法

### 認証の方式を差し替える

- サーバーでは、リクエストからログインユーザーを特定する部分（LoginUserProvider と、ASP.NET Core の認証の処理）を入れ替える。業務処理、権限の確認、作成者・更新者の記録は、ここで特定したログインユーザーを使うので、変えなくてよい。
- 画面とサーバーの間には、ログインしていなければサーバーは 401 を返し、画面は 401 を受け取るとログインのダイアログを表示し、ログインし直したら同じ呼び出しを送り直す、という取り決めがある（SES-005）。外部の認証基盤の画面に移ってログインする方式にするときは、401 を受け取ったときの画面の扱いを入れ替える。
- 手書きの API を足したときは、既定でログインが必要になり、ログインしていなければ 401 を返す。ログインせずに呼び出せるようにするには、その API ごとに許可する。

### 期限・回数・初期パスワードを変える

- ログイン状態の期限（SES-004）、ログインの失敗の回数の制限（AUTH-010）、初期パスワード（PWD-004）の値は、設定ファイルではなくソースの定数で決めている。変えるにはソースを修正して、ビルドし直す。

### ユーザーを別のデータ構造に置き換える

ユーザーを表すデータ構造は、デモから引き継いだ「従業員」である。多くの箇所から参照されているので、置き換えると広い範囲に影響する。

- nijo.xml のユーザー（従業員）とセッションの定義を変える。
- 追随させるもの：ログインユーザーを特定する処理、ログイン・パスワードの各処理、ログイン画面、ユーザーアカウントの保守の画面、ユーザーの権限、ダミーデータ、ログに出すログインユーザー ID、作成者・更新者に記録する値、通知の宛先とジョブの起動したユーザー（ユーザー ID を文字列で持つ）、画面のタブの間で共有するユーザー ID。
