# 6. データ構造と項目の型

項目の型ごとの、保存のされ方、画面での入力のしかた、入力チェック、検索のしかたを扱う。入力チェックで値を丸めたり切り捨てたりせず、気付かないまま値が変わるのを防ぐ、という考え方で全体をそろえている。型ごとの DB と検索での扱いは nijo が決めていて、変えられない（TYP-014）。

## 6.2 限界

- TYP-001 と TYP-004 の変換は、入力の手間を減らすためのもので、画面の入力欄でだけ行う。画面を経由しない値（ジョブ、ファイルの取り込み、API の直接の呼び出し）は変換されないので、そろえる必要があれば、その処理の中で変換する。
- 「金額項目」は「円」、「数量」は「個」しか付けられない（TYP-011、TYP-012）。ほかの単位が要る項目には、カスタム属性を足す。
- TYP-002 の数え方は、DB の製品が長さを数える単位と違うことがある。SQL Server などでは、絵文字や結合文字を含む値が、入力チェックを通っても保存のときに DB の列の長さを超えてエラーになることがある。DB の製品に合わせるには、文字列の長さの入力チェックを書き換える。
- 文字の種類（半角英数字だけ、など）を制限する指定はない。カスタム属性による入力チェック（11.4）で作る。
- 日付時刻はタイムゾーンをもたず、業務のタイムゾーンの現地時刻として扱う（ENV-004）。

## 6.3 開発者向け情報

### データ構造の分け方

- `IsStored` を指定するデータ構造（データモデル）は、データの整合性を保つ単位で分ける。1つのデータモデルは、子（`child`）や子の配列（`children`）を含めて、まとめて登録・更新・削除される。
- `IsQueryable` を指定するデータ構造（クエリモデル）は、画面に表示する粒度で分ける。
- ほかのデータ構造は、外部参照（`ref-to`）で参照する。多対多の関係は、子の配列と外部参照で表す。

### 文字列と数値の扱い

- 型ごとの入力チェック（文字列の長さ、数値の桁数、必須）の中身は、手書きのコード（`Core/OverridedDbContext.Validation.cs`）にある。nijo は、これらを DbContext の abstract メソッドとして生成し、登録・更新のコマンドの入力チェックから項目ごとに呼ぶ。手書きのコードは、TYP-002・TYP-005・TYP-008 のとおりに書いたテンプレートの初期値で、案件の事情に合わせて書き換えてよい。
- DB の製品が長さを数える単位（UTF-16 の単位など）に合わせるときは、文字列の長さのチェック（`ValidateMaxLength`）を書き換える。
- 未入力の項目は、空の文字列ではなく、値なし（null）として保存する。画面は、空の文字列をサーバーに送らない。
- 金額や数量の計算結果の丸めは、計算する業務処理の中で行う。丸めの共通の処理はない。

### 区分値の設計

区分値は、その性質によって、静的区分、汎用参照テーブル、普通のデータモデル、nijo.xml を介さない手書きの enum を使い分ける。汎用参照テーブルは、「コード、名称、表示順」程度の項目しかもたない区分値を、区分の種類ごとにテーブルを作らず、1つのテーブルにまとめて保存する nijo の仕組みである。区分の種類ごとに DB のビューを作る（5.4）。

#### A. 本番運用中に区分値が増減しない区分の場合

1. DB の列や、クエリモデルの検索条件・検索結果、コマンドの引数や戻り値に登場する
   **→ nijo の静的区分として実装する（自動生成後に C# の enum や TypeScript のユニオン型になる）。**
2. 登場しない
   **→ C# の enum などを手書きのコードで宣言して使う。**

#### B. 本番運用中に区分値が増減する区分の場合

1. 「コード、名称、表示順」程度を超えて、「オプション1, 2, ...」「属性1, 2, ...」などのキー以外の項目をもつ
   **→ それはもはやコード/名称だけの区分と同列に扱ってよい存在ではないので、普通のデータモデルとして設計する。**
2. 「コード、名称、表示順」程度の項目しかもたない
   **→ nijo の汎用参照テーブルを使う。**

### 汎用参照テーブル

テンプレートとデモ101では使っていないが、区分値の設計（B-2）で使う。

- キーは複数の項目からなる。そのうち、区分の種類を表す項目（例：業務分類・コード種別）は nijo.xml に書いた値に固定され（`IsHardCodedPrimaryKey`）、残りの項目（例：コード値）だけを運用中に登録する。区分の種類と、固定される値の組み合わせは、nijo.xml の `GenericLookupTableCategories` に定義する。
- 項目は「コード、名称、表示順」程度にとどめる。それを超える項目をもたせたくなった区分は、普通のデータモデルに切り離す（B-1）。
- 登録・更新・削除は、普通のデータモデルと同じく生成された処理で行う。区分の種類を表す項目の値は、生成された補助のプロパティから取り出して設定する。区分の種類ごとの値の一覧（ドロップダウンの選択肢など）も、同じ補助のプロパティから取り出す。
- 区分値を参照するデータは、区分の種類を表す項目をもたず、残りの項目（コード値）だけをもつ。nijo.xml では、参照の項目に区分の種類（`Category`）を指定する。
- DB の外部キーの制約は付かない。代わりに、生成された入力チェックが、参照先の区分値が存在するかを確かめる。ただし、入力チェックと保存の間に区分値が削除されると、存在しない区分値を参照したデータが保存されることがある。
- 参照するデータを検索するときは、区分の種類ごとに作られた DB のビューと結合して、その時点の名称や表示順を取り出す。ビューの列と結合の関係は、nijo が Entity Framework Core の設定として生成するが、ビューを作る SQL は生成しない。ビューを作る SQL は、テンプレートの Management のコマンドが、nijo が生成したビューの情報をもとに作る（5.4）。このコマンドは SQLite を対象にしているので、ほかの DB の製品にする場合は書き換える。生成されたコードはビューがあることを前提にしているので、汎用参照テーブルを使う場合は、ビューを常に最新に保つ。
