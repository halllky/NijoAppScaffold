# 12. 外部システム連携

ここで言う外部システムとは、このシステムの開発チームの管理下に無いもの、環境によってはモックを置いて動作させたくなるものを指す。例えばデータベースやログファイルは確かにアプリケーションのメモリ空間の外部にあるが、外部システムではない。メールサーバーは開発中の誤送信防止のためにモックで動かしたくなるので外部システムに含めるという解釈もできるが、開発環境では常にlocalhostでSMTPを立てる開発規約とするなどしてDBと同じ扱いにするならば外部システムではないとみることもできる。

ここでは、外部システムの更新を伴う処理の決まりと、外部システムの代わりに動くモックを扱う。モックは主に開発環境で外部システムの環境を用意しなくても動作確認できるようにするために使うものであり、基本的には本番稼働開始後も削除せず残す想定。

テンプレートに実際の外部システムとの連携サンプルはなく、連携を追加するための枠がある。

## 12.1 外部仕様

| ID | 仕様 | 確認方法 | 関連非機能要件 | 備考 |
|---|---|---|---|---|
| EXT-001 | 外部システムの更新を伴う処理では、原則として、外部システムの更新をすべて先に行い、1つでも失敗したら DB をコミットしない | 検査 | | DB の確定の後に外部システムを更新する必要がある処理は、個別に決める |
| EXT-002 | 外部システムごとに、どの実装（本物の実装、モックなど）を使うかを設定で切り替えられる。一部の外部システムだけをモックにして動かせる | 検査 | | 見本は、テンプレートではエラーの通知のメールの送信（ALR-005）、デモ101では参考実装の商品管理システムとの連携。 |
| EXT-003 | どの実装を使うかの設定を省略したときは、起動を止める | 検査 | | モックのまま本番環境が動き続け、誰も気付かない事態を防ぐため。開発環境やテスト環境でも、モックを使うことを設定に明記する |
| EXT-004 | 開発環境以外でモックを使っているときは、起動のときに、モックを使っている外部システムの名前をログに Warning で出力する | 検査 | | 本番環境で意図せずモックのまま動かすのを防ぐため。意図してモックで動かすときも、どれがモックかをログで確かめられる |

## 12.2 限界

- 成功済みの外部システムの更新は、後続の外部システムの更新や DB のコミットが失敗しても取り消されない。
- 外部システムの呼び出しのリトライ・タイムアウトの仕組みはない。外部システムごとに実装する。

## 12.3 主なカスタマイズ方法

### 外部システム連携を追加する

- 外部システムごとにインターフェースを定め、本物の実装とモックを作り、設定で切り替える（EXT-002、EXT-003、EXT-004）。本物の実装は、接続のしかたの違いなどで複数あってもよい。モックが何をするか（送る内容をファイルに書き出す、決まった応答を返すなど）は、外部システムごとに決める。実装を登録する場所はテンプレートにある。
- 更新を伴う連携は、EXT-001 の順序で行われるよう、アプリケーションサービスのトランザクションに参加させる（12.4）。

## 12.4 開発者向け情報

- 外部システムの更新は、その場で実行せず、トランザクションに予約する。予約した更新は、コミットのときに、DB の確定より先に、予約した順に実行される（EXT-001）。途中で失敗したら、それ以降の更新は実行せず、DB の変更を取り消す。コミットせずに終わると、予約した更新は実行されない。
- 失敗より前に成功した外部システムの更新は取り消されず、運用担当者が復旧する（12.2）。そのため、予約には、どのデータを更新しようとしたか（キーなど）が分かる名前を付ける。1つの操作で複数の更新を予約するときは、途中で失敗したときの復旧のしかたを決めてから実装する。
- 外部システムの更新の失敗による例外は捕まえない（9.4）。
- 外部システムからの読み取りは、予約せずにその場で行ってよい。
- どの実装を使うかの設定の確認（EXT-003）と、モックを使っていることの Warning（EXT-004）は、共通の仕組みにはしていない。外部システムを DI コンテナに登録する処理の中で、外部システムごとに書く。実装の選択肢が外部システムごとに異なるため。
- 予約のしかたの細部（どこから予約するか、リトライをどこに書くか）は、トランザクションのクラス（`ExternalResourceTransaction`）の予約のメソッドのコメントを参照する。
