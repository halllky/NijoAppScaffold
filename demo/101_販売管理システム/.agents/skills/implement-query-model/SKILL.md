# クエリモデルの実装

クエリモデルは「一覧検索 1 種類」を表す読み取り専用のモデルである。
絞り込み・並び替え・件数取得・ページングの骨格は自動生成されており、
開発者は「検索結果の各項目をどこから取得するか（SQL の FROM 句と SELECT 句）」と、必要に応じて骨格に差し込まれるメソッドだけを実装する。

`CreateQuerySource` が返した `IQueryable` に対して、WHERE・ORDER BY・件数取得・ページングが自動で付加される。

```
CreateQuerySource   … FROM 句・SELECT 句
AppendWhereClause   … WHERE 句（自動生成。オーバーライド可）
AppendOrderByClause … ORDER BY 句（自動生成。オーバーライド可）
件数取得・Skip/Take
OnAfterLoaded       … 現在ページの行に対するメモリ上の後処理（オーバーライド可）
```

## 進め方

1. 自動生成された検索処理のソースを読み、実装方式を確認する。記憶や推測ではなく生成物を正とする。
   - `CreateQuerySource` が抽象メソッドなら「LINQ to Entities 方式」、ビューを参照する実装が生成されていれば「ビュー方式」（スキーマ定義で `MapToView` を指定）。
   - データモデルから自動生成されたクエリモデルのように `CreateQuerySource` の実装まで生成されている場合は、FROM 句・SELECT 句の実装は不要である。
2. 方式に応じて以下の節に従って実装する。ファイルは次のように分ける。
   - **C# のオーバーライド**は、アプリケーションサービス（`OverridedApplicationService`）の partial class に書く。
     業務のまとまりごとのフォルダ（同じまとまりのコマンドモデルと同じフォルダ）に、クエリモデル 1 つにつき 1 ファイル、ファイル名はクエリモデル名とする。
   - **ビュー方式のビュー定義 SQL** は `Core/MigrationsScript/` に置く（「ビュー方式」の節）。C# のオーバーライドが何も無ければ C# のファイルは作らない。
   - **外部システムからの読み取り**は、クエリモデルのファイルに直接書かず、外部システムごとのフォルダに置かれたインターフェースを通じて呼ぶ。
3. ビルドし、実際に検索を実行して、絞り込み・並び替え・件数・ページ送りがそれぞれ正しく動くことを確かめる。
   ビュー方式では、ビューとの不整合はビルドで検出されないため、すべての列について絞り込みと並び替えを実行して確かめる。

## 自動生成されたファイルは編集しない

振る舞いはオーバーライドで変える。生成物のままでは実現できない場合は、コードを歪めて回避せずユーザーに報告する。

## 検索結果の値はすべて SQL で算出する（両方式共通）

検索結果の各項目は、集計・結合・条件分岐・複数のデータ源の連結も含めて DB 側で計算する。
SQL で算出した項目であれば、自動生成される絞り込み・並び替え・件数取得・ページングが自動で正しく動く。

## LINQ to Entities 方式

`CreateQuerySource` をオーバーライドし、DbContext のエンティティから検索結果の型への射影（`Select`）を書き、1 つの `IQueryable` として返す。

- 参照先の項目はナビゲーションプロパティで辿り、集計も射影の中で行う（SQL に翻訳される）。
- 射影の式は、EF Core が SQL に翻訳できるものだけで書く。SQL に翻訳できない C# のメソッド（自作メソッド、文字列整形など）を式の中で呼ばない。
- クエリの途中で `ToList` などを呼んでメモリに展開しない。子配列を持つ項目を射影の中で `.Select(...).ToList()` と組み立てるのはよい。
- 複数のデータ源を連結する場合は `Concat` / `Union` で 1 つの `IQueryable` にまとめる。
- 翻訳できるかどうかは実行時まで分からない。実際に検索を実行し、例外が出ないこと、および想定どおりの SQL が発行されていることをログで確かめる。

## ビュー方式

検索結果の型は DB のビューにマッピングされたエンティティとして生成され、`CreateQuerySource` もそのビューを読む実装が生成済みである。
開発者が書くのは、そのビューを作る SQL（`CREATE VIEW`）である。

- **ビュー名・列名・キーは生成されたエンティティ設定を正とする**。生成された EF Core 設定（`ToView(...)`、`HasColumnName(...)`、`HasKey(...)`）を読み、
  子配列のビューも含めて、ビュー名と全列名をそれと完全に一致させる。
  キーが定義されている場合、ビューの結果でキーが一意になるように書く（一意でないと、EF Core が行を取り違える）。
- **ビューは EF Core のマイグレーションでは作成されない**。ビューを作る SQL は `Core/MigrationsScript/` に置く。
  このフォルダの `.sql` はファイル名の昇順に実行され、リリース時もこのフォルダがそのまま配布される。既存の自動生成ファイルは編集しない。
  - ビュー 1 つにつき 1 ファイル、ファイル名は `V{4 桁の連番}_{ビュー名}.sql` とし、既存の最大の連番の次を使う。
    `V` で始めることで、数字で始まるテーブル定義のマイグレーション SQL より後に実行される。
    ほかのビューを参照するビューは、参照先より大きい連番にする。
  - ファイルの先頭で既存のビューを削除してから作成する（`DROP VIEW IF EXISTS …;` → `CREATE VIEW …`）。
  - 文字コードは BOM 付き UTF-8 とする。
- **SQL は対象の RDBMS の方言で書く**。開発環境と本番環境で RDBMS が異なる場合は、両方で動くことを確かめる。
- **参照しているテーブルの構造が変わったら、ビューも直す**。スキーマ定義の変更でテーブルの列名や構造が変わっても、ビューの SQL は自動では追従しない。

## 読み込み後処理は表示の補完に限る（両方式共通）

読み込み後処理（`OnAfterLoaded`）は、SQL の実行後に**現在ページの行だけ**を対象にメモリ上で動く。
ここで設定した値では絞り込み・並び替えができず、件数にも反映されない。

ここで行ってよいのは、DB の外にしかない情報（外部システム・ファイルなど）の補完と、SQL では表現できない表示用の整形だけである。
行を除外してはならない。

外部から情報を取得するときは、ページ内のキーをまとめて 1 回で取得するなどパフォーマンスに配慮すること。

## 見せてよい行の制限は CreateQuerySource で行う（両方式共通）

利用者の権限などによって閲覧できる行が限られる場合、その絞り込みは `CreateQuerySource` の中で行う。
ビュー方式では、`CreateQuerySource` をオーバーライドし、基底の実装が返す `IQueryable` に条件を追加する。
画面側で隠す・読み込み後処理で除外する方法では、件数とページングが狂ううえ、API を直接呼ばれると見えてしまう。

## 絞り込み・並び替えのオーバーライドでは、追加なら基底を呼ぶ（両方式共通）

自動生成の条件に追加したいのであれば基底の実装を必ず呼ぶ。呼ばないと、自動生成された条件がすべて無効になる。

## 検索処理の中でデータを書き換えない（両方式共通）

ログ出力を除き、DB・外部システム・ファイルへの書き込みを行わない。
