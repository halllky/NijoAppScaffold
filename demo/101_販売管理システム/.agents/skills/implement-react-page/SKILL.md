# React 画面の実装

画面は、自動生成されたモデル（`client/src/__autoGenerated`）と画面部品（`client/src/ui`）の上に組み立てる。

## 進め方

1. 画面が使うモデルを確認する。記憶や推測ではなく生成物を正とする。
   - `__autoGenerated/models/{モデル名}.ts` の型（`DisplayData`・`SearchCondition`・`RefTarget`・`SortableMember` など）、
     新規作成関数（`createNewDisplayData` など）、`deepEqual`、`metadata` 定数。
   - 呼び出すクエリモデル・コマンドモデルの名前と、引数・戻り値の型。サーバー側の振る舞い（検証・確認メッセージ・権限）は C# の実装を読んで確認する。
   - 生成物に `metadata` が無い、型が nijo.xml と食い違うなど、自動生成が古い場合は、回避コードを書かず再生成するようユーザーに伝える。
2. `ui/index.ts` を読み、使える部品を確認する。各部品の使い方は、その部品の JSDoc を読んで確認する。
3. `routes.tsx` を読み、画面がどう収集されてルーティングに登録されるか、`SearchDialogHost` がどこに置かれ、検索ダイアログの対応表がどこで組み立てられているかを確認する（後述「画面ファイルの構成」）。
4. 後述「画面の種類ごとの組み立て方」に従って実装する。
5. client フォルダで `npm run tsc` を実行し、型エラーが無いことを確かめる。
   そのうえで実際に画面を動かし、初期表示・入力エラー（クライアント側・サーバー側）・確認メッセージ・保存後の表示・画面離脱時の確認を確かめる。

---

## 自動生成されたファイルは編集しない

`__autoGenerated` は再生成で上書きされる。生成物のままでは実現できない場合は、コードを歪めて回避せずユーザーに報告する。

## ui は公開されたものだけを使い、画面の都合で変えない

- 画面からは `ui/index.ts` が export するものだけを使う。
- 入力欄・ラベル・メッセージ表示・グリッドの列は、基本的に `useDisplayDataForm` / `useSearchConditionForm` が返すもの（`Input`・`FieldLabel`・`RootErrors`・`useEditableGrid`）を使う。
  素の `<input>` や react-hook-form の `register` で項目を自作する場合はその理由をコメントで書く。
- ui で実現できないことがある場合、画面側で ui の内部を真似て作り込まない。どの画面でも使える機能として ui に足すべきか、ユーザーに確認する。

## 画面ファイルの構成

`routes.tsx` と `navigationItems.tsx` が画面のモジュールをどう集めているかを読み、それに合わせる。デモ101をもとにした構成では次のとおり。

- 業務画面のフォルダ（`pages`）の**直下**の `.tsx` が自動で集められる。1 画面 1 ファイル。ファイル名は、そのフォルダの既存のファイルの規則に合わせる（まだ無ければ `P{3 桁の番号}_{画面名}.tsx`）。
- 各画面のモジュールは次を export する。
  - `default`: ルーティング定義（`RouteObject`）。新規と編集のように 1 画面に複数の URL がある場合は配列。
  - `navigationItem`（任意）: 画面上部のナビゲーションに出す場合だけ。
  - 他の画面からその画面へ遷移するための URL を返す関数（例: `getLinkUrlTo{画面名}(キー)`）。URL 文字列を他の画面のファイルに直書きしない。
- 画面本体のコンポーネントは export しない。
- 複数の画面で使うダイアログや検索ダイアログは、自動収集の対象外の場所（業務画面のフォルダの下のサブフォルダなど）に置く。
- トップページ・ログイン・ログアウトの画面は業務画面ではなくアプリの枠の一部で、`App.tsx`・`routes.tsx` から直接参照されている。業務画面の番号はこれらと重ならないようにする。

## 業務画面は自己登録し、業務固有のコードは業務画面のフォルダの中に閉じる

業務画面は、ファイルを置くだけでルーティング・ナビゲーション・検索ダイアログの対応表に登録される（自己登録）。
そのため、業務画面のファイルやフォルダを丸ごと削除しても、残りのソースはそのままコンパイルが通る。この性質を崩さない。

- 業務画面を、共通部分（`App.tsx`・`routes.tsx`・`navigationItems.tsx`・検索ダイアログの対応表・`ui` など）から import しない。
  ルーティング・ナビゲーション・検索ダイアログへの登録は、共通部分の一覧に書き足すのではなく、画面やダイアログのモジュール自身の export で行う。
- 業務固有のコード（特定のモデルを扱う部品・関数・型）は、業務画面のフォルダの中に置く。`ui` や `client/src` 直下など、業務画面のフォルダの外に置かない。
  `ui` は特定のモデル（`__autoGenerated/models/…`）を import しない。
- デモ101そのものを改修する場合、デモ101から新規プロジェクトテンプレートを作る処理（業務画面と業務固有のフォルダを削除する）の後も `npm run tsc` が通る必要がある。
  業務画面のフォルダの外に業務固有のファイルを足すと、テンプレートにそのファイルが残るか、コンパイルが壊れる。

## サーバーは callComplexPostEndpointAsync で呼ぶ

一覧検索・外部参照の検索・コマンド実行は、すべて `example/callComplexPostEndpointAsync` を通す。第 1 引数はクエリモデル名・`ref-to:{参照先}`・コマンドモデル名で、引数と戻り値の型はそこから決まる。

- 戻り値の `type` は 3 通り。
  - `ok`: 成功。`returnValue` に戻り値、`detail` に警告・情報メッセージが入っていることがある。
  - `error`: 入力エラーなど。`detail` を画面のフォームの `setServerMessages` に渡す。
  - `canceled`: 利用者が確認メッセージでキャンセルした、または中断された。何もしない。
- 「〜しますがよろしいですか？」の確認はこの関数が行う。画面で `window.confirm` を自作しない。
  読み取りだけの呼び出し（検索・初期表示）には `{ ignoreConfirm: true }` を付け、更新するコマンドには付けない。
- 中断できる呼び出し（検索、入力に追従する再計算）には `signal` を渡す。
- 編集したデータを送る前に `example/toWillBeChangedApplied(読み込んだ時点の値, 現在の値, モデル.deepEqual)` を通す。
  変更された行にだけ `willBeChanged` が立ち、サーバー側はそれを見て更新対象を決める。比較の基準は、保存し直した後ではなく**画面が読み込んだ時点の値**にする。

## 業務ルールはサーバーに置く

- 入力値の検証・計算・権限判定の正はサーバー側である。画面で検証を足すのは、利用者が早く気付けるようにするためだけで、サーバー側の検証を省いてよい理由にはならない。
- 権限によってボタンを隠すのはよいが、それだけで操作を禁止したことにしない。
- 金額計算のような業務上の計算は、画面で再実装せず、計算用のコマンドを呼んで結果を表示する（後述「入力に追従するサーバー計算」）。

## 項目の並べ方

```tsx
<FieldGroup labelWidth="6rem">
  {/* 意味のまとまりごとに列を分ける */}
  <FieldColumn>
    <FieldLabel name="受付日" requiredMark>
      <Input.DateInput name="受付日" />
    </FieldLabel>
    <FieldLabel name="担当者">
      <Input.RefTo name="担当者" />
    </FieldLabel>
  </FieldColumn>
  <FieldColumn>
    ...
  </FieldColumn>
  {/* FieldGroup 直下の FieldLabel は横幅いっぱい */}
  <FieldLabel name="備考">
    <Input.TextArea name="備考" />
  </FieldLabel>
</FieldGroup>
```

- 項目は `FieldLabel` で囲む。表示名・ヘルプ・その項目のメッセージは `FieldLabel` が表示するので、ラベル文字列を画面に直書きしない。
- 並びは `FieldGroup` と `FieldColumn` で決める。列の区切りは項目の意味の切れ目に置く。ラベル幅は `labelWidth` でそろえる。
- 入力欄は項目の型に合ったものを使う。合わないものを使うと描画時に例外になる。

  | 項目の型 | フォームの入力欄 | グリッドの列 |
  |---|---|---|
  | 単語 | `Input.TextBox` | `col.text` |
  | 文章 | `Input.TextArea` | `col.textArea` |
  | 整数・小数・シーケンス・年 | `Input.NumericTextBox` | `col.numeric` |
  | 日付・日時・年月 | `Input.DateInput` | `col.date` |
  | 真偽値 | `Input.CheckBox` | `col.checkBox` |
  | 列挙体 | `Input.EnumSelection` | `col.enumeration` |
  | 外部参照 | `Input.RefTo` | `col.refTo` |

- 検索条件のフォームでは同じ入力欄が検索条件用の外観（範囲指定・複数選択など）になる。`name` は絞り込み条件（`filter`）から見たパスで書く。
- 数値の単位（「円」「個」など）と桁区切りは、メタデータのカスタム属性（金額項目・数量）で決まる。画面ごとに単位を付け足さず、nijo.xml の項目に属性を付ける。
  `ReadOnlyColumn.numeric` の `suffix` のように画面側で指定する部品を使う場合は、その属性と食い違わないようにする。
- 読み取り専用は `isReadOnly`、入力欄ごとの追加の検証は `rules`（`required`・`validate`）で指定する。
  `rules.required` と `FieldLabel` の `requiredMark` は連動しないので、両方指定する。
- 配置にこだわらない画面（管理用の画面など）は、`AutoDisplayDataFields` / `AutoSearchConditionFields` / `autoResultColumns` でメタデータから機械的に組み立ててよい。

## メッセージ

- フォームごとに `RootErrors` を必ず 1 つ置く。`FieldLabel` もグリッドの列も無い項目へのメッセージはここに集まる。置かないとメッセージが利用者に届かない。
- メッセージには 2 種類ある。
  - クライアント側エラー: メタデータの入力制約、`rules`、`formMethods.setError`。react-hook-form の検証の仕組みで消える。
  - サーバー側メッセージ: `setServerMessages(detail)` で表示する。次の `setServerMessages` か `clearServerMessages` まで消えない。
- サーバー側メッセージは、**送信したときの値**の `instanceId` で項目と結びつけられる。保存後にフォームの値を置き換える（`reset`）場合は、置き換える前に `setServerMessages` を呼ぶ。
- メッセージ表示を画面で自作しない。

## 画面離脱時の確認

`PageBase` の `isDirty` に `formMethods.formState.isDirty` を渡す。保存後に遷移するときは、先に `reset` して編集中でない状態に戻してから遷移する（同じ処理の中で続けて呼んでよい）。

## 画面の種類ごとの組み立て方

### 一覧検索画面（クエリモデル 1 つを検索する）

`useSearchConditionForm` と `SearchPageBase` で組み立てる。
検索の実行、URL のクエリパラメータとの同期、ページング、並び替え、検索中の表示、検索エラーの表示は `SearchPageBase` が行うので、画面で検索を effect から呼んだり結果を state に持ったりしない。

```tsx
function 〇〇一覧画面() {
  // 検索条件のフォーム
  const form = useSearchConditionForm(〇〇一覧)
  const { Input, FieldLabel } = form

  return (
    <SearchPageBase
      form={form}
      pageTitle="〇〇"
      sortOptions={SORT_OPTIONS}
      createInitialCondition={createInitialCondition}
      search={(condition, signal) => callComplexPostEndpointAsync('〇〇一覧', condition, { ignoreConfirm: true, signal })}
      header={<Link to={getLinkUrlTo〇〇詳細()} className="text-teal-600 underline">新規登録</Link>}
      searchCondition={(
        <FieldGroup>
          ...（検索条件の FieldLabel と Input）
        </FieldGroup>
      )}
      defineSearchResultColumns={[() => [
        // 詳細画面へのリンク。クリックでセルが選択されないよう interactive を使う
        ReadOnlyColumn.interactive<〇〇一覧.DisplayData>('', row => (
          <Link to={getLinkUrlTo〇〇詳細(row.〇〇ID)} className="text-sky-600 underline">詳細</Link>
        ), { columnId: '詳細リンク', defaultWidth: 60, isFixed: true }),
        ReadOnlyColumn.text<〇〇一覧.DisplayData>('名称', row => row.名称, { columnId: '名称' }),
        ReadOnlyColumn.numeric<〇〇一覧.DisplayData>('金額', row => row.金額, { columnId: '金額', suffix: '円' }),
      ], []]}
    />
  )
}

/** 並び順の選択肢。キーは生成された SortableMember 型で検査される */
const SORT_OPTIONS: SortComboItem<〇〇一覧.SortableMember>[] = [...]

/** 画面を開いたときとクリアしたときの検索条件。既定の並び順もここで決める */
function createInitialCondition(): 〇〇一覧.SearchCondition {
  return { ...〇〇一覧.createNewSearchCondition(), sort: [/* 生成された型が許す並び順の文字列 */] }
}
```

- 検索結果の列は `ReadOnlyColumn` の `text` / `numeric` / `custom` / `interactive` で定義する。`columnId` は必須で、グリッド内で重複させない。
- 行の詳細をその場で見せたい場合は `sidePane` を使う。

### 詳細編集画面（1 件を読み込んで編集・保存する）

```tsx
export default [
  { path: "/xxx/new", element: <〇〇詳細 mode="new" />, loader: async () => { /* 初期表示コマンド */ } },
  { path: "/xxx/edit/:id", element: <〇〇詳細 mode="edit" />, loader: async ({ params }) => { /* 初期表示コマンド */ } },
] satisfies ReactRouter.RouteObject[]
```

1. **読み込み**は React Router の `loader` で行う。初期表示用のコマンドかクエリモデルを `ignoreConfirm: true` で呼び、`ok` でなければ例外を投げる（ルートのエラー画面が表示される）。
   新規登録で初期値の加工が要るなら、それも初期表示コマンドに任せるか、loader の中で行う。
2. **フォーム**は `useDisplayDataForm(モデル, { defaultValues: loaderData })`。
   保存後の再読み込みなどで loader のデータが変わったらフォームを置き換える effect を置く（ルーターとの同期）。
   ```tsx
   React.useEffect(() => { reset(loaderData) }, [loaderData, reset])
   ```
3. **保存**は `formMethods.handleSubmit` で包む。外部参照のコードの照合は非同期の検証として登録されており、`handleSubmit` はその完了を待つので、照合中かどうかを画面で気にしなくてよい。
   ```tsx
   const handleSave = handleSubmit(async values => {
     const currentValues = toWillBeChangedApplied(loaderData, values, 〇〇詳細.deepEqual)
     const result = await callComplexPostEndpointAsync('〇〇登録', currentValues)
     if (result.type === 'canceled') return
     setServerMessages(result.detail)
     if (result.type !== 'ok') return
     // 新規登録: 編集中でない状態に戻してから、登録したデータの編集画面へ遷移する
     reset(values)
     navigate(getLinkUrlTo〇〇詳細(result.returnValue.〇〇ID))
     // 修正: loader を再実行して最新の値（バージョンなど）を読み込み直す → revalidate()
   })
   ```
4. **枠**は `PageBase`。`isDirty` を渡し、保存ボタンは `Button` の `loading={isSubmitting}` で二重送信を防ぐ。

### 明細（子配列）のグリッド

```tsx
// 行の追加・削除。グリッドはこれらの手段を持たないので useFieldArray を併用する
const { append, remove } = RHF.useFieldArray({ control, name: '明細' })
const handleAddRow = () => {
  const row = 〇〇詳細.createNewDisplayData_明細()
  append(row, { shouldFocus: false })
}
// グリッドが渡す行の位置は画面上の位置なので、配列の添字は instanceId から求める
const handleRemoveRow = useEvent((rowKey: string) => {
  const index = getValues('明細').findIndex(row => row.instanceId === rowKey)
  if (index !== -1) remove(index)
})

// グリッド。列の見出しと入力制約はメタデータから決まる
const [gridProps, rowMessages] = useEditableGrid('明細', {
  columns: col => [
    col.refTo('商品', { defaultWidth: 360 }),
    col.numeric('数量', { isReadOnly: row => row.existsInDatabase }),
    col.button('削除', (_, rowKey) => handleRemoveRow(rowKey)),
  ],
}, [])

// 描画。行ごとのメッセージの一覧は、配列の FieldLabel の中に置く
<FieldLabel name="明細" vertical afterLabel={<Button mini outline onClick={handleAddRow}>行追加</Button>}>
  {rowMessages}
</FieldLabel>
<EditableGrid {...gridProps} className="flex-1 min-h-32 border border-gray-300" />
```

- 行は `instanceId` で識別される。行を複製するときは `instanceId` を振り直す。
- 行の新規作成は生成された `createNewDisplayData_{子配列}` を使う。画面で採番する必要のあるキー（UUID など）があれば、ここで設定する。
- 列の定義が画面の値（state など）を参照する場合は、第 3 引数の deps に列挙する。
- 読み取り専用は、グリッド全体なら `EditableGrid` の `isReadOnly`、行・セル単位なら列の `isReadOnly` に関数で指定する。
- 項目と結びつかない表示専用の列は `ReadOnlyColumn` を混ぜてよい。
- 子配列の中にさらに子配列がある場合はグリッドに収まらない。行ごとに枠を作って、その中に入力欄を並べる。

### 一括編集画面（検索した複数件をまとめて編集・保存する）

- 検索条件のフォーム（`useSearchConditionForm`）と、編集のフォーム（一括更新コマンドの引数の `useDisplayDataForm`）の 2 つを持つ。メッセージはそれぞれのフォームの `RootErrors` に出る。
- 検索結果を編集フォームの行に詰め替えるときは、`existsInDatabase = true`、`willBeChanged = false` にする。
  詰め替えた値を「読み込んだ時点の値」として ref に保持し、保存時の `toWillBeChangedApplied` の比較の基準にする。
- 削除は、DB に保存済みの行なら `willBeDeleted` を立てる（保存時に削除される。復元もできる）。新しく追加した行なら配列から取り除く。
- 保存できたら、同じ検索条件で検索し直してフォームを置き換える（バージョンなどを最新にするため）。サーバー側メッセージはその前に渡す。

### 照会画面（編集しない）

- フォームは使わない。`loader` で必要な検索を `Promise.all` でまとめて呼び、結果を表示する。
- 一覧は `EditableGrid` に `ReadOnlyColumn` の列を渡して表示する。`rowKeys` と `getLatestRowObject` は表示する配列から `useMemo` / `useCallback` で作る。
- 画面内の一覧のページングは `Pager` を使い、現在のページは URL のクエリパラメータで持つ（loader が読み、再読み込みやブラウザバックで復元される）。

### モーダルダイアログ（画面から開いてコマンドを実行する）

- `Modal` と `useDisplayDataForm` で作り、呼び出し側は**表示している間だけ描画する**（`{isOpen && <〇〇ダイアログ ... />}`）。描画のたびに入力内容が初期状態から始まる。
- 閉じる処理と、成功後の画面の再読み込みは呼び出し側に任せ、props（`onClose`・`onSuccess` など）で受け取る。その責務の境界をコンポーネントの JSDoc に書く。
- 入力欄は `<form noValidate onSubmit={handleSubmit(...)}>` の中に置く（検証はブラウザでなく react-hook-form で行う）。

### 外部参照の検索ダイアログ

- 外部参照の入力欄（`Input.RefTo`・`col.refTo`）は、項目のメタデータの参照先から、`SearchDialogHost` に渡された対応表を引いて検索ダイアログを決める。画面側は検索ダイアログを指定しない。
- デモ101をもとにした構成では、参照先のメタデータから自動で組み立てた検索ダイアログが既定で使われる。
  検索条件欄・結果の列・コードと名称にする項目を調整したい場合だけ、`defineSearchDialog` で個別に定義し、対応表に登録する。
  登録は、対応表を組み立てているモジュールを書き換えずに、検索ダイアログを定義したモジュール自身の export と型の登録（モジュール拡張）で行う（自己登録）。
  具体的な書き方は、対応表を組み立てているモジュールの JSDoc に従う。
  個別の定義を削除すれば、その参照先は自動で組み立てた検索ダイアログに戻る。
- 外部参照の入力欄以外から検索ダイアログを使う（例: 複数の商品を選んで明細に一括追加する）場合は、
  検索ダイアログの `useOpen()` が返す `selectOne` / `selectMany` を呼ぶ。戻り値は選ばれたもの、選ばずに閉じたら `undefined`。

## 入力に追従するサーバー計算

金額の自動計算のように、入力が変わるたびにサーバーで計算した結果を表示する場合は次のようにする。

- 計算のきっかけになる項目だけを `useWatch` で取り出し、`JSON.stringify` した文字列を effect の依存にする（サーバーとの同期）。
  配列やオブジェクトをそのまま依存にすると、値が同じでも参照が変わるたびに呼ばれてしまう。
- 前回の呼び出しは `AbortController` で中断し、中断された呼び出しの結果は捨てる。
- 結果は `setValue` で該当の項目に書き戻す。行ごとの結果は、行の添字ではなくキーや `instanceId` で突き合わせる。

## フォームの値の変化に反応する処理

ある項目を選んだら別の項目に既定値を入れる、のような処理は、まずイベントハンドラで書けないかを考える。
外部参照のセルのように値の変更を受け取る手段が無い入力欄の場合だけ、`formMethods.subscribe` で値の変化を購読して行う。
その場合、DB から読み込んだだけの行を書き換えない（読み込んだだけで編集中扱いになり、離脱確認が出てしまう）。

## 見た目

- スタイルは Tailwind のユーティリティクラスを直接書く。ボタンは `Button`（`fill` / `outline` / `mini` など）を使い、画面ごとに色を作らない。
- 画面内リンクは react-router-dom の `Link` を使う（`<a href>` だと画面全体が読み込み直される）。
- グリッドのセルの中にリンクやボタンを置くときは `ReadOnlyColumn.interactive` か `col.button` を使う。自作するとクリックでセルの選択が始まってしまう。
