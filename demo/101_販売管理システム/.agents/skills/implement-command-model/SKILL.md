# コマンドモデルの実装

コマンドモデルは、利用者やスケジューラーによる「1 回の操作」を表す。
自動生成されるのは `Execute{コマンド名}Async` の抽象メソッドと、それを呼び出す窓口だけであり、処理の中身はすべて開発者が書く。

## 進め方

1. 自動生成された抽象メソッドのシグネチャ（引数・戻り値・メッセージの型）を確認する。記憶や推測ではなく生成物を正とする。
2. アプリケーションサービス（`OverridedApplicationService`）の partial class にオーバーライドを書く。ファイルは次のように分ける。
   - Core プロジェクトの中に業務のまとまりごとのフォルダを作り、コマンド 1 つにつき 1 ファイル、ファイル名はコマンド名とする。
   - 複数のコマンドで共有する、データモデルの整合性チェックや保存後処理のメソッドは、コマンドのファイルに混ぜず、そのデータモデル用のファイル（`{データモデル名}DataModel.cs`）にまとめる。
   - 外部システムとの通信は、コマンドのファイルに直接書かない。外部システムごとのフォルダにインターフェースと実装（本番用・開発用モック）を置き、DI で切り替えられるようにする。
3. ビルドし、実際に呼び出して確かめる。正常系に加え、入力エラー・権限なし・検証のみモードの各場合を確かめる。

---

## 自動生成されたファイルは編集しない

振る舞いはオーバーライドで変える。生成物のままでは実現できない場合は、コードを歪めて回避せずユーザーに報告する。

## 処理の順序は Execute メソッドに並べる

典型的な順序は次のとおり。該当しない段は省く。

1. 権限チェック（画面でボタンを隠していても API は直接呼べるため、必ずサーバーで判定する）
2. コマンドの読み込み（`LoadForEdit{データモデル名}Async`）または作成（`StartCreating{データモデル名}`）
3. 値の設定と入力チェック（`GetValidationErrors` と独自のチェック）。エラーがあればここで return
4. 検証のみモードなら、確認メッセージを積んで return
5. トランザクション開始
6. 保存（`TrySaveAsync`）。失敗したらコミットせずに return
7. コミット（外部システムへの更新もここで実行される）
8. 戻り値と完了メッセージの設定（コミット前に設定すると、失敗時に存在しないデータを画面に返してしまう）

## 検証のみモードでは何も変えない

同じコマンドが「検証のみ」（`context.ValidationOnly == true`）と「実行」の 2 回に分けて呼ばれることがある。
検証のみのときは、DB・外部システム・ファイル・メール送信など、あらゆる副作用を起こさない。

- 自動生成された部品や `TrySaveAsync` は検証のみモードを判定しない。`TrySaveAsync` の前で判定して抜ける。
- `GetValidationErrors` までは検証のみモードでも実行し、データモデル側の検証エラーも 1 回目で利用者に見せる。
- 自前で書く副作用は、トランザクションへの予約（後述）を通すか、`ValidationOnly` が false のときだけ行う。

## 初動対応するのが利用者ならメッセージで返し、運用担当者なら例外を投げる

エラーを `context.Messages` で返すか例外で投げるかは、そのエラーに最初に対処するのが誰かで決める。
「想定内かどうか」「業務上起こりうるかどうか」では決めない。

- **利用者が画面上で対処できる**もの（入力誤り、権限のない操作、他者の更新との競合、業務上の前提を満たさない操作など）は、`context.Messages` に設定して処理を抜ける。
- **利用者には対処できず、運用担当者がログを見て対処する**もの（外部システムの障害、設定値の欠落、あるはずのマスタデータが無い、データ不整合、バグなど）は例外を投げる。
  利用者に「管理者に連絡してください」と伝えるしかないものは例外にする。
- 例外をキャッチして利用者向けメッセージに変換しない。運用担当者に届くべき情報が消える。
  例外メッセージには、運用担当者が原因と対象を特定できる情報（処理名、キー、外部システム名など）を含める。

メッセージで返すときは次のようにする。

- メッセージはできるだけ具体的な位置（項目、明細の i 行目の項目など）に付ける。どの項目にも属さないものだけ全体（ `context.Messages.AddError` など Messages 直）に付ける。
- 1 件目のエラーで打ち切らず、独立して検証できるものは全部検証してから抜ける。
  後続の検証が前提を失う場合（キーが空など）だけ、その場で打ち切る。

## 保存は TrySaveAsync を通す

データモデルの登録・更新・削除は、自動生成されたコマンドを `DbContext.TrySaveAsync` に渡して行い、DbContext に直接書き込まない。
監査項目の設定と楽観排他が保存処理の中で行われているため。

- 保存結果は必ず確認する。失敗していれば `result.Errors.CopyTo(context.Messages)` で利用者に伝え、以降の処理を行わずに抜ける。
- 複数件はループ後にまとめて `TrySaveAsync` に渡す。
- 意図的に迂回するときは、その理由をコメントに残す。

## 検証エラーの付与先は画面の項目に合わせる

`GetValidationErrors()` の結果は `CopyTo` で画面側のメッセージへ移す。`CopyTo` は同名のパスにそのままコピーするので、階層や名前が違うときは対応する階層を渡す。階層が合っていないと、エラーで処理は止まるのに画面の項目に表示されない。

## どこから書き込まれても守るべきルール（ユースケース非依存のルール）はデータモデル側に書く

「このデータは常にこうでなければならない」というルール（例: 明細は 1 件以上、確定済みの明細は変更不可）は、
データモデル用のファイルに名前付きのメソッドとして書き、そのデータモデルを保存するすべてのコマンドから呼ぶ。
保存後に常に行う処理（例: 在庫数量の通知）も同様に、`TrySaveAsync` の成功後に呼ぶ。
自動的には呼ばれないので、新しいコマンドを追加するときは既存のコマンドを確認して呼び漏らさないようにする。

## 画面で編集されたデータは、画面が読み込んだ時点のバージョンで更新する

更新・削除では、画面が読み込んだ時点のバージョンを引数から受け取って `{データモデル名}KeyWithVersion` に渡す。
保存の直前に DB から読み直したバージョンを渡すと、利用者が画面を開いている間の他者の更新を黙って上書きしてしまう。
バージョンが null だと例外になる。楽観排他は省略できない。
画面を介さないバッチなどでは任意の条件で読み込み（`LoadForEdit{データモデル名}Async(query => ...)`）、読み込み時点のバージョンで排他をかける。

## トランザクションはアプリケーションサービスの BeginTransactionAsync で張る

`DbContext.Database.BeginTransactionAsync` を直接呼ばない。直接呼ぶと、外部システム（外部 API、ファイル、メール、メッセージキューなど）への更新がトランザクションに連動しなくなる。

```csharp
await using var tran = await BeginTransactionAsync();
var result = await DbContext.TrySaveAsync(command);
if (!result.Success) { // コミットせずに抜ければ、DB はロールバックされ、予約した外部更新も実行されない
    result.Errors.CopyTo(context.Messages);
    return;
}
// 外部システム更新の予約
await tran.CommitAsync();
```

- **ロールバックは、コミットせずにスコープを抜けることで行う**。明示的なロールバックは書かない。
- **トランザクションはネストできない**。Execute メソッドの中で開始・コミットし、下請けメソッドの中で開始しない。
- **外部システムへの更新は、その場で実行せずトランザクションに予約する**（`CurrentTransaction.Prepare(リソース名, 更新処理)`）。
  予約した更新がコミット時にどう実行されるか（順序、失敗時の扱い）は `ExternalResourceTransaction` を読んで確認する。
  - 予約は外部システムのインターフェースの実装の中で行い、トランザクションの外で呼ばれたら例外を投げるようにする。コマンドからはインターフェースのメソッドを呼ぶだけにする。
  - 失敗より前に成功した外部更新は取り消されず、運用担当者が復旧する。そのためリソース名にはどのデータを更新しようとしたか（キーなど）を含める。
    1 つの操作で複数の外部更新を予約するときは、途中で失敗した場合の復旧方法を決めてから実装する。
  - 一時的な失敗に対するリトライは、予約する更新処理の中で行う。
  - 外部更新の失敗による例外はキャッチしない。
- **外部システムからの読み取り**は予約不要で、その場で行ってよい。
- **トランザクションの範囲は業務要件から決め、Execute メソッド上で見えるように書く**。
  「全件まとめて成功か失敗か」ならループの外で 1 回、「1 件ずつ確定する」ならループの中で都度開始・コミットする。
  1 件ずつ確定する場合は、その理由をコメントに残し、一部だけ成功したことを利用者に伝えるメッセージも実装する。

## 現在時刻はアプリケーションサービスが提供するものを使う

`DateTime.Now` を直接呼ばず、アプリケーションサービスの `CurrentTime` を使う。1 回の操作の中で時刻がぶれず、テストで時刻を固定できる。
