# README

開発環境の用意と、開発の始め方を書く。アプリケーションの振る舞いは `標準仕様書.md` に書く。

## 必要なもの

- .NET SDK と Node.js（バージョンは標準仕様書 2.1）
- nijo のコマンドラインツール（nijo の配布元から入手する）。パスを通すか、環境変数 `NIJO_CLI_PATH` にそのパスを設定する。以降の `$NIJO_CLI_PATH` は nijo のコマンドを指す。
- 手順のスクリプトを動かすための bash。Windows では bash が動く環境を用意する。
- マイグレーションを作る場合は `dotnet-ef`

## 起動

1. `nijo new <フォルダ> --template demo101` で、テンプレートから新しいプロジェクトを作る。
2. client プロジェクトで `npm ci` を実行する。
3. Task フォルダの DEBUG.sh を実行する。
   - 自動生成とビルドをやり直したうえで、サーバーと画面の開発サーバーを同時に起動する。
   - 別々に起動する場合は、このフォルダで `$NIJO_CLI_PATH generate` を実行してから、WebApi プロジェクトで `dotnet watch`、client プロジェクトで `npm run dev` を実行する。
4. 画面の開発サーバーが表示する URL をブラウザで開く。
5. 画面上部のデバッグメニューから DB を作り直す（標準仕様書 22.2）。
6. ダミーデータのユーザーでログインする（ユーザー ID とパスワードは、ダミーデータを作る処理に書かれている）。

## nijo.xml の編集と再生成

- `$NIJO_CLI_PATH serve` で、nijo.xml を編集する画面が開く。保存時に自動生成するよう設定するか、`$NIJO_CLI_PATH generate` で再生成する。
- 画面側はホットリロードで、サーバー側は `dotnet watch` で、変更が反映される。
- DB の定義が変わった場合は、Task フォルダの ADD_MIGRATION.sh でマイグレーションを追加する（標準仕様書 5.3）。

## チームでの開発

- 開発者全員が、同じバージョンの nijo を使う。生成されるコードはバージョン管理しないので（標準仕様書 3.4）、生成されるコードは各開発者の nijo のバージョンで決まる。
- nijo.xml は1つのファイルだが、要素ごとに一意の識別子（UniqueId 属性）をもち、属性を1行ずつ書く形で保存される。そのため、別々の要素への変更は、通常のマージで合わせられる。同じ要素を同時に変えた場合は、手で解決する。
- ブランチを取り込んだ後は、再生成してからビルドする。
- マイグレーションは、複数のブランチで同時に追加すると、マイグレーションの名前の番号と、モデルの状態を記録したファイルが重なる。重なった場合は、片方のブランチのマイグレーションを削除し、取り込んだ後の nijo.xml でマイグレーションを追加し直す。
- 開発環境の DB（SQLite のファイル）と、開発環境用の設定ファイルは、開発者ごとに持つ。

## nijo のリファレンスの入手

- `$NIJO_CLI_PATH generate-reference --out <出力先>` で、項目の型とコマンドラインの使い方のリファレンスが Markdown で出力される。
- nijo.xml の書き方の詳細は、nijo の配布元のドキュメントを参照する。

## アプリケーションの名前と名前空間の変更

- テンプレートの名前 `MyApp` でフォルダ全体を検索し、新しいアプリケーションの名前に置き換える。
  - デモ101のリポジトリの中では、プロジェクトのファイル名は `Demo101` になっている。テンプレートとして配布するときに `MyApp` に置き換えられる。
- 置き換える対象の種類は次のとおり。個々のファイルの一覧は検索の結果を正とする。
  - nijo.xml のアプリケーション名とルート名前空間（変えたら再生成する）
  - 手書きのコードの名前空間
  - ソリューションとプロジェクトのファイル名、プロジェクト間の参照
  - client プロジェクトのパッケージ名
  - 画面に表示するアプリケーション名とブラウザのタブのタイトル
- 置き換えた後、再生成・ビルド・型チェックが通ることを確認する。
